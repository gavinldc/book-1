# 第 1 章　为什么用 Cloudflare 做游戏后端

> 状态：初稿　｜　限额与定价核实日期：2026-11-20（1.6、1.8 节为 2026-11-24）

这一章回答四个问题：Cloudflare 这套东西能不能撑起一个游戏后端，哪些游戏适合、哪些不适合，一个月要花多少钱，以及它和 AI 结合、用 vibe coding 的方式开发为什么更省事。读完你应该能判断自己的项目该不该往下看。

## 1.1 游戏后端到底要做什么

抛开具体玩法，一个联网游戏的后端大致要做六件事：

1. **认人**：知道请求是谁发的，同一个玩家换设备、换平台后还是同一个人。
2. **存档**：玩家的等级、货币、背包不能丢，也不能被客户端随便改。
3. **对局**：把几个玩家放进同一个房间，按规则推进状态，并把结果同步给每个人。
4. **排名与社交**：排行榜、好友、邀请。
5. **收钱**：支付回调、发货、补单。
6. **运营**：配置下发、活动、埋点、告警。

传统做法是租几台云服务器，跑一个常驻进程管房间，再配上 MySQL、Redis、消息队列和负载均衡。这套方案成熟，但小团队要为它付出两样东西：一是运维精力，二是为流量峰值预留的闲置机器。

Cloudflare 的开发者平台提供了另一种拼法：没有服务器要管，按请求计费，代码默认部署在全球。问题在于它不是为游戏设计的，哪些地方合用、哪些地方别扭，需要拆开看。

## 1.2 手上有哪些积木

本书会用到的产品如下，后面各章会逐个展开。

| 产品 | 是什么 | 在游戏后端里的角色 |
|---|---|---|
| Workers | 运行在边缘节点上的无状态函数 | HTTP 接口入口、鉴权、路由 |
| Durable Objects | 带私有存储的单线程有状态对象，每个对象全球唯一 | 房间、匹配队列、排行榜、单个玩家的会话 |
| D1 | 托管的 SQLite 数据库 | 账号、订单等需要跨玩家查询的数据 |
| KV | 最终一致的键值存储，读多写少 | 远程配置、静态表 |
| R2 | 对象存储 | 对局回放、日志归档、资源文件 |
| Queues | 消息队列 | 埋点上报、异步发奖、削峰 |
| Workers AI | 平台托管的模型推理 | 聊天翻译、内容审核、机器人台词 |

这里面最关键的是 Durable Objects（下文简称 DO）。没有它，Workers 只是一个无状态的接口层，做不了房间。

## 1.3 核心模型：一个房间一个对象

DO 的特性可以概括成三句话：

- 每个对象有一个全局唯一的 ID，全世界对同一个 ID 的请求都会被路由到同一个实例上。
- 对象内部是单线程的，同一时刻只处理一个事件，不需要加锁。
- 每个对象自带一份私有的 SQLite 存储，读写是本地调用。

这正好对应游戏里"房间"的概念：一个房间一个对象，房间里的玩家都连到它上面，状态在对象内存里，落盘用自带的存储。下面是一个最小的房间，它接受 WebSocket 连接，并把任何一个人发来的消息广播给房间里的所有人：

```ts
import { DurableObject } from "cloudflare:workers";

export class Room extends DurableObject<Env> {
  async fetch(request: Request): Promise<Response> {
    const pair = new WebSocketPair();
    const [client, server] = Object.values(pair);
    this.ctx.acceptWebSocket(server); // 交给运行时托管，对象空闲时可以休眠
    return new Response(null, { status: 101, webSocket: client });
  }

  async webSocketMessage(ws: WebSocket, message: string | ArrayBuffer) {
    for (const peer of this.ctx.getWebSockets()) {
      peer.send(message);
    }
  }
}

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const roomId = new URL(request.url).searchParams.get("room") ?? "lobby";
    return env.ROOM.getByName(roomId).fetch(request);
  },
};
```

这段代码里没有连接管理、没有进程间通信、没有"这个房间在哪台机器上"的路由表。传统架构里要自己解决的房间寻址问题，平台用对象 ID 替你解决了。

`acceptWebSocket` 这一行值得注意。它启用的是 WebSocket 休眠机制：对象一段时间没有收到事件后会被移出内存，但客户端的连接仍然挂在 Cloudflare 的网络上；下一条消息到来时，对象被重新唤醒，构造函数再执行一次。休眠期间不计时长费用，代价是内存里的状态会清空，所以重要状态必须落到存储里。第 5 章会详细讲怎么围绕这一点设计房间。

## 1.4 适合什么样的游戏

**回合制与房间制对战。** 棋牌、飞行棋、宾果、卡牌对战这一类，消息频率低，每条消息都要服务端裁决，状态量小。这是 DO 最舒服的场景。

**异步对战。** 玩家打的是对手的阵容快照或操作回放，后端只需要存取数据和校验结果，用 Workers 加存储就够了。

**休闲与超休闲的联网部分。** 存档、排行榜、邀请奖励、广告发奖校验。这类游戏的后端请求零散，买量时流量又会突然冲高，按请求计费、自动扩缩容的模型很合适。

**玩家分布在多个地区。** Workers 在离玩家最近的节点执行。DO 则会创建在离首个请求者较近的位置，对同一地区的玩家凑成的房间比较友好。

**没有专职运维的小团队。** 没有机器要打补丁，没有容量要规划，部署是一条命令。

免费额度也足够做原型：Workers 每天 10 万次请求，使用 SQLite 存储的 DO 在免费版里就能用。

## 1.5 不适合什么样的游戏

这一节比上一节重要。选错了方向，后面的章节帮不了你。

**帧同步和高频状态同步。** 射击、格斗、MOBA 这类游戏每秒要同步十几到几十次。问题有三个：其一，客户端到 Workers 只能走 WebSocket，它建立在 TCP 上，丢一个包会卡住后面所有的包，弱网下延迟抖动明显；Workers 的套接字接口文档只列出了 TCP，没有提供 UDP。其二，高频消息让房间对象永远无法休眠，时长费用会全额计算（见 1.7）。其三，收到的每条消息都计费。

**重 CPU 的服务端计算。** 每个实例的内存上限是 128 MB。付费版单次请求的 CPU 时间默认上限是 30 秒，最高可调到 5 分钟，免费版只有 10 毫秒。大规模寻路、物理模拟、服务端跑完整战斗演算，都不该放在这里。

**单场景大量玩家。** 一个 DO 是单线程的，官方给出的软限制是每个对象每秒约 1,000 个请求。几百人挤在同一个场景里互相可见的玩法，需要你自己把场景切片到多个对象上，复杂度会迅速上升。

**需要常驻内存的大状态。** 对象会被休眠和驱逐，内存只能当缓存用。习惯把整个世界放在进程内存里的架构，搬过来要重写。

**复杂的跨玩家查询。** D1 单库上限是 10 GB（免费版 500 MB），DO 的存储则是每个对象各管各的。需要对全体玩家做复杂统计分析的需求，应该把数据导出到专门的分析系统，而不是在线上库里查。

**主要用户在中国大陆。** 本书面向出海场景。Cloudflare 在大陆境内的访问质量和合规要求是另一个话题，不在讨论范围内。

还有一个不属于技术限制、但必须提前想清楚的问题：**平台绑定**。DO 没有其他云厂商的等价产品，用它写出来的房间逻辑迁移成本很高。本书的应对办法是把游戏规则写成与平台无关的纯函数，只让薄薄的一层去接触平台接口，第 2 章会讲目录怎么分。

## 1.6 规模上来以后

上一节讲的是不适合的游戏。这一节讲另一个问题：游戏类型合适，但做大了会碰到什么。下面四个天花板都有出路，前提是在设计阶段就留好位置，等撞上了再改代价会很高。这里只说结论和方向，具体做法在后面的章节。

**数据超过 D1 的 10 GB。** D1 单库上限是 10 GB，官方明确说明这个上限不能申请提高。它的设计思路本来就不是一个大库，而是横向扩展成很多个小库。对应到游戏里，本书的做法分几层：

- 玩家自己的数据（存档、背包、货币）不放 D1，放在每个玩家各自的 Durable Object 存储里。付费版的账号总容量不设上限，单个对象上限 10 GB，相当于天然按玩家分库。
- D1 只放需要跨玩家查询的数据，比如账号索引、订单、邀请关系，这部分增长慢得多。
- 日志和埋点不进 D1，通过队列写到 R2 或外部的分析系统。
- 仍然超了，就按地区或按哈希拆成多个库，冷数据归档到 R2。付费版包含 10 万个数据库的额度。
- 最后的出口是 Hyperdrive：它让 Workers 高效地连接外部的 Postgres 或 MySQL，可以把关系型数据整体搬出去，接口层的代码不用大改。

详见第 3 章。

**全服推送。** 平台没有现成的全服广播。一个对象能挂的连接数是"数千"这个量级，不可能让全服玩家都连到同一个对象上。先分清你要的是哪一种推送，三种需求的做法完全不同：

| 需求 | 做法 |
|---|---|
| 公告、活动开启、配置更新，不要求秒级到达 | 不推送。客户端定期拉取一个版本号，接口结果走缓存，成本几乎为零。大部分所谓的全服推送属于这一类 |
| 在线玩家的实时广播，比如跑马灯、全服事件 | 设一组"频道"对象，玩家按 ID 哈希连到其中一个。广播时由 Worker 或队列逐个通知这组对象，每个对象再发给自己身上的连接。发出的消息不计请求费 |
| 离线玩家的系统通知 | 平台本身做不了，需要接 FCM、APNs，或者各平台自己的消息能力，比如 Telegram 的机器人消息 |

实时广播这一类也可以交给专门的第三方实时消息服务。详见第 5 章和第 9 章。

**全局热点对象。** 排行榜、匹配队列这类东西，最直接的写法是做成一个全局对象。但每个对象是单线程的，软限制是每秒约 1,000 个请求，超出后请求会先排队，再返回过载错误。出路是分片：排行榜按地区或分数段拆成多个对象，匹配队列按地区和段位拆；写入先在上游聚合再批量提交，读取尽量走缓存。详见第 6 章和第 7 章。

**玩家分布在不同大洲。** 对象创建在离首个请求较近的数据中心，创建之后不会迁移（官方表示未来计划支持）。创建时可以给一个位置提示，但只对第一次调用生效，而且是尽力而为。所以一个由东南亚玩家创建的房间，南美玩家进来延迟会很高。出路是匹配时就按地区分组，让房间建在多数玩家附近。详见第 6 章。

这四条背后是同一个原则：**按实体拆分，不要留全局单点。** 一个玩家一个对象，一个房间一个对象，凡是"全服只有一个"的东西，从第一天起就按可以分片来设计。这个平台的扩展能力来自对象的数量，而不是单个对象的大小。

## 1.7 算一笔账

先看付费版的计价规则，这里只列和游戏相关的几项：

| 计费项 | 每月包含 | 超出部分 |
|---|---|---|
| 账号月费 | 5 美元起 | |
| Workers 请求 | 1,000 万次 | 每百万次 0.30 美元 |
| Workers CPU 时间 | 3,000 万毫秒 | 每百万毫秒 0.02 美元 |
| DO 请求 | 100 万次 | 每百万次 0.15 美元 |
| DO 时长 | 40 万 GB·秒 | 每百万 GB·秒 12.50 美元 |
| DO 存储写入 | 5,000 万行 | 每百万行 1.00 美元 |
| 流量（出口带宽） | 不收费 | |

有两条规则对游戏影响很大：

- WebSocket 建立连接算 1 次 DO 请求；之后**收到**的消息按 20 条折算 1 次请求，**发出**的消息不计费。
- DO 时长只在对象驻留内存时计算，休眠期间不计。

现在假设一个回合制房间游戏：日活 1 万，每人每天打 5 局，每局 4 人、10 分钟，每人每局向服务端发 60 条消息，另外每人每天调用 50 次普通接口，平均每次请求耗 5 毫秒 CPU。

| 项目 | 月用量 | 超出部分费用 |
|---|---|---|
| Workers 请求 | 接口 1,500 万 + 建连 150 万 = 1,650 万 | 650 万 × 0.30 = 1.95 美元 |
| Workers CPU | 1,650 万 × 5 毫秒 = 8,250 万毫秒 | 5,250 万 × 0.02 = 1.05 美元 |
| DO 请求 | 建连 150 万 + 消息 9,000 万 ÷ 20 = 600 万 | 500 万 × 0.15 = 0.75 美元 |
| DO 存储写入 | 每局约 50 行，共 1,875 万行 | 在包含额度内 |

这几项加上月费，一共不到 9 美元。真正的变量是 DO 时长。每天 12,500 个房间，每个房间存续 600 秒，时长按 128 MB 计：

- **房间全程驻留内存**：0.128 GB × 600 秒 × 12,500 间 × 30 天 = 2,880 万 GB·秒，扣除额度后约 **355 美元**。
- **房间九成时间在休眠**：288 万 GB·秒，扣除额度后约 **31 美元**。

也就是说，同一个游戏，月账单可能是 40 美元，也可能是 364 美元，差别只在房间对象有多少时间醒着。

这个例子里每个房间平均每 2.5 秒就收到一条消息，对象很可能根本没有机会休眠，实际账单会更靠近高的那一端。由此可以得出本书在设计上反复用到的一条原则：

> **消息节奏决定成本。** 能由客户端本地推演的就不要发给服务端；心跳交给运行时自动应答，不要唤醒对象；等待玩家操作的间隙要让对象能睡着。

对比之下，请求数和流量几乎不值得优化。特别是流量不收费这一点，和按出口带宽计费的传统云厂商差别很大，对资源下载量大的游戏尤其明显。

## 1.8 和 AI 结合更方便

现在做游戏很难绕开 AI：出海产品要做多语言聊天，房间里要有内容审核，人不够时要有像样的机器人，开发本身也越来越多地交给 AI 编程助手。这套技术栈在两个层面上都比较省事：一个是运行时调用平台自带的 AI 能力，一个是开发时用 vibe coding 的方式让 AI 帮你写。

### 运行时：调用模型只是多一个绑定

在传统架构里接入一个模型，要申请密钥、管理密钥、处理限流和重试，账单也在另一家。在 Workers 里，模型和数据库一样是一个绑定。配置文件加三行：

```jsonc
// wrangler.jsonc
{
  "ai": { "binding": "AI" }
}
```

代码里直接调用。下面是把一句房间聊天翻译成阿拉伯语的例子：

```ts
const result = await env.AI.run("@cf/meta/llama-3.1-8b-instruct", {
  prompt: `把下面这句游戏内聊天翻译成阿拉伯语，只输出译文：${text}`,
});
```

没有密钥要保管，费用记在同一张账单上。Workers AI 的模型目录按任务分类，和游戏相关的有文本生成、文本嵌入、文本分类、翻译、语音识别、语音合成和文生图。计费单位叫 Neuron，免费版和付费版每天都有 1 万个的免费额度，付费版超出部分每 1,000 个 0.011 美元。

围绕它还有三样配套的东西：

| 产品 | 作用 | 游戏里怎么用 |
|---|---|---|
| AI Gateway | 架在模型调用前面的一层代理，提供缓存、限流、重试、模型降级、日志和费用分析。后面可以接 Workers AI，也可以接 OpenAI、Anthropic、Google Gemini 等外部模型 | 给每个玩家限流防止刷爆账单；同一句话的翻译结果直接走缓存；主模型失败时自动换备用模型 |
| Agents SDK | 构建和托管 AI 智能体的工具包。每个智能体就是一个 Durable Object，自带状态、WebSocket 和定时调度 | 有记忆的客服、陪玩角色、运营助手 |
| Vectorize | 向量数据库，存放和检索嵌入向量 | 客服知识库检索、相似内容推荐 |

Agents SDK 这一行值得多说一句：智能体和房间用的是同一个底层模型。本书后面花大量篇幅讲的对象生命周期、休眠、存储和定时器，在写智能体时原样适用。学会用 DO 做房间，也就学会了在这个平台上做智能体的地基。

落到具体的游戏功能上，比较成熟的用法有这几类：

- **聊天翻译**：多语言玩家同处一个房间时，按接收方的语言翻译消息。
- **内容审核**：聊天、昵称、房间名的违规检测。
- **机器人的"人味"**：机器人的出牌和走子仍然用规则算，只让模型生成表情和台词。
- **客服与运营**：回答常见问题，生成各语言版本的活动文案。

也有几条需要守住的边界：

- **不要把模型放在对局的关键路径上。** 一次推理要几百毫秒到几秒，而且结果不确定。回合裁决、胜负判定必须是确定性的代码。
- **不要在房间对象里等模型返回。** 对象等待期间无法休眠，时长照常计费（见 1.7）。应该由 Worker 或队列的消费者去调用模型，把结果再送回房间。
- **机器人的决策不要交给模型。** 规则算法又快又便宜，行为还可以复现。第 6 章讲机器人补位时会展开。
- **每个玩家的用量要有上限。** 任何由玩家输入触发的模型调用都可能被刷，限流要在第一天就做好。
- **目录里是开源模型。** 对质量要求高的场景，通过 AI Gateway 调用外部的商业模型，仍然能享受缓存和限流。

需要说明的是，传统架构同样能调用这些模型接口，功能上并没有做不到的事。差别在于这里少了几样要自己搭的东西：密钥管理、调用代理、限流和用量统计。

### Vibe coding：把后端交给 AI 助手来写

Vibe coding 指的是用自然语言描述想要什么，由 AI 编程助手去写代码、跑代码、改代码，人主要负责提需求和验收。这种方式做前端页面已经很常见，做后端却经常卡住。卡住的原因通常不在代码本身，而在代码之外：控制台里点出来的资源、散落各处的环境配置、只有某个同事知道的部署步骤。助手看不到这些东西，也就没法对结果负责。

这套技术栈恰好把这些障碍降得很低：

- **一种语言。** 接口、房间逻辑、共享协议、构建脚本全是 TypeScript，助手不用在几种语言和框架之间切换。
- **基础设施写在配置文件里。** 用了哪些数据库、哪些对象、哪些队列，全部声明在 wrangler 的配置文件中。助手读一个文件就知道整个系统长什么样，加一个资源也只是改几行配置。
- **类型把配置和代码连在一起。** `wrangler types` 会根据配置生成绑定的类型定义。助手写错一个绑定名，编译阶段就报错，不用等到运行时。
- **本地能完整跑起来。** `wrangler dev` 在本机模拟 Workers、DO、D1 和队列。助手可以自己启动、自己发请求、自己看日志，不需要你把线上环境的权限交给它。
- **部署和回滚都是一条命令。** 没有需要口头传授的发布流程，发错了也能立刻退回上一个版本。
- **代码量小。** 没有连接池、服务发现、进程管理这些脚手架，剩下的几乎都是业务逻辑，容易完整放进助手的上下文里。
- **试错便宜。** 免费额度足够反复折腾，按请求计费意味着没有"忘了关的机器"。

合在一起的效果是：助手可以独立走完"改、跑、测、发"的整个循环，而不是写完一段代码就交还给你。

| 步骤 | 助手做的事 | 用到的命令 |
|---|---|---|
| 看懂项目 | 读配置文件和共享类型 | |
| 改 | 修改代码，需要新资源时改配置 | `wrangler types` |
| 跑 | 在本机启动整套后端 | `wrangler dev` |
| 测 | 运行单元测试和接口测试 | `vitest` |
| 发 | 部署到预览环境或线上 | `wrangler deploy` |
| 查 | 看线上实时日志 | `wrangler tail` |
| 退 | 出问题时回到上一个版本 | `wrangler rollback` |

一次典型的对话大概是这样：

> 在房间对象里加一个"准备"阶段：四个人都发送 ready 之后才开始第一回合，有人掉线超过 30 秒就把他换成机器人。规则写成 shared 目录下的纯函数并补上单元测试，本地跑通后告诉我改了哪些文件、对房间的休眠有没有影响。

助手会去读房间代码和协议类型，写规则和测试，启动本地环境验证，最后给你一份改动说明。你要做的是看说明、看测试、决定发不发。

#### 让 vibe coding 不翻车的几条约定

助手写得快，也错得快。下面这些约定是本书示例项目从第 2 章起就遵守的，它们的共同目的是让错误在到达玩家之前暴露出来。

- **游戏规则写成纯函数，并且配测试。** 输入是当前状态和一个操作，输出是新状态。这样的代码助手改完能自己验证，你验收时看测试用例就够了。它同时也是降低平台绑定的手段（见 1.5）。
- **前后端共享协议类型。** 消息结构只定义一次，任何一端改了字段，另一端在编译时就会报错。
- **在仓库里放一份写给助手的约定文件。** 写清目录分工、命名规则、禁止事项，以及"涉及限额和价格必须查官方文档"这类要求。助手每次开工都会读它，比每次口头叮嘱可靠。
- **线上凭据不交给助手。** 本地环境和预览环境足够它完成工作，正式发布交给自动化流水线，由人来触发。
- **涉及钱的代码必须人工审。** 支付核销、发奖、货币扣减这几处，错了就是真实的损失，而且往往不可逆。
- **让助手说明改动对成本的影响。** 一个不小心写出来的定时轮询，或者一个永远睡不着的对象，不会报错，只会出现在月底的账单上（见 1.7）。每次改动房间逻辑，都让它回答两个问题：消息频率变了没有，对象还能不能休眠。同时在账号里设好用量告警。
- **让助手查文档，不要让它凭记忆。** 平台的限额、价格和接口变化很快，模型记住的往往是旧版本。Cloudflare 的文档站提供了供模型读取的索引文件 [llms.txt](https://developers.cloudflare.com/llms.txt)，每个产品还有各自的版本。官方还提供了 MCP 服务，其中主服务（`https://mcp.cloudflare.com/mcp`）自带文档搜索工具，另有一个专门的文档服务（`https://docs.mcp.cloudflare.com/mcp`）。把它们接到助手上，它查到的就是当前的文档。本书凡是涉及数字和接口签名的地方，也是这样核实并标注日期的。

#### 它省掉的和省不掉的

Vibe coding 省掉的是写代码的时间，省不掉的是设计上的判断：状态该放在对象内存里还是落盘，哪些操作必须在一个事务里完成，哪些校验必须放在服务端，房间什么时候可以休眠。这些问题助手会给出一个能跑的答案，但未必是对的答案，而且错误常常要到流量上来之后才显现。

所以本书后面各章的重点不是逐行讲代码，而是讲清每个系统的设计取舍和容易踩的坑。代码可以交给助手写，取舍需要你自己懂，这样才能提出对的需求，也才看得出它交回来的东西有没有问题。

## 1.9 和传统方案怎么选

| 维度 | 云服务器 + 常驻进程 | Workers + Durable Objects |
|---|---|---|
| 起步成本 | 机器、数据库、缓存都要先开起来 | 免费版可以跑通原型 |
| 流量波峰 | 提前扩容，或者配置自动伸缩 | 平台自动处理 |
| 闲时成本 | 机器照常计费 | 接近于零 |
| 运维 | 系统补丁、监控、容量规划都要自己做 | 基本没有 |
| 实时性上限 | 可以用 UDP，可以做帧同步 | 只有 WebSocket，适合低频消息 |
| 单机算力 | 按需选配 | 128 MB 内存，CPU 时间有上限 |
| 调试与工具 | 生态成熟，想装什么装什么 | 受运行时限制，部分 Node.js 库不能用 |
| 接入 AI | 自己管密钥、代理、限流和用量统计 | 模型是一个绑定，配套有网关和智能体工具包 |
| Vibe coding | 资源和部署步骤常在代码之外，助手难以独立完成 | 资源写在配置文件里，本地可完整运行，助手能走完改、跑、测、发的循环 |
| 迁移成本 | 低，各家云大同小异 | 高，DO 没有等价替代品 |

一个简单的判断方法：如果你的游戏每个玩家每秒向服务端发的消息不到一条，并且团队里没有人想半夜起来处理机器故障，这套方案值得认真考虑。反过来，如果玩法的核心是毫秒级的操作对抗，直接选传统方案。

两者也可以混用。接口、账号、支付、排行榜放在 Cloudflare 上，只把实时战斗放在专门的游戏服务器里，是很常见的折中。

## 1.10 本书的路线

后面的章节会围绕一个四人回合制棋盘游戏的后端展开，代码在仓库的 `examples/` 目录下。选这个类型，是因为它能把房间、匹配、排行榜、支付这几条线都自然地串起来，又正好落在这套技术栈最擅长的区间里。

接下来两章是准备工作：第 2 章搭工程，第 3 章讲几种存储各自该放什么数据。从第 4 章开始逐个实现系统。

## 本章小结

- Cloudflare 做游戏后端的核心是 Durable Objects：一个房间一个对象，寻址、并发、存储都由平台解决。
- 适合回合制、房间制、异步对战和休闲游戏；不适合帧同步、重计算和单场景大量玩家。
- 做大以后会碰到 D1 单库 10 GB、没有现成的全服广播、单对象吞吐上限、对象不迁移这四个天花板。出路都是按实体拆分，不留全局单点。
- 账单的大头是 DO 时长，取决于对象有多少时间驻留内存。控制消息节奏、让对象能休眠，比优化请求数重要得多。
- 运行时调用模型只是多一个绑定。但模型不能进对局的关键路径，也不要让房间对象等它返回。
- 这套栈适合 vibe coding：一种语言、资源写在配置里、本地可完整运行，助手能独立走完改、跑、测、发的循环。它省掉的是写代码的时间，省不掉设计上的判断。
- 平台绑定是真实的代价，要靠代码分层来降低。

## 数据核实说明

本章的限额和价格取自 Cloudflare 官方文档，核实日期为 2026-11-20（1.6 节和 1.8 节的 AI 相关内容为 2026-11-24），完整数字见[附录 A](../appendix/a-cloudflare-limits.md)。这些数字会变，做预算前请以官方文档为准。

以下两点来自作者的经验，本轮没有在文档中逐字核对，引用前请自行确认：

- DO 时长固定按 128 MB 计费，与实际内存占用无关。
- 对象空闲多久后进入休眠。文档只说"一小段时间"。

另有两点文档没有写明：AI Gateway 标注为所有套餐可用，但没有说明各项功能是否免费；Vectorize 在免费版是否可用，产品首页没有说明。1.6 节里的应对方案（频道对象、排行榜分片、按地区匹配等）是作者给出的设计方向，文档只提供了其中的限额和机制；单个对象能挂多少连接，文档只说"数千"，没有给出确切上限。1.8 节里关于 vibe coding 的理由和约定是作者的判断，不是来自文档；其中的 `wrangler dev`、`wrangler types` 和 `vitest` 已在第 2 章的示例项目里实际运行过，`wrangler deploy`、`wrangler tail`、`wrangler rollback` 需要账号，只核对了文档。1.3 节的最小房间代码与第 2 章示例项目的写法一致，后者已通过测试。
