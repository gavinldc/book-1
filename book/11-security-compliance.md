# 第 11 章　安全与合规

> 状态：初稿　｜　文档核实与实际运行日期：2026-11-25

安全不是这一章才开始做的事。前面每一章都在做：服务端生成骰子点数，价格只从服务端的商品表里取，回调先验签名再读内容，发奖按编号去重。这一章做两件事：把散落在各章的防护串起来看一遍，补上其中还缺的几块；然后讲数据和合规，也就是玩家对自己的数据有哪些权利，以及这些数据放在哪里。

合规的部分先说明一句：这本书讲的是技术上要准备什么，不是法律意见。各个地区的规定不同，而且在变，上线前要找懂当地法规的人确认。

这一章的代码在 [examples/server/src/security/](../examples/server/src/security/)。

## 11.1 谁在攻击什么

先把对手分清楚。游戏后端面对的攻击大致是这几类，动机不同，防的办法也不同：

| 对手 | 想要什么 | 典型做法 | 主要的防线 |
|---|---|---|---|
| 刷子 | 游戏里能变现的东西 | 批量注册小号，刷邀请、广告、新手奖励 | 抬高注册成本，奖励设门槛和上限（11.3、11.6 节） |
| 作弊的玩家 | 赢 | 改客户端，伪造消息，用脚本代打 | 服务端权威，重放校验，统计信号（11.5 节） |
| 盗号的 | 别人的账号 | 偷令牌，撞凭证 | 短期令牌，凭证轮换（第 4 章） |
| 捣乱的 | 让你的服务不可用，或者让你的账单变大 | 大量请求，专挑贵的接口 | 限流（11.2 节） |
| 内部的失误 | 没有恶意 | 手滑多发了奖励，配错了价格 | 上限、校验、操作记录（第 9 章） |

对付所有这些，原则只有一条：**让攻击的成本高于它的收益。** 没有攻不破的系统，但刷一个奖励要花一分钟、而奖励只值一分钱的系统，没有人会去刷。所以防护有两个方向可以用力：抬高成本（限流、人机验证、门槛），或者降低收益（上限、只发不能变现的东西）。

最后一行容易被忽略。实际造成损失最多的往往不是攻击，而是自己人的失误。第 9 章的配置校验、附件上限和操作记录，防的就是这个。

## 11.2 限流：三层

第 4 章给登录接口加了限流，当时说其余的接口留到这一章。完整的限流有三层，各自挡不同的东西。

### 第一层：平台的防火墙

请求到达 Worker 之前，先经过 Cloudflare 的网络。这一层有几样东西不用写代码：

- **DDoS 防护**是默认开着的，大流量的攻击在这里就被吸收了，到不了你的代码。
- **限流规则**在控制台里配置：某个路径、同一个来源地址、在多长时间内超过多少次请求，就拦截一段时间。
- **Bot Fight Mode** 是免费的机器人识别，打开后会对明显是自动化工具的请求发起质询。

限流规则在各套餐下的差别不小，免费版只能建 1 条规则，计数周期固定是 10 秒，只能按来源地址计数；Pro 是 2 条，Business 是 5 条。所以这一层适合放一两条很粗的规则，比如"任何一个地址 10 秒内超过 200 个请求就拦 10 秒"，用来挡住最粗暴的那一类流量。被它拦下的请求不会调用 Worker，也就不产生费用。

这一层有两个局限：

- **它不知道玩家是谁。** 它只能按地址、路径这些请求本身的特征来计数。很多出海市场的移动网络是大量用户共用一个出口地址的（第 4 章提过），按地址限得太紧会误伤正常玩家。
- **机器人识别可能误伤。** 游戏的客户端和第三方平台的回调，在机器人识别看来也是"程序发出的请求"。官方文档说明，要给特定的流量开例外（比如自己的 API 客户端），需要用付费的 Super Bot Fight Mode。打开之前要在预发环境确认登录、对局和支付回调都不受影响。

### 第二层：Worker 里按玩家限

进到 Worker 之后，就知道请求是哪个玩家发的了。这一层用第 4 章的限流绑定，按玩家计数：

```ts
const TIERS: Record<Tier, { limiter: "SENSITIVE_LIMITER" | "API_LIMITER" | "WEBHOOK_LIMITER"; by: "player" | "ip" }> = {
  // 能让服务端替你做一件有成本的事的接口：下单、开房、发申请、按短码查房间。
  sensitive: { limiter: "SENSITIVE_LIMITER", by: "player" },
  // 其余会改动数据的接口。
  api: { limiter: "API_LIMITER", by: "player" },
  // 第三方平台的回调。没有玩家身份，按来源地址计数。
  webhook: { limiter: "WEBHOOK_LIMITER", by: "ip" },
};
```

接口按用途分成几档，每一档一个限流器：

| 档 | 包括 | 按什么计数 | 每分钟 |
|---|---|---|---|
| 登录 | `/auth/*`（第 4 章） | 来源地址 | 20 |
| 敏感 | 下单、开房、镜像对战、好友申请、填邀请人、按短码查房间、导出和删除账号 | 玩家 | 30 |
| 普通 | 其余会改动数据的接口，以及排队和进房的连接 | 玩家 | 120 |
| 回调 | `/webhooks/*` | 来源地址 | 120 |
| 不限 | 普通的读取、管理接口 | | |

"敏感"的标准是：**这个接口能让服务端替调用者做一件有成本的事。** 下单要调用支付平台，开房要创建对象，好友申请会写进别人的对象，短码查询可以被用来枚举。前面几章里说"上线前要限流"的接口都在这一档。

限流放在入口，在所有业务处理之前：

```ts
export async function enforceRateLimit(request: Request, env: Env, pathname: string): Promise<Response | null> {
  const tier = tierOf(request.method, pathname);
  if (!tier) return null;
  const rule = TIERS[tier];

  const ip = request.headers.get("CF-Connecting-IP") ?? "unknown";
  let key = `ip:${ip}`;
  if (rule.by === "player") {
    // 按玩家计数：换网络、换地址都绕不过去。没有合法令牌的请求退回到按地址计数。
    // WebSocket 的令牌在子协议里，不在 Authorization 请求头里，要用对应的办法取。
    const playerId =
      request.headers.get("Upgrade") === "websocket"
        ? await authenticateWebSocket(request, env)
        : ((await authenticate(request, env))?.sub ?? null);
    if (playerId) key = `player:${playerId}`;
  }

  const { success } = await env[rule.limiter].limit({ key: `${tier}:${key}` });
  if (success) return null;
  log.warn("rate_limited", { tier, key, path: pathname });
  metric(env, "rate_limited", [tier], [1]);
  const response = fail(429, "too_many_requests");
  response.headers.set("Retry-After", "60");
  return response;
}
```

几点说明：

- **按玩家计数比按地址计数准。** 一个玩家换了网络，计数跟着他走；一百个玩家共用一个出口地址，互不影响。没有令牌或者令牌无效的请求退回到按地址计数，它们本来也过不了后面的登录检查。
- **取身份要按连接的类型来。** 普通请求的令牌在请求头里，WebSocket 的在子协议里（4.8 节）。这段代码的第一版只认请求头，结果排队和进房的连接全部退回到了按地址计数。这个缺陷是第 12 章压测时才发现的，12.1 节有完整的经过。
- **被限流的请求要告诉客户端什么时候再试。** 应答里带 `Retry-After`。客户端收到 429 应该等待，而不是立刻重试；立刻重试只会让它一直被限。
- **限流的命中要记下来。** 一条 `warn` 日志加一个指标。正常情况下这个指标接近零，它突然变大，要么是有人在攻击，要么是客户端写出了一个会疯狂重试的缺陷。两种都需要知道。
- **回调按地址计数的用处有限。** 支付平台从很多地址发回调，攻击者也可以换地址。这一档挡的是最简单的洪水式请求；真正的保护是第 8 章的签名校验，它不依赖限流。

这里有一个开销：按玩家限流要先校验令牌，后面的业务处理还会再校验一次。校验是一次 HMAC 计算，在微秒级，换来的是把限流放在任何业务逻辑之前。

第 4 章说过限流绑定的特点：计数是近似的，每个地点各算各的。所以它不能用来实现"每个玩家每天只能领 10 次"这种必须精确的规则。那是第三层的事。

### 第三层：对象里的业务上限

精确的、和业务有关的上限，在数据所在的地方执行。前面几章已经做了一批：

| 上限 | 在哪 | 章 |
|---|---|---|
| 每条连接 10 秒最多 20 条消息 | 房间对象 | 5 |
| 好友最多 50 个，未处理的申请最多 50 条 | 玩家对象 | 7 |
| 邀请奖励每人最多领 20 次 | 玩家对象 | 7 |
| 一小时内最多 20 个未付款的订单 | 玩家对象 | 8 |
| 广告奖励每天最多 10 次 | 玩家对象 | 8 |
| 邮箱最多 100 封，单封附件有上限 | 玩家对象、管理接口 | 9 |

这一层是精确的，因为一个玩家只有一个对象，计数和判断在同一个事务里（第 8 章）。它也是最后一道防线：前两层挡的是"太多"，这一层保证的是"即使都通过了，最多也只能拿走这么多"。

三层合起来看：

| | 挡什么 | 精确吗 | 被挡的请求花钱吗 |
|---|---|---|---|
| 防火墙 | 大流量、明显的自动化 | 粗 | 不花 |
| Worker 限流 | 单个玩家或地址的高频调用 | 近似 | 花一次 Worker 调用 |
| 对象里的上限 | 业务上不允许的累计量 | 精确 | 花一次对象调用 |

越靠前的层越便宜、越粗，越靠后的层越精确、越贵。每一层只做自己擅长的事。

## 11.3 批量注册

### 所有的刷，都从注册开始

第 7 章的邀请奖励、第 8 章的广告奖励，以及任何"新玩家有礼"的设计，被刷的方式都一样：注册一大批账号。而创建一个游客账号，就是调用一次 `POST /auth/guest`，不需要任何东西。

第 4 章给这个接口加了按地址的限流，一个地址每分钟 20 次。对一个用代理池的刷子来说，这几乎没有阻碍。真正需要的是让每一次注册都要付出一点代价。

### 人机验证

Cloudflare 的 Turnstile 是一个人机验证组件。客户端在页面上嵌入它，它在后台判断当前是不是一个真实的浏览器环境（大多数情况下用户什么都不用点），然后给出一个令牌。客户端把令牌随注册请求一起发给服务端。

官方文档里有一句话要先记住：**页面上的组件本身不提供任何保护。** 令牌必须拿到服务端，向 Cloudflare 核实之后才算数。只在前端放一个组件、后端不核实，等于什么都没做。

```ts
export async function verifyTurnstile(env: Env, token: unknown, ip: string): Promise<boolean> {
  // 本地开发和测试时可以关掉。线上的配置里要打开。
  if ((env.TURNSTILE_ENFORCE as string) !== "true") return true;
  if (typeof token !== "string" || token === "" || token.length > MAX_TOKEN_LENGTH) return false;

  try {
    const response = await fetch(SITEVERIFY, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({
        secret: env.TURNSTILE_SECRET,
        response: token,
        remoteip: ip,
        // 带上它之后，这次核实因为超时而重试时不会被当成"令牌被用了第二次"。
        idempotency_key: crypto.randomUUID(),
      }),
    });
    const result = (await response.json()) as { success: boolean; "error-codes"?: string[] };
    if (!result.success) log.info("turnstile_rejected", { codes: result["error-codes"] ?? [] });
    return result.success === true;
  } catch (error) {
    // 核实不了就当作没通过。放行的话，验证服务一出故障，注册接口就对机器人敞开了。
    log.error("turnstile_unavailable", { error });
    return false;
  }
}
```

关于令牌要知道三点：有效期 5 分钟；只能用一次，重复提交会被拒绝；最长 2,048 个字符。

**核实不了时拒绝。** 验证服务访问不了的时候，有两个选择：放行，或者拒绝。放行意味着只要让核实请求失败，验证就形同虚设；拒绝意味着验证服务故障期间新玩家注册不了。示例选了拒绝，并打一条 `error` 日志。对一个注册接口来说，短时间内注册不了，比对机器人敞开要好。

### 只在创建新账号时要求

```ts
// 创建新账号是整个系统里成本最低的"拿到一个身份"的办法，所以只在这里要求人机验证。
// 老玩家带着凭证回来不需要。
if (provided === undefined && !(await verifyTurnstile(env, body.turnstileToken, ip))) {
  return fail(403, "verification_required");
}
```

验证只加在"没带凭证的游客登录"上，也就是创建新账号的那一次。老玩家带着凭证回来不需要，每次打开游戏都验证一遍会很烦人。

Telegram 登录也不需要。它的 `initData` 是平台签过名的（4.5 节），一个 Telegram 账号背后是一个手机号，注册成本本来就比游客账号高得多。这也是第 7 章那条建议的由来：**涉及奖励的功能，尽量只对绑定了平台身份的账号开放。** 人机验证抬高的是游客账号的成本，平台身份则是把成本转嫁给了平台的注册流程。

### 这个开关的默认值

示例里人机验证由一个配置变量 `TURNSTILE_ENFORCE` 控制，默认是 `"false"`。这和第 9 章说的"安全相关的开关，缺失时应该拒绝而不是放行"是矛盾的，这里要说清楚为什么这样选，以及代价是什么。

原因是本地开发和测试：每次新建游客账号都要真的去完成一次验证，开发时很不方便。Turnstile 提供了测试用的密钥（对任何令牌都返回通过），但那仍然需要访问外部服务。

代价是：**上线时忘了把它设成 `"true"`，注册接口就没有保护，而且不会有任何报错。** 所以它必须出现在上线清单里（第 12 章），并且值得加一条监控规则：新账号的创建速度超过正常范围时告警。如果你的团队不需要在本地频繁创建账号，更好的做法是把这个开关去掉，永远校验，本地用测试密钥。

## 11.4 不存在的 ID

第 7 章留下一个没堵死的口子。对象是按名字自动创建的：访问一个从没用过的玩家 ID，也会得到一个对象，它的构造函数会建表，于是留下了数据。当时好友申请的接口用格式校验加一次对象调用来判断"对方存不存在"，而那次对象调用本身就已经把对象建出来了。

现在用一张 D1 里的名录来回答这个问题：

```sql
CREATE TABLE player (
  player_id TEXT PRIMARY KEY,
  created_at INTEGER NOT NULL
);
```

```ts
export async function registerPlayer(db: D1Database, playerId: string, now: number): Promise<void> {
  // 每次登录都执行一次。已经在名录里的玩家不会被改动，早于名录存在的老玩家会在下次登录时补上。
  await db.prepare("INSERT OR IGNORE INTO player (player_id, created_at) VALUES (?, ?)").bind(playerId, now).run();
}
```

名录在登录时由入口直接写入，而不是像排行榜那样经过发件箱和队列。原因是时效：刚注册的玩家立刻就可能被朋友加好友，名录晚一两秒，那次申请就会被当成"玩家不存在"。写入用的是"不存在才插入"，每次登录都执行一次，所以它能自己补全：这张表上线之前就注册的老玩家，下次登录时会被补进去。

凡是玩家 ID 来自别处的地方，现在都先查名录，查到了才去访问对象：

```ts
// 先在名录里确认对方是一个真实存在的玩家。查的是 D1，不会碰到那个 ID 对应的对象。
if (target !== me && !(await findPlayer(env.DB, target))) return fail(404, "not_found");
```

这样的地方有四处：好友申请、填邀请人、广告平台的回调、管理后台。测试里验证了效果：用一个格式正确但编出来的 ID 去发好友申请，返回 404，并且玩家对象的总数没有增加。

```ts
const before = (await listDurableObjectIds(env.PLAYER)).length;
const fake = `p_${"ab".repeat(12)}`;
expect((await post("/friends/request", { playerId: fake }, token)).status).toBe(404);
expect((await listDurableObjectIds(env.PLAYER)).length).toBe(before);
```

这是这本书里第三次出现同一个教训：没开过的房间不存在（第 6 章），名字由客户端提供的对象要想清楚不存在时会怎样（第 7 章），现在是它的解法。**对象可以按名字凭空创建，这是它方便的地方，也是需要守住的地方。** 凡是名字不由服务端自己生成的，访问之前都要有一个不依赖对象本身的办法确认它该不该存在。

## 11.5 反作弊

### 第一层：让作弊在结构上做不到

反作弊最有效的手段不是检测，而是让客户端没有东西可以作弊。前面几章做的事情，放在一起是这样的：

| 客户端能说的 | 客户端不能决定的 | 章 |
|---|---|---|
| "我要掷骰子" | 掷出几点 | 2、5 |
| "我要买这个商品" | 价格是多少，买到什么 | 8 |
| "我看完广告了" | 有没有真的看，奖励多少 | 8 |
| "我是这个玩家" | 身份，只认签过名的令牌 | 4 |
| "现在轮到我" | 回合和时间，由房间判断 | 5 |
| "我的分数是这么多" | 分数，由服务端从玩家对象读 | 6 |
| "我在实验的这一组" | 分组，由服务端算 | 9 |

每一行都是同一句话：**客户端只能表达意图，结果由服务端算。** 改客户端、抓包重放、伪造消息，对这样的系统都没有用，因为客户端手里没有任何一个能决定结果的值。

所以反作弊的第一个问题永远是：这个作弊之所以可能，是不是因为服务端信了客户端的某个值？如果是，改掉它，比任何检测都管用。

这一层防不住的有三类，后面的手段是为它们准备的：

- **用脚本代打。** 脚本发出的每一个操作都是合法的，只是不是人在操作。
- **串通。** 两个人约好，一个故意输给另一个。
- **信息泄露。** 有隐藏信息的游戏（手牌、战争迷雾），如果服务端把不该给的信息发给了客户端，改过的客户端就能看到。这要靠 5.3 节按玩家过滤视图来防，属于第一层没做好。

### 第二层：对局可以重放

第 6 章把每一局的操作都记了下来。规则是确定性的，所以拿着这份记录，任何时候都能把一局从头算一遍，看结果对不对。

要做到这一点，记录还缺两样东西，这一章补上了：

```ts
// 开局的那一刻记下座位顺序。重放一局时，谁先谁后要和当时一样。
if (before.phase === "waiting" && after.phase === "playing") {
  writes[SEATS_KEY] = after.players.map((p) => p.id);
}
// 对局中的离开（包括被踢）也是会改变结果的一步，一样要记。
const left = action.type === "leave" && before.phase === "playing";
```

一是开局时的座位顺序，二是对局中的离开。原来的日志只记了掷骰子和超时，但有人中途离开同样会改变结果（剩下一个人时直接判胜）。**凡是会改变结果的操作，都要在日志里。** 检验的办法就是重放：重放不出当时的结果，说明日志缺了东西。

重放的函数很短：

```ts
export function replayRecord(record: MatchRecord): ReplayResult {
  if (!record.seats) return { ok: false, reason: "no_seats", winner: null };

  let state: RoomState = initialState();
  // ……每个座位依次 join、ready，进入对局……

  for (const [index, entry] of record.log.entries()) {
    // 日志里的三种记录：正数是掷出的点数，0 是超时，-1 是离开。
    const action: Action =
      entry.dice > 0
        ? { type: "roll", playerId: entry.playerId, dice: entry.dice }
        : entry.dice === 0
          ? { type: "timeout", playerId: entry.playerId }
          : { type: "leave", playerId: entry.playerId };
    const error = step(action);
    if (error) return { ok: false, reason: `step ${index}:${error}`, winner: null };
  }

  if (phase() !== "finished") return { ok: false, reason: "not_finished", winner: null };
  if (state.winner !== record.winner) return { ok: false, reason: "winner_mismatch", winner: state.winner };
  return { ok: true, winner: state.winner };
}
```

它用的就是 `shared` 里的那套规则，和房间对象运行时用的是同一份代码。

重放有三个用处：

- **处理申诉。** 玩家说"这一局判得不对"，管理后台有一个接口把这一局重放一遍，给出当时记录的结果和重放的结果。两者一致，就按日志逐步向玩家解释；不一致，是一个需要查的缺陷。
- **验证记录没被改过。** 记录里的赢家、点数、顺序，任何一处被改动，重放都对不上。
- **验证规则的改动。** 规则的代码改了之后，拿一批历史记录重放一遍。如果本来对得上的现在对不上了，说明这次改动改变了已有对局的结果，这通常不是你想要的。这正是 6.11 节说"录像要带上规则版本"的原因。

要说明它的边界：这个示例游戏里，所有会影响结果的值（骰子）都是服务端生成的，所以重放验证的是**服务端自己的记录是否自洽**，它查不出"玩家作弊"，因为玩家没有作弊的余地。在有决策的游戏里，重放的价值更大：可以用它离线检查每一步决策在当时是否合法，以及用更重的算法去判断一连串决策像不像人做出来的。

### 第三层：统计信号

脚本和串通在单局里看不出来，要从大量对局的统计里找。对局记录和排行榜都在 D1 里，这类分析就是一些查询。几个常用的信号：

| 信号 | 说明什么 | 怎么查 |
|---|---|---|
| 胜率长期明显高于同分段 | 可能有外部辅助，或者在刷弱对手 | 对局记录按玩家统计胜率，和分数接近的人比 |
| 对局数异常多，全天没有间断 | 脚本代打 | 按玩家、按小时统计对局数 |
| 总是和同一批人打，并且总是赢 | 串通 | 对局记录里统计对手的集中程度 |
| 大量很短的对局，一方很快离开 | 刷场次，或者故意送分 | 日志很短、以离开结束的对局 |
| 操作的间隔过于均匀 | 脚本 | 需要记录每一步的时间，示例没有记 |

这些查询跑在定时任务里（第 9 章），结果写进一张待审核的表，或者打成日志由监控规则来盯（第 10 章）。

对统计信号要有两点清醒的认识。

**它给出的是嫌疑，不是结论。** 胜率高可能只是打得好。任何一个信号单独拿出来都不足以封号。合理的流程是：信号把玩家标记出来，人来看他的对局记录，确认之后才处置（第 9 章的封禁接口，要填原因）。自动封号一旦误伤，损失的是真实的玩家和口碑。

**设计比检测更省事。** 示例里好友房不计分（第 6 章），所以两个人约好在好友房里互相送分没有意义；镜像对战的录像只取排位赛的（6.11 节），所以没法自己造一段很弱的录像给自己打。这些都是在设计上让串通没有收益，比事后去查串通容易得多。

## 11.6 邀请刷量

第 7 章给邀请奖励定了规则：只在注册后一段时间内可填，邀请人必须注册得更早，被邀请人赢两局计分的对局才发奖，每人最多领 20 次。那些规则把损失框住了。识别是谁在刷，靠的是 D1 里那张邀请关系表。

```sql
-- 邀请了很多人，但拿到奖励的比例很低：拉来的账号大多没有真的在玩。
SELECT inviter, COUNT(*) AS invited, SUM(rewarded_at IS NOT NULL) AS rewarded
FROM invite
WHERE created_at > ?
GROUP BY inviter
HAVING invited >= 10
ORDER BY invited DESC
```

可以看的信号：

- **被邀请的账号发奖之后就不再出现。** 刚好满足门槛就停止活动，是刷子的典型特征。真实的玩家达到门槛之后还会继续玩。
- **被邀请的账号注册时间很集中。** 一个小时内来了二十个。
- **被邀请的账号都是游客，没有绑定任何平台身份。**
- **达到门槛的方式很一致。** 都是恰好两局胜利，对手都是机器人或录像。

处置上有两个比封号更好用的手段，第 7 章提过：

- **延迟发放。** 奖励先记为待发放，过几天再到账。这几天里可以观察被邀请的账号是否还在活动。刷子要的是快，延迟本身就降低了吸引力。
- **追回。** 确认是刷的之后，用一笔反向的流水把奖励扣回来（第 8 章的做法），同时把他的邀请资格关掉。

以及这一章新加的两道防线：注册要过人机验证（11.3 节），涉及奖励的功能只对绑定了平台身份的账号开放。它们抬高的是每一个小号的成本，和上限、门槛是互补的。

## 11.7 管理后台的权限

第 9 章的管理后台用 Cloudflare Access 做登录，能进来的人什么都能做。上线之后要把权限分开。

**按职责分角色。** 至少三档：

| 角色 | 能做什么 | 谁 |
|---|---|---|
| 只读 | 查看玩家、流水、订单、对局 | 客服 |
| 操作 | 封禁、解封、发邮件、核实订单 | 资深客服、运营 |
| 配置 | 发布和回滚全服配置、发全服邮件 | 少数几个人 |

Access 可以按身份系统里的用户组来放行，签发的令牌里也可以带上用户所属的组。做法是给不同的路径配不同的 Access 策略，同时在 Worker 里按令牌里的组再检查一次。和第 9 章一样，两边都要做：Access 挡在外面，Worker 里的检查保证不论从哪个入口进来都一样。

**大额的操作要两个人。** 第 9 章给单封邮件的附件设了上限。超过上限的补偿不应该是"把上限调高"，而是一个需要第二个人批准的流程：一个人提交，另一个人确认之后才执行。

**操作记录要有人看。** 记下来但从来不看的记录，只在出事之后有用。定期抽查（比如每周看一遍所有的封禁和超过一定金额的邮件），以及对异常的模式设监控规则：某个管理员一小时内发了几十封带附件的邮件，值得一条告警。

示例项目没有实现角色划分。

## 11.8 玩家对自己数据的权利

很多地区的法规（欧盟的 GDPR 是最常被提到的）给了用户两项基本的权利：拿到自己的数据，以及要求删除。不论你的玩家在不在这些地区，这两个功能都值得做，应用商店的审核也越来越多地要求应用内能删除账号。

### 导出

```ts
exportData(now: number) {
  const sql = this.ctx.storage.sql;
  return {
    playerId: this.id,
    profile: this.readProfile(),
    wallet: this.getWallet(),
    // 只给出绑定了哪些平台。身份对象的名字里有凭证的哈希，不属于要导出的内容。
    identities: Object.keys(this.getAccount().identities),
    friends: this.listFriends(),
    mail: this.listMail(now),
    ledger: this.getLedger(200),
    orders: sql
      .exec("SELECT order_id, product_id, provider, amount, currency, status, created_at FROM purchase")
      .toArray(),
  };
}
```

"一个玩家一个对象"在这里又一次带来了方便：一个玩家的数据几乎都在他自己的对象里，导出就是把它读出来。在传统的架构里，这件事要去十几张表里按用户 ID 各查一遍，还经常漏掉某一张。

导出的内容里没有身份对象的名字。游客身份的名字是凭证的哈希，它是用来登录的东西，不是"关于这个玩家的数据"。

### 删除

删除比导出麻烦，因为玩家的痕迹不只在他自己的对象里：

| 在哪 | 是什么 | 怎么处理 |
|---|---|---|
| 身份对象 | 这个平台账号属于哪个玩家 | 解除归属 |
| 好友的玩家对象 | 好友列表里有他 | 通知对方去掉 |
| D1 | 排行榜、录像、邀请关系、名录 | 删除 |
| D1 | 支付记录 | 保留 |
| 自己的玩家对象 | 其余所有的 | 清空 |

这是一个要跨好几个对象和 D1 的多步操作，任何一步都可能失败。做法和这本书里所有跨对象的操作一样：先在自己这边把事情定下来，再通过发件箱和队列一步步去做，每一步都能重来。

第一步在玩家对象里，同步完成：

```ts
async requestErase(now: number): Promise<void> {
  const sql = this.ctx.storage.sql;
  const identities = Object.values(this.getAccount().identities);
  this.ctx.storage.transactionSync(() => {
    sql.exec("UPDATE profile SET banned = 1 WHERE id = 1");
    sql.exec("DELETE FROM session");
    // 告诉每一个好友：把我从你的列表里去掉。
    for (const row of sql.exec("SELECT player_id FROM friend").toArray()) {
      this.emit({ type: "friend_remove", from: this.id, to: String(row.player_id), at: now });
    }
    sql.exec("DELETE FROM friend");
    this.emit({ type: "erase", playerId: this.id, identities, at: now });
  });
  await this.flush();
}
```

这一步之后，玩家已经登录不了了，接口返回 202，表示"已受理，正在处理"。真正的清除在队列的消费者里：

```ts
export async function eraseEverywhere(env: Env, playerId: string, identities: string[]): Promise<void> {
  // 一、解除身份的归属。之后同一个平台账号再登录，得到的是一个全新的玩家。
  for (const name of identities) {
    await env.IDENTITY.getByName(name).release(playerId);
  }

  // 二、D1 里按玩家存的各份副本。
  await env.DB.batch([
    env.DB.prepare("DELETE FROM leaderboard WHERE player_id = ?").bind(playerId),
    env.DB.prepare("DELETE FROM replay WHERE player_id = ?").bind(playerId),
    env.DB.prepare("DELETE FROM invite WHERE invitee = ?").bind(playerId),
    // 他邀请过的人还在，只是不再指向他。
    env.DB.prepare("UPDATE invite SET inviter = 'deleted' WHERE inviter = ?").bind(playerId),
    env.DB.prepare("DELETE FROM player WHERE player_id = ?").bind(playerId),
    // 支付记录不删：财务和税务上有保存期限的要求。它里面只有一个已经不对应任何人的玩家 ID。
  ]);

  // 三、最后清空玩家对象。放在最后，是因为前两步失败重来时还需要它存在。
  await env.PLAYER.getByName(playerId).finishErase();
}
```

三个步骤的顺序是有讲究的：

- **每一步都可以重复执行。** 解除一个已经解除的身份、删除已经不存在的行、清空一个空的对象，都不会出错。所以中途失败时整条通知被重新投递，从头再来一遍即可。
- **清空自己放在最后。** 这条通知是从玩家对象的发件箱里发出来的，要清除的身份列表也在通知里。如果先清空了对象，后面的步骤失败后重来时，就没有地方再找回这些信息了。
- **身份被解除后可以重新认领。** 玩家删除账号之后，用同一个 Telegram 账号再登录，得到的是一个全新的、空的玩家。这是删除应有的含义。

### 删不掉的，和不在这里的

"删除我的数据"不等于系统里一个字节都不剩。几处要事先想清楚，并且写进隐私政策：

- **支付记录要保留。** 财务和税务对交易记录有保存期限的要求，这通常是法规允许的例外。保留下来的记录里只有玩家 ID，而这个 ID 已经不对应任何人了。
- **对局记录里还有他的 ID。** 别人的对局记录里，对手一栏是他。这些记录 30 天后自动清理（第 9 章）。
- **日志。** 日志里有玩家 ID，7 天后过期（第 10 章）。这也是日志里不要记录超出需要的个人信息的原因之一。
- **备份。** D1 有 30 天的时间点恢复。删除的数据在这段时间内理论上还能恢复出来，过期后才彻底消失。
- **第三方。** 埋点在 Firebase 上（第 10 章），那里的数据要通过分析平台自己提供的用户数据删除功能去删。支付平台那边的交易记录归支付平台管。

实际运营中，删除通常还会加一个冷静期：玩家提出删除后先停用账号，过一段时间（比如 14 天）再真正执行，期间可以撤销。误点和被盗号后的恶意删除都不少见。示例是立刻执行的。

## 11.9 数据放在哪里

有些法规要求特定地区的用户数据存放在该地区之内。这套技术栈的默认行为是数据跟着访问走：对象创建在离第一个访问者较近的地方，D1 的主库创建在离你创建它时较近的地方。要满足数据驻留的要求，得明确指定。

平台为几种存储提供了**辖区**的设置，目前支持欧盟（`eu`）和 FedRAMP：

| 存储 | 怎么指定 | 限制 |
|---|---|---|
| Durable Object | 代码里用 `env.PLAYER.jurisdiction("eu")` 得到一个限定在欧盟的命名空间，在它上面取对象 | 同一个名字在不同辖区里是不同的对象 |
| D1 | 创建数据库时加 `--jurisdiction=eu` | 只能在创建时指定，之后不能加也不能改 |
| R2 | 创建存储桶时指定 | 同上 |

有三点会直接影响架构：

- **辖区只管数据存在哪、对象在哪运行，不管 Worker 在哪运行。** 官方文档写明，Worker 仍然可以从世界任何地方访问这些受限的资源。如果要求连处理都在境内，需要另外的产品（Regional Services）。
- **对象的 ID 会出现在辖区之外。** 文档说明，出于计费和调试的需要，对象的 ID 会被记录在指定的辖区之外。所以玩家 ID 本身不要包含个人信息，示例里它是服务端生成的随机值。
- **D1 的辖区要在一开始就决定。** 建好的库不能改辖区。一个全球共用的库和"欧盟玩家的数据留在欧盟"是冲突的，要么整个库放在欧盟，要么按地区分库。

最后一点的代价不小。按地区分库之后，每一个查 D1 的地方都要先知道这个玩家属于哪个地区；排行榜、名录、支付记录都要分开；跨地区的好友关系和对战要想清楚数据往哪边走。玩家对象也一样：`jurisdiction("eu").getByName(id)` 和 `getByName(id)` 是两个不同的对象，访问一个玩家之前要先知道他在哪个辖区，这个信息通常编码在玩家 ID 的前缀里。

所以建议是：**上线之前就确认有没有数据驻留的要求。** 没有的话，用默认的行为，不要为了"以后可能需要"而提前分库。有的话，在第一行代码之前就把"玩家属于哪个地区"设计进玩家 ID 和路由里，事后再改等于迁移全部数据。

示例项目没有使用辖区。

## 11.10 合规：技术上要准备什么

下面这张表列的是游戏后端常遇到的几类规定，以及它们在技术上对应什么。再说一次，具体的要求以当地的法规和平台的最新政策为准。

| 话题 | 大致的要求 | 技术上要准备的 |
|---|---|---|
| 平台内的支付 | Telegram 小程序里卖数字商品必须用 Stars；苹果和谷歌的应用商店要求应用内的数字商品走它们的内购 | 按平台走对应的支付渠道（第 8 章的订单结构支持多个渠道） |
| 未成年人 | 一些地区对未成年人的消费有限制，未经同意的消费可以要求退款 | 退款和追回的流程（第 8 章）；需要时加年龄确认和消费上限 |
| 随机奖励 | 很多地区和应用商店要求公示抽取的概率 | 概率写在服务端的配置里，对外展示的和实际执行的是同一份 |
| 差异化定价 | 对不同的人显示不同的价格，在一些地区受消费者保护法规的限制 | 价格实验要谨慎；实验分组有记录可查（第 9 章） |
| 数据采集的同意 | 一些地区要求在采集行为数据之前取得用户同意 | 同意之前不初始化分析 SDK（第 10 章的埋点在客户端） |
| 数据权利 | 导出、删除 | 11.8 节 |
| 数据驻留 | 特定地区的数据存放在境内 | 11.9 节 |
| 隐私政策 | 说明采集什么、存在哪、留多久、给了谁 | 这本书里的保留期：日志 7 天，对局记录 30 天，流水 180 天，支付记录长期 |

有两行值得多说一句。

**随机奖励。** 示例游戏没有抽卡这类玩法。如果你的游戏有，注意"对外展示的和实际执行的是同一份"这句话：概率表放在第 9 章的配置里，客户端展示的概率从 `/config` 读，服务端抽取时用的也是它。不要在客户端另外写一份用于展示的概率，两份迟早会不一致，而不一致的那一天就是违规的那一天。抽取的随机数由服务端生成，每一次抽取写进流水，这和掷骰子、发奖是同一套做法。

**差异化定价。** 第 9 章的 A/B 测试在技术上可以用来测试不同的价格。这在一些地区是有法律风险的，在任何地区都有口碑风险：玩家之间会交流，发现同一件东西别人买得更便宜，比价格本身更让人不满。测试"送什么"比测试"卖多少钱"安全得多。

## 11.11 测试

安全相关的测试有一个特点：大多是在测"不应该发生的事确实没有发生"。

限流的测试直接把接口调用到超过限额：

```ts
// 测试里的每个请求都带着不同的来源地址。
for (let i = 0; i < 35; i++) {
  statuses.push((await post("/rooms", {}, { token: session.accessToken })).status);
}
expect(statuses.slice(0, 30).every((status) => status === 200)).toBe(true);
expect(statuses.at(-1)).toBe(429);
// ……另一个玩家不受影响……
```

注释说的那一点是有意安排的：测试辅助函数给每个请求一个不同的来源地址，所以这个测试同时证明了"换地址绕不过按玩家的限流"。

人机验证默认是关的，测试它需要一份打开了开关的环境。做法是给测试环境包一层代理，只改这一个值：

```ts
/** 一份打开了人机验证的环境，其余和测试环境完全相同。 */
const strictEnv = new Proxy(env, {
  get: (target, key) => (key === "TURNSTILE_ENFORCE" ? "true" : Reflect.get(target, key)),
}) as Env;
```

然后分别测：没带令牌被拒绝，令牌没通过被拒绝，验证服务不可用时被拒绝，老玩家带着凭证回来不需要令牌。

删除账号的测试是这一章里最长的一个：先造出一个有好友、有排行榜记录、有余额的玩家，请求删除，然后逐项确认各处都清掉了，最后用原来的凭证再登录，确认得到的是一个不同的玩家 ID。清除函数另外单独调用了两遍，确认重复执行不出错。

重放的测试分两种。一种是真的打完一局（包括有人中途离开的），等记录落库，取出来重放，结果要一致。另一种是手工构造一份记录，然后分别改赢家、改点数、改顺序，每一种改动重放都要对不上。

## 11.12 示例项目的变化

这一章结束时，示例项目多了这些东西：

- `server/src/room.ts`：开局时记下座位顺序，对局中的离开也写进操作日志。

## 本章小结

- 防护的原则是让攻击的成本高于收益。可以抬高成本，也可以降低收益。损失最多的往往是自己人的失误。
- 限流分三层：防火墙挡大流量，不知道玩家是谁；Worker 里按玩家限高频调用，计数是近似的；对象里执行精确的业务上限。越靠前越便宜越粗。
- 接口按"能不能让服务端替调用者做一件有成本的事"来分档。被限流的请求要带上重试的时间，命中要记日志和指标。
- 所有的刷都从注册开始。创建新账号要过人机验证，令牌必须在服务端核实，核实不了时拒绝。涉及奖励的功能尽量只对绑定了平台身份的账号开放。
- 对象可以按名字凭空创建。名字不由服务端生成时，访问之前要有不依赖对象本身的办法确认它该不该存在。
- 反作弊的第一层是让客户端只能表达意图，结果由服务端算。先问"这个作弊是不是因为服务端信了客户端的某个值"。
- 凡是会改变结果的操作都要在日志里，检验的办法是重放。重放用来处理申诉、验证记录、验证规则的改动。
- 统计信号给出的是嫌疑，不是结论，处置之前要有人看。在设计上让串通没有收益，比事后去查容易。
- 管理后台要分角色，大额操作要两个人，操作记录要有人看。
- 导出是把玩家对象读出来。删除是一个跨对象的多步操作：先停用，再经队列分步清除，每一步可重复，清空自己放在最后。
- 支付记录、日志、备份、第三方平台上的数据各有各的处理方式，要事先想清楚并写进隐私政策。
- 数据驻留的要求要在上线之前确认。D1 的辖区只能在创建时指定，事后改等于迁移全部数据。
- 合规的要求以当地法规和平台政策为准。对外展示的概率和实际执行的要是同一份。测试价格要谨慎。
