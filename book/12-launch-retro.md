# 第 12 章　压测、账单与上线复盘

> 状态：初稿　｜　文档核实与实际运行日期：2026-11-25

功能写完了，测试都通过了，离上线还差三个问题：人多了撑不撑得住，一个月要花多少钱，出了事怎么办。这一章回答这三个问题，然后回头看这套架构哪些地方做对了，哪些地方是付了代价的。

这一章的代码在 [examples/loadtest/](../examples/loadtest/) 和 [examples/tools/](../examples/tools/)。

## 12.1 压测

### 测什么

单元测试证明的是逻辑对不对。压测要回答的是另一类问题：很多人同时来的时候，系统的哪一部分先出问题。对这套架构来说，值得测的是这几种情况：

| 场景 | 压的是哪里 | 关心什么 |
|---|---|---|
| 很多人同时排队 | 匹配对象 | 一个地区一个对象，每秒约 1,000 个请求的软限制 |
| 很多局同时在打 | 房间对象、玩家对象 | 每个对象压力都很小，看的是总量下的延迟和错误率 |
| 很多局同时结束 | 队列、D1 | 对局记录和分数通知的积压，发件箱的延迟 |
| 压测期间发一次版 | 所有对象 | 连接断开后的重连风暴，新旧版本并存时有没有报错 |
| 很多人同时看排行榜 | D1、缓存 | 缓存有没有起作用，数名次的查询有多贵 |

第一种最值得测，因为它是这套架构里少数"很多人打到同一个对象上"的地方。其余的对象都是一个玩家一个、一个房间一个，天然分散。

### 脚本

示例里有一个压测脚本，模拟一批玩家走完整的流程：登录、排队、进房、准备、轮流掷骰子直到结束。

```bash
node loadtest/run.mjs --base https://<你的预发地址> --players 200 --rounds 2 --think 200 --ramp 20
```

它是一个不到两百行的 Node.js 脚本，只用了内置的 `fetch` 和 `WebSocket`。每个虚拟玩家做的事和真实客户端一样：

```js
async function player(index) {
  let session;
  try {
    session = await timed("login", () => login(index));
  } catch (error) {
    return fail("login", error.message);
  }
  for (let round = 0; round < ROUNDS; round++) {
    try {
      const started = performance.now();
      const roomId = await timed("match_wait", () => findMatch(session));
      await playMatch(session, roomId);
      samples.match.push(performance.now() - started);
      counts.matches++;
    } catch (error) {
      fail("match", error.message);
      return;
    }
  }
}
```

脚本里有两个参数是有意加的：

- **思考时间（`--think`）。** 真实玩家不会在轮到自己的那一毫秒就出手。没有思考时间的压测，测出来的是一种现实中不存在的负载：消息密度高出几十倍，对象永远没有机会休眠。
- **进入速度（`--ramp`）。** 一千个玩家在同一秒登录，测的是登录限流，不是系统。让他们在一段时间内陆续进来。

脚本记录每一步的耗时，最后给出中位数和 95 分位：登录、等待匹配、进房、每一次掷骰子从发出到看到新状态、整局。

自己写脚本而不用现成的压测工具，是因为这里的流程是有状态的：要等服务端的消息才知道下一步做什么，掷骰子要带上刚收到的版本号。这类流程用通用工具表达起来比直接写代码麻烦。脚本模拟的是协议，所以协议变了（比如第 5 章给 `roll` 加了版本号），它要跟着改。

### 先撞上的是自己的防护

第一次对预发环境跑压测，几乎一定会失败，而且失败的原因和系统的承载能力无关：你被自己前面几章做的防护挡住了。

| 防护 | 现象 | 压测时怎么处理 |
|---|---|---|
| 登录接口按地址限流（第 4 章） | 第 21 个玩家开始登录失败，返回 429 | 预发环境的限流器是单独配置的，压测期间调高；或者从多个地址发起 |
| 人机验证（第 11 章） | 创建账号返回 403 | 预发环境用官方的测试密钥，它对任何令牌都返回通过 |
| 防火墙的限流规则（第 11 章） | 请求在到达 Worker 之前就被拦了 | 给压测的来源地址加一条放行规则，测完删掉 |
| 按玩家的限流（第 11 章） | 不应该出现。出现了说明虚拟玩家的行为不像真人 | 检查脚本，而不是调限流 |

最后一行值得注意。按玩家的限流是照着真实玩家的行为定的，压测脚本如果触发了它，通常是脚本有问题（比如失败后立刻重试）。

脚本有一个 `--local` 参数，用于对本地开发服务器测试：它给每个虚拟玩家伪造一个不同的来源地址，绕开按地址的登录限流。这个办法只在本地有效，线上的来源地址是 Cloudflare 填的，客户端改不了。

**压测只对预发环境做。** 第 2 章把预发和正式环境的资源完全分开了，压测产生的几千个账号、几千局对局记录都留在预发的库里，测完可以整个清掉。

### 压测发现的一个问题

写这一章时，脚本在本地第一次跑到 200 个玩家，结果是这样的：

```text
用时 32.3 秒，完成 56 人次对局

错误：
  196 次  match: connect failed
  2 次  match: closed 4003
```

登录全部成功，但绝大多数玩家连不上匹配队列。原因在上一章刚写的限流里：排队和进房的连接被归在"按玩家计数"的那一档，而取玩家身份用的是 `Authorization` 请求头。WebSocket 的令牌不在请求头里，在子协议里（4.8 节）。取不到身份，代码按设计退回到了按来源地址计数，于是所有从同一个地址来的连接共用每分钟 120 次的额度。

这个缺陷在线上的表现会是：同一个出口地址后面的玩家（一个公司、一所学校、一家移动运营商的一个网关）在高峰期莫名其妙地排不进队，而单个玩家自己测试时一切正常。上一章的 13 个测试没有发现它，因为测试里每个请求都带着不同的来源地址，那个设计本来是为了证明"按玩家限流不受地址影响"，结果恰好盖住了这个问题。

修正是让限流按连接的类型用对应的办法取身份：

```ts
// WebSocket 的令牌在子协议里，不在 Authorization 请求头里，要用对应的办法取。
const playerId =
  request.headers.get("Upgrade") === "websocket"
    ? await authenticateWebSocket(request, env)
    : ((await authenticate(request, env))?.sub ?? null);
if (playerId) key = `player:${playerId}`;
```

并补了一个测试：130 个不同的玩家从同一个地址排队，一个都不应该被限流。

另外那两个 `closed 4003` 不是缺陷。它们是配好了对、但对手没能连进来的玩家：房间等了 30 秒没等到人，按第 6 章的设计关闭了。

这件事说明了压测的另一个价值。它不只是测"能撑多少人"，更是第一次让**很多个不同的玩家同时**走完整条路径。单元测试里的玩家是一个一个来的，很多只在"同时"和"很多"的情况下才出现的问题，在那里看不到。

### 本地能测出什么

修正之后同样的参数再跑一次：

```text
目标 http://localhost:8799，200 个玩家，每人 2 局，思考 200 毫秒，每秒进入 20 人

用时 16.7 秒，完成 400 人次对局

步骤            次数    p50     p95     最大   （毫秒）
login            200    169     211      213
match_wait       400     81    1414     3900
join             400     52     148     3789
roll            2111      5      63      225
match            400   2452    4602     6182

没有错误。
```

这是在一台笔记本上对本地开发服务器跑的。它能说明的只有两件事：整条流程在并发下是通的，没有因为同时进行而出错；以及一局平均掷 10 到 11 次骰子，这个数后面算账时要用。

它**不能**说明线上的任何性能。本地所有的对象都在同一个进程里，没有网络延迟，没有对象所在位置的问题，没有冷启动，平台的各种限额也都不存在。延迟的数字和承载能力，只有对着部署在平台上的预发环境测才有意义。

对预发环境测的时候，脚本输出的延迟只是一半。另一半在平台那边，用第 10 章准备好的东西看：

- 平台的指标：各个对象类的请求数和错误数，Worker 的 CPU 时间，D1 的查询耗时，队列的积压。
- 自己的指标：`match_made` 的等待时长，`outbox_flush` 的延迟，`settle` 里重试的占比，`rate_limited` 的次数。
- 日志：`error` 级别的事件有没有出现。

压测期间这些指标的样子，就是以后判断"线上正常不正常"的基线。

## 12.2 会先撞上哪些限额

附录 A 列了一百多条限额。实际会先撞上的没有那么多，下面按"这套架构里大概在什么时候遇到"排了一遍。每一条前面的章节都处理过，这里是汇总。

| 限额 | 什么时候撞上 | 现象 | 对策 |
|---|---|---|---|
| 单个对象每秒约 1,000 个请求 | 一个地区的排队人数很多 | 请求先排队，再返回过载错误 | 按地区、分段拆队列（6.7 节） |
| 一次调用同时最多 6 个出站连接 | 一次请求里并发调用很多对象或外部接口 | 多出的调用在排队，延迟变长 | 分批，或者经队列扇出 |
| D1 按读取的行数计费 | 查名次、不带上限的统计 | 账单里 D1 的读取行数很高 | 查询带上限，榜单走缓存（7.4 节） |
| D1 单条查询最多 100 个参数 | 一次查很多玩家 | 查询报错 | 限制好友数，或者分批（7.7 节） |
| KV 同一个键每秒写 1 次 | 把频繁变化的东西放进 KV | 写入报错 | KV 只放很少改动的数据（9.2 节） |
| 一次调用最多写 250 个指标数据点 | 在循环里打指标 | 超出的数据点被丢弃 | 汇总之后打一个点 |
| 队列单条消息 128 KB | 把整局的状态或很长的日志放进消息 | 发送报错 | 消息里只放编号，内容另存 |
| 对象存储单个值的大小上限 | 把所有东西放进一个键 | 写入报错 | 按用途分键，日志分段 |
| 定时触发器改动后最长 15 分钟才生效 | 临时加一个定时任务 | 该跑的那一次没跑 | 提前部署，活动靠配置里的时间生效（9.4 节） |
| 限流绑定按地点各自计数 | 用它实现精确的次数限制 | 实际放过的比设定的多 | 精确的上限放在对象里（11.2 节） |
| 日志保留 7 天 | 查一周前的问题 | 查不到 | 需要长期保留的导出去（10.8 节） |
| 一个对象最多 32,768 条连接 | 做全服广播的频道对象 | 新连接被拒绝 | 分片，远在到达上限之前（5.11 节） |

有两条规律：

**大多数限额撞上时的现象是"报错"，少数是"变贵"或者"悄悄不对"。** 报错的容易发现。要多留心的是后两类：D1 的读取行数不会报错，只会出现在月底的账单上；限流绑定的近似计数、被丢弃的指标数据点、采样掉的日志，都不会有任何提示。

**几乎每一条的对策都是"拆"或者"设上限"。** 拆成更多的对象，拆成更小的批次，给查询加上限，给列表加上限。这套平台的每个部件都有明确的容量，设计时让每个部件上的负载有界，比事后优化容易得多。

## 12.3 账单

### 数出每一局发生了什么

第 1 章在动手之前估过一次成本，当时的假设是拍出来的。现在系统写完了，可以对着代码数：一局对局、一个玩家一天，实际会产生多少计费的操作。

以一局两个真人的排位赛为例：

| 计费项 | 一局里有多少 | 怎么数出来的 |
|---|---|---|
| Workers 请求 | 4 | 两条排队的连接，两条进房的连接 |
| 对象请求 | 约 15 | 匹配对象 2 次连接；房间 1 次开房、2 次连接、1 次清理的定时器，加上约 13 条消息按 20 条折 1 次；每个玩家 4 次调用 |
| 对象写入行数 | 约 80 | 房间每次状态变化写状态和定时表各 1 行，设一次定时器算 1 行，掷骰子多写 1 行日志；玩家结算时各写 5 到 6 行 |
| 对象活跃时长 | 约 1 秒 | 所有事件处理加起来的时间 |
| 队列操作 | 9 | 一条对局记录、两条分数通知，各算写入、读取、删除 |
| D1 写入行数 | 9 | 对局记录 1 行；两段录像、两条排行榜，各带 1 行索引 |
| 指标数据点 | 约 12 | 第 10 章的各项指标 |
| 日志条数 | 约 20 | 每次调用一条调用日志 |

其中有几条计费规则是数的时候才注意到的：

- **设一次定时器算写入一行。** 房间每次状态变化都重新设定时器，所以每一步都多一行。
- **索引也算行。** 往一张有一个索引的表里插入一行，计两行写入。
- **删除算写入。**
- **空闲并且可以休眠的对象不计时长，包括它被真正休眠之前的那一小段时间。** 所以房间的时长只算它实际在处理事件的时间。

### 钱花在哪了

把日活十万的那一栏展开看：

```text
对象写入行数                       6.2 亿        568.00
日志条数                         2.5 亿        141.00
Workers 请求                   1.2 亿         33.00
队列操作                        6750 万         26.80
指标数据点                        1.0 亿         23.00
对象请求                         1.5 亿         21.75
D1 写入行数                     7050 万         21.00
KV 读取                       4500 万         17.50
对象时长（GB·秒）                   104 万         12.50
```

这个结果和第 1 章的预期不一样，值得仔细看。

**最大的一项是对象的写入，占了三分之二。** 第 1 章的结论是"消息节奏决定成本"，担心的是对象睡不着带来的时长费用。那个结论本身没有错（看上面那张表的后两列），但在把休眠做对了之后，时长几乎不花钱，真正的大头变成了写入：每百万行 1 美元，而一局要写 80 行。

**第二大的是日志。** 这是第 10 章带来的。每一次调用一条调用日志，量和请求数成正比。

**对象时长排在最后。** 一局里房间实际工作的时间只有一秒左右，其余的时间它在休眠。第 5 章为"让房间能睡着"做的那些事（心跳由平台应答，定时用定时器而不是计时函数，不在内存里保留状态）在这里兑现了：如果房间在一局的 10 分钟里一直醒着，日活十万时的账单是八千美元，而不是九百。

所以第 1 章的那条原则要补上后半句：

> **先让对象能睡着，时长就不再是问题；之后成本由写入的行数决定。**

### 往下优化的顺序

知道了钱花在哪，优化就有了顺序。下面这几件事示例都没有做，因为在日活一万、每月 26 美元的规模上不值得；到了每月几百美元时，按这个顺序来：

**一、减少房间每一步的写入。** 现在每次掷骰子写四行：状态、定时表、日志、定时器。可以做的：

- 状态、定时表、日志合成一个键。它们本来就是在同一次写入里一起改的，合并之后每一步从三行变成一行。
- 定时器只在最早的到期时间确实变了的时候才重新设置。同一个玩家的回合里发生别的事时，截止时间没变，不需要再设一次。

这两项加起来，一局的写入能从 80 行降到 45 行左右，在日活十万的规模上能省下账单的将近三成。代价是一个键变大了，每次要整个重写。对一局几十步、状态几百字节的游戏，这没有任何问题。

**二、控制日志的量。** 调用日志可以关掉或者采样。但第 10 章说过，采样会让低频的错误日志丢失，告警跟着失效。更稳妥的顺序是先关掉不需要的调用日志，保留自己打的那些；确实还要降，再对请求量最大而又不重要的那部分采样。

**三、指标汇总之后再打。** 对象每次被唤醒打一个点的那种指标，可以改成抽样。Analytics Engine 自己会采样，但写入的数据点仍然按次数计费。

**不值得优化的：** Workers 的请求数、CPU 时间、流量。它们在账单里几乎看不见。为了省几次请求而把逻辑挪到客户端，或者为了省 CPU 而把代码写得难懂，都是不划算的。

### 两条计费上的细节

**超出的部分按计费单位向上取整。** 官方的例子是：超出 50 万 GB·秒的时长，按 100 万 GB·秒计费。所以每一项只要超出了包含的额度，至少要付一个单位的钱。上面日活一万的那张表里，指标数据点只超出了 20 万个，付的是一整个百万的 0.25 美元。这在小规模时让账单看起来比预想的高一点，规模大了之后可以忽略。

**真实的用量以平台的数据为准。** 模型里"一局 80 行写入"是数出来的，数的时候可能漏掉某次写入，也可能有哪条规则理解得不对。上线之后，用平台的用量数据除以对局数，得到真实的"每局多少"，替换掉脚本里的常数。如果真实的数比估算的高出一截，那本身就是一个值得查的信号：有某个地方在做你不知道的写入。

### 给账单上保险

成本失控通常不是因为玩家变多了，而是因为缺陷：一个死循环，一个不停重试的定时器，一次被刷。第 10 章说过要打开用量通知，这里再补一个更强硬的手段和它的风险。

Durable Object 可以设支出上限。达到上限之后，平台会**拒绝对对象的新请求**、拒绝存储的读写、拒绝新的定时器，直到你提高上限或者关掉它。它能保证账单不会无限增长，但对一个在线游戏来说，触发它等于整个游戏停服：进不了房间，读不了存档，结算发不出去。官方文档还说明了两点：已经打开的 WebSocket 连接上的消息不受影响；用量的上报和执行有延迟，所以上限并不保证账单一定不超过这个数。被挂起的定时器超过七天会被删除，恢复之后需要应用自己重新安排。

所以建议的做法是两级：

- **通知设得低。** 用量超过正常月用量的一倍半就通知，有人去看是怎么回事。
- **上限设得高。** 设在"正常情况下绝不可能达到，达到了一定是出了严重问题"的位置，比如正常月用量的十倍。它是最后一道保险，用来防止没人看到通知的那种情况。

## 12.5 上线，和上线之后

### 发版的顺序

每一次发布，不只是第一次，都按同一个顺序：

1. **先迁移，后发布。** 新代码依赖的表和列要先存在。反过来的顺序会让新代码在一段时间里对着旧的表结构运行。
2. **表结构的变更要让旧代码也能跑。** 因为第 1 步和第 2 步之间，线上跑的还是旧代码；发布之后的一段时间里，新旧版本的对象也会并存（3.3 节）。
3. **避开在线高峰。** 发布会让正在运行的对象重置，连接断开。第 5 章做的重连能让玩家回到对局里，但几千人同时重连仍然是一次集中的压力。
4. **用灰度。** `wrangler versions upload` 加 `wrangler versions deploy`，先放一小部分流量，看着第 10 章的指标，没有异常再放大（2.10 节）。灰度的粒度是对象，所以同一个房间里的人不会一半新一半旧。
5. **发完之后看十分钟。** 错误率、`unhandled_error`、结算的重试占比、发件箱的延迟。新版本的问题大多在头几分钟就会显现。

### 第一周看什么

上线的第一周，每天看一遍这几样：

- **错误类的告警有没有响过，响了是不是真的有事。** 第一周是调整阈值的时候：一直误报的要调高，该报没报的要补上。
- **匹配的三个数：平均等待时间、机器人占比、各地区的差别。** 下一小节展开。
- **发件箱的延迟和队列的积压。** 它们应该一直接近零。
- **每局的实际用量。** 用平台的用量数据除以对局数，和 12.3 节的估算对比。
- **死信表。** 第一周出现在里面的东西，几乎都是没想到的输入格式。
- **客服收到的问题。** 哪些是查得清的，哪些查不清。查不清的那些，说明还缺一条日志或者一个后台功能。

### 用数据调整匹配

第 6 章的匹配参数是拍的：起步接受 100 分的差距，每 3 秒放宽 100，等 10 秒补机器人，地区分成三个。当时说"有了数据再调"。现在有了。

| 看到的现象 | 说明什么 | 调什么 |
|---|---|---|
| 平均等待很短，机器人占比很低 | 人够多 | 可以把起步的分数差收紧，对局质量更好 |
| 机器人占比高，且集中在某个地区 | 这个地区人太少 | 把它并进相邻的地区 |
| 机器人占比高，且集中在某些时段 | 低峰期人少 | 低峰期合并队列，或者延长补机器人的等待 |
| 机器人占比高，且集中在高分段 | 高分玩家互相配不到 | 高分段的范围放宽得更快 |
| 等待时间的 95 分位远高于中位数 | 有一部分人总是等很久 | 看这些人的共同点：分数、地区、时段 |

这张表的每一行都对应 `match_made` 这个指标按某个标签分组之后的结果。这也是第 10 章坚持给指标带上地区和结果两个标签的原因：没有这两个标签，只能看到一个总的平均数，上面这些判断一个都做不了。

要做第三行和第四行的分析，还需要时段和分段这两个维度。时段可以从数据点的时间戳得到；分段要给指标加一个标签，按第 10 章的规则加在末尾。

调参数本身不需要发版的那一天会到来：把这几个数放进第 9 章的配置里。示例里它们还是代码里的常量。

## 12.6 回头看这套架构

全书用同一套结构做完了一个游戏后端的各个部分。最后回头看，哪些选择是对的，哪些是付了代价的。

### 做对了的

**一个玩家一个对象，一个房间一个对象。** 这是全书的基础，它带来的好处在后面每一章都出现过：

- 钱的并发问题在结构上不存在（第 8 章）。检查余额和扣款在同一个对象的同一个事务里，不需要锁。
- 身份的唯一性靠对象的命名保证（第 4 章）。
- 导出一个玩家的数据，就是把一个对象读出来（第 11 章）。
- 系统里没有热点。一百万个玩家是一百万个互不相干的小对象，没有哪一个会因为总人数增加而变慢。

**规则是纯函数。** 第 2 章定下的这条约定，当时看起来只是为了好测试。后来它让这些事成为可能：回合超时可以不等真实的时间就测出来（第 5 章），匹配规则可以直接用测试写出"等了 6 秒之后会怎样"（第 6 章），对局可以重放用于镜像对战（第 6 章）和校验（第 11 章），实验的分组可以离线重算（第 9 章）。**时间和随机数从外面传进来**，这一个做法的回报贯穿了全书。

**每一个跨边界的操作都带编号，都能重来。** 结算、发奖、发货、邮件、删除账号，用的是同一个模式：先在自己这边记下要做什么，再去做，对方按编号去重。这个模式写了很多遍，每一遍都不难，合起来让整个系统在任何一步失败之后都能恢复。

**不用运维。** 没有服务器要打补丁，没有数据库要扩容，没有日志系统要搭，没有告警服务要维护。第 10 章的告警和第 11 章的大部分防护是控制台里的配置。对一个小团队，这意味着人可以都花在游戏上。

**成本跟着使用量走，而且可以预测。** 没有玩家的时候几乎不花钱，12.3 节的表可以告诉你每多一万日活大概多花多少。

### 付了代价的

**跨玩家的数据都是最终一致的。** 排行榜晚一两秒，好友关系晚一两秒，支付记录晚一两秒。第 7 章的发件箱是这本书里最复杂的机制，而它存在的唯一原因是：两个对象不能在同一个事务里修改。在一个传统的数据库里，"甲加乙为好友"是一条事务，在这里是两个对象、一个队列、七个方法和一张"每种交叉情况最终落到哪"的表。

**没有办法对所有玩家做一件事。** 不能遍历对象，所以全服邮件、流水清理、表结构迁移都改成了"每个玩家下次出现时自己做"（第 9 章）。这个模式好用，但它是绕过一个限制的办法；真的需要在某个时刻对所有人生效的事（比如强制重置所有人的某个数据），仍然很难做。

**同一份数据经常要存两次。** 玩家对象里一份是源头，D1 里一份是用来查的副本：分数、邀请关系、支付记录、名录。每多一份副本，就多一条同步的路径和一种不一致的可能。

**凭空创建对象是要防的。** 这个教训出现了三次（第 6、7、11 章）。对象按名字自动创建很方便，但它意味着任何一个把外部传入的名字直接用来取对象的地方，都是一个可以被用来制造垃圾数据的口子。

**很多失败是不报错的。** 限流的计数是近似的，日志会被采样，指标数据点超限会被丢弃，分析平台的接口内容错了也返回成功，监控规则在没有数据时可能不触发。这本书里有相当多的篇幅是在给这些"安静的失败"加上能被看见的信号。

**本地和线上有差距。** 本地开发服务器上没有位置、没有冷启动、没有限额。测试能证明逻辑是对的，证明不了它在平台上表现如何。这个差距只能靠预发环境来补。

**绑定在一个平台上。** 规则在 `shared` 里，是和平台无关的纯函数，可以带走。除此之外，对象、它的存储、定时器、休眠的连接、队列、D1，都是这个平台特有的。换平台等于重写后端。这是选型时就要接受的事，第 1 章讨论过它适合和不适合的场景。

### 如果重新来一次

有三件事，如果从头再做，会更早地做：

**对象的存在性一开始就管起来。** 玩家名录到第 11 章才出现，在那之前的四章里，任何一个接受玩家 ID 的接口都有那个口子。它应该在第 4 章做账号的时候就有。

**发件箱在第 3 章就建好。** 第 3 章的结算用了"先记待办再发送"的做法，但只是房间里的一段代码。到第 7 章才把它做成通用的机制，然后第 8、9、11 章都在用。如果一开始就把它当作玩家对象的基础部件，中间几章会简单一些。

**每一局写多少行，早一点数。** 写入是账单里最大的一项，而房间的存储方式是第 3 章定的，那时关心的是"休眠后不丢"，没有数过行数。把状态、定时表、日志分成三个键是为了代码清楚，代价是每一步多写两行。这不是错误，在小规模时完全无所谓，但它说明了成本模型应该和代码一起写，而不是留到最后一章。

这三件事有一个共同点：它们都不是技术上做不到，而是当时没有意识到后面会反复用到。这大概也是写一个系统和设计一个系统的区别。设计的时候觉得每一章是一个独立的功能，写完才看出来哪几样东西是所有功能共用的地基。

## 12.7 示例项目的变化

这一章结束时，示例项目多了这些东西：

- `loadtest/run.mjs`：压测脚本。
- `tools/cost-model.mjs`：成本模型。
- `server/src/security/ratelimit.ts`：修正了连接的限流计数方式（12.1 节）。
- 测试：`test/security.test.ts` 新增 1 个，服务端一共 147 个测试。

到这里，示例项目的全貌是：

| | |
|---|---|
| 对象 | 房间、玩家、身份、匹配，四类 |
| 存储 | 对象自带的 SQLite；D1 一个库，10 张表；KV 一个命名空间 |
| 队列 | 对局记录、玩家通知，各带一个死信队列 |
| 定时任务 | 两个表达式，三件事 |
| 接口 | 玩家用的约 30 个，管理后台约 10 个，第三方回调 3 个 |
| 测试 | 规则 36 个，服务端 147 个 |

它仍然是一个示例：游戏本身只是掷骰子，客户端只有一个联调页面，很多地方只做了一种情况。但后端该有的每一层都在，每一层都能运行，而且都有测试。把它当作起点，换上你自己的规则，就是这本书希望达到的用法。

## 本章小结

- 压测回答的是"哪一部分先出问题"。最值得测的是很多人打到同一个对象上的地方，在这套架构里主要是匹配。
- 压测脚本要有思考时间和进入速度，否则测的是一种不存在的负载。
- 第一次压测先撞上的是自己的防护。预发环境的限流和验证要能单独配置。
- 压测是第一次让很多个不同的玩家同时走完整条路径，它能发现单元测试看不到的问题。
- 本地的压测只能说明流程在并发下是通的，性能和容量要对着平台上的预发环境测。
- 大多数限额撞上时会报错，要多留心的是只会变贵或者悄悄不对的那几条。对策几乎都是拆，或者设上限。
- 成本要对着代码数：一局里有多少次请求、多少行写入。上线后用真实的用量替换估算。
- 把休眠做对之后，对象的时长几乎不花钱，成本由写入的行数决定。优化从减少每一步的写入开始，不要去省请求数和 CPU。
- 用量通知设得低，支出上限设得高。支出上限触发时游戏会停服，它只是最后一道保险。
- 上线清单里凡是"验证过"的条目，都不能用"应该没问题"代替。
- 发版的顺序：先迁移后发布，表结构让旧代码也能跑，避开高峰，用灰度，发完看十分钟。
- 匹配的参数用指标来调，指标要带着能分组的标签。
- 这套架构的好处来自"一个玩家一个对象"和"规则是纯函数"；代价是跨玩家的数据最终一致、不能遍历对象、数据要存两份、很多失败不报错。

全书到这里结束。附录 A 是限额和价格的汇总，附录 B 是协议和错误码的约定。
