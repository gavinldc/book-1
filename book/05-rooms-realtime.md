# 第 5 章　房间与实时对战

> 状态：初稿　｜　文档核实与实际运行日期：2026-11-24

前面几章里的房间只能应付一切顺利的情况：玩家连上、准备、轮流掷骰子、有人到终点。真实的对局不是这样的。玩家会掉线，会切到后台半天不回来，会开两个窗口，会重复发送同一个操作，也会有人故意发一些不该发的东西。这一章把房间做成能上线的样子。

这一章的代码在 [examples/shared/src/rules.ts](../examples/shared/src/rules.ts)、[protocol.ts](../examples/shared/src/protocol.ts) 和 [examples/server/src/room.ts](../examples/server/src/room.ts)。

## 5.1 房间这一层只做五件事

先把分工说清楚。房间对象不写游戏规则，它是规则和外部世界之间的那一层，负责：

1. **管理连接**：谁连着、谁掉了、谁被顶替了。
2. **把外部发生的事翻译成操作**：一条消息、一次断线、一个定时器到点，都变成交给规则的一个操作。
3. **保存**：规则算出的新状态写进存储。
4. **广播**：把新状态发给房间里的人。
5. **管理时间**：回合什么时候截止，房间什么时候清理。

规则在 `shared` 里，是纯函数（2.3 节）。这一章新增的所有行为，掉线、超时、弃权，都是先在规则里加一个操作，再由房间在合适的时机调用它。房间里所有的状态变化都走同一条路：

```ts
private async apply(action: Action): Promise<RuleError | null> {
  const before = await this.load();
  const result = applyAction(before, action);
  if (!result.ok) return result.error;
  if (result.state !== before) await this.commit(before, result.state);
  return null;
}
```

读出状态，交给规则，规则说不行就返回错误，说行并且状态确实变了就保存和广播。这条路径上，读和写之间没有任何对外的调用，所以不会被别的消息插进来（3.6 节）。

**只有一条路径**这件事本身很重要。玩家的操作、定时器的超时、管理员的踢人，如果各有各的改状态的代码，迟早会有一处忘了广播，或者忘了处理"这一步让对局结束了"。

## 5.2 状态机：把所有会发生的事都列成操作

房间的状态有三个阶段：等待、对局中、已结束。这一章之后，规则认识的操作有六个：

| 操作 | 谁触发 | 等待阶段 | 对局中 | 已结束 |
|---|---|---|---|---|
| `join` | 玩家连接 | 加入；已在房间里则恢复在线 | 只允许已在房间里的人回来 | 同左 |
| `disconnect` | 最后一条连接断开 | 直接离开 | 保留位置，标记为离线 | 标记为离线 |
| `leave` | 玩家主动退出，或被踢出 | 离开 | 弃权 | 离开 |
| `ready` | 玩家消息 | 准备；所有人都准备好则开局 | 拒绝 | 拒绝 |
| `roll` | 玩家消息 | 拒绝 | 只有当前回合的人可以 | 拒绝 |
| `timeout` | 定时器到点 | 拒绝 | 当前回合的人轮空或弃权 | 拒绝 |

这张表就是状态机。每一格都有明确的答案，包括"拒绝"。写规则时最容易漏的不是合法的路径，而是那些"不该在这个阶段出现"的操作：对局结束后又来了一个掷骰子，等待阶段来了一个超时。规则对每一种都要有确定的反应，测试也要覆盖到。

有两点值得单独说。

**时间不进规则。** 规则里没有时钟，它不知道"现在几点"，也不判断"有没有超时"。超时由房间判断，然后作为一个 `timeout` 操作交给规则。这样规则仍然是纯函数，"连续超时两次判弃权"这样的逻辑可以用几行测试验证，不需要真的等待：

```ts
it("连续两次超时按弃权处理", () => {
  const state = run([
    ...twoReady,
    { type: "timeout", playerId: "a" },
    { type: "roll", playerId: "b", dice: 1 },
    { type: "timeout", playerId: "a" },
  ]);
  expect(state.phase).toBe("finished");
  expect(state.winner).toBe("b");
});
```

**状态带版本号。** 状态里多了一个 `version` 字段，每变化一次加一。它由规则的入口统一维护，各个操作的分支不用管：

```ts
export function applyAction(state: RoomState, action: Action): Result {
  const result = reduce(state, action);
  if (!result.ok || result.state === state) return result;
  return { ok: true, state: { ...result.state, version: state.version + 1 } };
}
```

一个操作如果没有改变任何东西，规则原样返回传入的那个对象，版本号不变，房间也就不会保存和广播。版本号后面有三个用处：服务端用它拒绝过时的操作（5.3 节），客户端用它丢弃乱序到达的旧状态（5.5 节），排查问题时用它对齐两端的日志。

## 5.3 服务端权威：客户端说的每一句话都要验

"服务端权威"的意思是：对局的真实状态只在服务端，客户端只能提出请求，不能陈述事实。具体落到代码上是六条。

**一、身份来自连接，不来自消息。** 消息里没有"我是谁"这个字段。是谁发的，由这条连接在建立时校验过的令牌决定（4.8 节），保存在连接的附加数据里。客户端没有任何办法替别人发操作。

**二、结果由服务端算。** 客户端只能说"我要掷骰子"，不能说"我掷出了 6"。随机数、伤害、掉落、抽卡结果，一切有随机性或者有价值的东西都在服务端生成。协议里 `roll` 消息没有点数字段，就是为了让这件事在类型层面就不可能。

**三、解析消息用白名单，并且重新组装。**

```ts
switch (message.type) {
  case "ready":
    return { type: "ready" };
  case "leave":
    return { type: "leave" };
  case "roll":
    // 只取认识的字段，重新组装一个对象，多余的字段不会被带进后面的逻辑。
    return Number.isSafeInteger(message.version) ? { type: "roll", version: message.version as number } : null;
  default:
    return null;
}
```

解析函数不是检查一遍然后把原对象传下去，而是只挑出认识的字段，组成一个新对象。客户端在消息里多塞的任何字段都到不了后面的代码。这能挡住一整类问题：后面的某段代码把消息对象展开进了状态，或者直接存了起来。

**四、限制消息的大小。** 平台允许的单条消息上限是 32 MiB，而这个游戏的合法消息不到 50 个字符。解析之前先看长度，超过 256 个字符直接拒绝，不要让 `JSON.parse` 去处理一个几十兆的字符串。

**五、拒绝过时的操作。** 掷骰子的消息要带上客户端当时看到的状态版本号：

```ts
case "roll": {
  // 客户端是看着某个版本的状态做出这个操作的。版本对不上，说明它看到的已经过时。
  if (message.version !== (await this.load()).version) {
    this.send(ws, { type: "error", code: "stale_version" });
    return;
  }
  action = { type: "roll", playerId, dice: rollDice() };
  break;
}
```

它防的是这样的情况：玩家点了按钮，网络卡住，客户端重发了一次；或者玩家在回合快结束时点了按钮，消息到达时已经因为超时换过一轮又轮回到他了。在这个掷骰子的游戏里，大多数重复的操作会被"不是你的回合"挡住，但不能指望这一点。在出牌、下注这类游戏里，同一个操作被执行两次就是一次事故。带版本号是一个通用的办法：**一个操作只对它所基于的那个状态有效。**

**六、限制每条连接的消息频率。**

```ts
private allow(ws: WebSocket, attachment: Attachment): boolean {
  const now = Date.now();
  const next =
    now - attachment.windowStart >= RATE_WINDOW_MS
      ? { ...attachment, windowStart: now, count: 1 }
      : { ...attachment, count: attachment.count + 1 };
  ws.serializeAttachment(next);
  if (next.count <= RATE_MAX_MESSAGES) return true;
  ws.close(CloseCode.TooManyMessages, "too many messages");
  return false;
}
```

每条连接 10 秒内最多 20 条消息，超过就断开。这里不能用 4.10 节的限流绑定，那个是近似的，而且是给入口用的；房间里要的是针对单条连接的准确计数。计数放在连接的附加数据里而不是成员变量里，原因还是那一个：对象随时会休眠，成员变量会清空。

限频保护的是两样东西。一是房间的吞吐，对象是单线程的，一个人刷消息会拖慢整个房间。二是账单，收到的消息是计费的，而且每条消息都会打断休眠。

### 隐藏信息

掷骰子没有秘密，所有人看到的状态都一样。但扑克、麻将、带战争迷雾的游戏都有"只有某个人能看到"的信息。这类游戏要多守一条：**不该让某个玩家知道的信息，不能发给他的客户端。** 不要把完整状态发下去再让客户端自己隐藏，发下去的数据都能被读出来。

做法是在规则里加一个"视图"函数，为每个玩家算出他能看到的那一份：

```ts
// 规则里：某个玩家能看到的状态。别人的手牌只留张数。
export function viewFor(state: RoomState, playerId: string): PlayerView {
  return {
    ...state,
    players: state.players.map((p) =>
      p.id === playerId ? p : { ...p, hand: undefined, handCount: p.hand.length },
    ),
  };
}
```

广播时逐个连接调用它。视图函数放在规则里，和规则一起测试："玩家 B 的视图里没有玩家 A 的手牌"应该是一条测试。示例项目没有隐藏信息，没有实现这个函数。

## 5.4 连接：标签、顶替和关闭码

### 用标签按玩家找连接

接受连接时可以给它打标签，之后按标签取出连接：

```ts
this.ctx.acceptWebSocket(server, [playerId]);
// ……
for (const ws of this.ctx.getWebSockets(playerId)) { … }
```

标签和附加数据都跟着连接走，休眠后都还在，但用途不同：标签用来**找**连接（"这个玩家的所有连接"），附加数据用来**读**连接上的信息（"这条连接是谁的，发了多少条消息"）。每条连接最多 10 个标签，每个标签最长 256 个字符。如果要做观战，可以再加一个 `spectator` 标签，把观众和玩家分开广播。

### 同一个玩家只留一条连接

玩家开了第二个窗口，或者网络切换后客户端重连而旧连接还没被发现已断，这时同一个玩家会有两条连接。示例的做法是新的顶替旧的：

```ts
// 同一个玩家只保留最新的一条连接，旧的被顶替。
for (const old of this.ctx.getWebSockets(playerId)) {
  old.close(CloseCode.Replaced, "replaced");
}
```

顶替比拒绝新连接好。拒绝的话，一个网络刚恢复的玩家会被自己那条已经死掉但服务端还不知道的旧连接挡在外面。

旧连接关闭后，房间会收到它的关闭事件。这时不能把它当成"玩家掉线了"，因为新连接还在：

```ts
private async onGone(ws: WebSocket): Promise<void> {
  const { playerId } = ws.deserializeAttachment() as Attachment;
  if (this.ctx.getWebSockets(playerId).some((other) => other !== ws)) return;
  await this.apply({ type: "disconnect", playerId });
}
```

只有这个玩家的最后一条连接断开，才算掉线。

### 关闭码要有含义

服务端主动断开连接时，带上一个应用自己定义的关闭码。4000 到 4999 这一段是留给应用用的：

```ts
export const CloseCode = {
  Replaced: 4001,        // 同一个玩家从别处连了进来
  Kicked: 4002,          // 被管理员移出房间
  RoomClosed: 4003,      // 房间已经结束并清理
  TooManyMessages: 4008, // 发消息太快
} as const;
```

客户端要根据关闭码决定下一步，这是关闭码存在的意义：

| 关闭码 | 客户端该做什么 |
|---|---|
| 4001 被顶替 | 不要重连。重连会把另一个窗口顶掉，两个窗口来回顶替 |
| 4002 被踢出、4003 房间关闭 | 不要重连，回到大厅 |
| 4008 消息太快 | 这是客户端的错误，不要自动重连 |
| 1006 异常断开，以及其他情况 | 用指数退避加随机抖动重连 |

关闭码定义在 `shared` 里，两端用同一份。

### 两个握手上的细节

**握手阶段的拒绝，浏览器拿不到原因。** 房间满了、对局已经开始，示例在握手时返回 409。测试和原生客户端能读到这个状态码，但浏览器的 `WebSocket` 接口不暴露它，页面上只能看到一次关闭码为 1006 的失败。如果需要让网页客户端知道被拒绝的原因，要换一种做法：先接受连接，立刻发一条错误消息，再用一个自定义的关闭码断开。

**收到对方的关闭后要回应。** 官方文档要求在 `webSocketClose` 里调用一次 `close()` 来完成关闭握手：

```ts
async webSocketClose(ws: WebSocket): Promise<void> {
  try {
    ws.close();
  } catch {
    // 已经关闭。
  }
  await this.onGone(ws);
}
```

兼容日期在 2026-04-07 及之后的项目，运行时会自动完成这次握手，示例里保留这一行是为了在两种情况下都正确。另外还要实现 `webSocketError`，连接出错时走同样的处理，否则一个出错的连接不会触发掉线逻辑。

## 5.5 断线重连

### 掉线不等于离开

上一章为止，连接一断，玩家就被移出房间，对局中等于直接认输。这在移动端是不能接受的：进电梯、切到别的应用回一条消息、网络从无线切到移动数据，都会断开连接。

现在的规则是按阶段区分的：

| 阶段 | 掉线后 | 理由 |
|---|---|---|
| 等待 | 直接离开房间 | 还没开局，占着位置只会让别人等一个不会回来的人 |
| 对局中 | 保留位置，标记为离线 | 给他回来的机会；回合照常计时 |
| 已结束 | 标记为离线 | 结果已定，不影响任何事 |

对局中掉线的玩家，位置、进度都在。其他人会在状态里看到他变成了离线，客户端可以把他的头像置灰。

### 重连就是再加入一次

重连不需要专门的接口。客户端用同样的地址和令牌再连一次，房间照常提交一个 `join` 操作，规则发现这个人已经在房间里，就把他恢复成在线：

```ts
case "join": {
  const existing = state.players.find((p) => p.id === action.playerId);
  if (existing) {
    // 已经在房间里：这是一次重连，任何阶段都允许。
    if (existing.connected) return { ok: true, state };
    return { ok: true, state: updatePlayer(state, action.playerId, { connected: true }) };
  }
  if (state.phase !== "waiting") return { ok: false, error: "already_started" };
  // ……
}
```

"对局开始后不能加入"和"对局中可以重连"是同一个分支里的两种情况，区别只在于这个人是不是本来就在房间里。因为玩家 ID 来自令牌，别人冒充不了。

### 重连后发完整的状态

重连的客户端不知道自己错过了什么。最简单也最可靠的做法是直接发一份完整的当前状态，而不是把错过的消息补发给它：

```ts
if (joined.state !== before) {
  // 状态变了，所有人（包括新连接）都会收到广播。
  await this.commit(before, joined.state);
} else {
  // 状态没变（比如同一个玩家开了第二个窗口），只给新连接发一份完整状态。
  this.send(server, await this.snapshot(joined.state));
}
```

这要求协议满足一个条件：**客户端只凭一条状态消息就能把界面完整地画出来。** 示例的协议从第 2 章开始就是每次广播完整状态，所以重连没有任何额外的工作。如果你的协议是只发变化量的（5.8 节），就必须另外准备一条"完整快照"消息，用于加入和重连。

客户端这边有两件事要做：

- **用版本号丢弃旧状态。** 收到的状态版本号比手上的还小，就丢掉。
- **重连后以服务端为准。** 本地做过的任何预测、播到一半的动画，都以收到的快照为准重置。

### 怎么知道该回哪个房间

客户端如果是整个应用被杀掉后重新启动的，它不记得自己在哪个房间。有两种办法：

- **客户端自己记。** 进房间时把房间号存在本地，启动时检查。简单，但换设备就没了。
- **服务端记。** 在玩家对象里记下"当前所在的房间"，登录后查询。这是一次跨对象的写入：进房间时由入口告诉玩家对象，对局结束时由房间在结算的同一次调用里清掉。

示例项目没有实现第二种。做的时候要注意，这个记录只是一个提示，不是事实：以房间自己的状态为准，客户端拿着房间号去连，连不上（房间已清理，或者自己已经不在里面）就当作没有进行中的对局。

## 5.6 一个定时器，多件事

房间里有三件事需要"到点执行"：

- 当前回合超时。
- 结算失败后的重试（3.7 节）。
- 对局结束后清理房间。

而一个对象同一时刻只能有一个定时器，后设的会覆盖先设的。上一章的房间只有结算重试一件事，直接设定时器没有问题；现在如果回合计时也直接设，就会把结算重试的那一次冲掉。

解决的办法是把"要做的事"和"定时器"分开。各件事的到期时间记在存储里的一张表里（下面叫它定时表），定时器永远只设在最早的那一个上：

```ts
interface Timers {
  turn?: number;   // 当前回合的截止时间
  settle?: number; // 下一次重试结算的时间
  close?: number;  // 清理房间的时间
}

private async arm(timers: Timers): Promise<void> {
  const times = Object.values(timers).filter((at): at is number => typeof at === "number");
  if (times.length === 0) await this.ctx.storage.deleteAlarm();
  else await this.ctx.storage.setAlarm(Math.min(...times));
}
```

定时器触发时，逐件检查是不是真的到期了：

```ts
async alarm(): Promise<void> {
  const due = (at: number | undefined) => at !== undefined && at <= Date.now();

  if (due((await this.timers()).close)) {
    await this.destroy();
    return;
  }
  if (due((await this.timers()).turn)) {
    const playerId = currentPlayer(await this.load());
    if (playerId) await this.apply({ type: "timeout", playerId });
  }
  if (due((await this.timers()).settle)) {
    await this.settle();
  }
  // 还有没到期的事，把定时器重新设上。
  await this.arm(await this.timers());
}
```

这段代码有三个刻意的地方：

- **每件事都自己检查时间，不假设"被叫醒就是到点了"。** 定时器保证至少执行一次，失败后还会重试，所以处理函数可能被多调用；而且它是为最早的那件事设的，别的事可能还没到期。示例有一个测试专门验证：在回合没到期时手动触发定时器，什么都不会发生。
- **每一步都重新读一次安排。** 前一步可能改了它，比如超时让对局结束，结算跟着就发生了。
- **最后总是重新设一次定时器。** 只要还有没做的事，定时器就一定在。

### 回合的截止时间

截止时间在回合换人时设置，和状态在同一次写入里保存：

```ts
const timers = await this.timers();
if (after.phase !== "playing") {
  delete timers.turn;
} else if (currentPlayer(before) !== currentPlayer(after)) {
  // 换人了才重新计时；同一个人的回合里发生别的事（比如有人掉线）不会让他多出时间。
  timers.turn = Date.now() + TURN_MS;
}
```

注意条件是"当前回合的人变了"，而不是"状态变了"。如果每次状态变化都重新计时，轮到的人只要让另一个人反复掉线重连，就可以无限拖延自己的回合。

广播状态时，把截止时间一起发给客户端：

```ts
this.broadcast({ type: "state", state: after, deadline: timers.turn ?? null });
```

**发的是截止的时刻，不是剩余的秒数。** 发"还剩 30 秒"的话，消息在路上花了多久、客户端什么时候处理的，都会让倒计时不准，重连的人更是不知道已经过去了多久。发时刻，客户端自己用本地时间算剩余时间，重连后收到的仍然是同一个时刻。它的前提是客户端的时钟大致准确；要求更高时，可以在连接建立后做一次简单的对时，用服务端和本地的时间差来修正。

客户端显示的倒计时只是给人看的，真正判定超时的只有服务端的定时器。客户端的倒计时归零后，不应该自己当作已经超时，而是等服务端发来新的状态。

### 定时器和休眠

定时器不会阻止休眠。等待玩家思考的 30 秒里，对象可以正常休眠，到点由平台唤醒。这正是不能用 `setTimeout` 来做回合计时的原因：它会让对象在整个回合里都醒着，按时长全额计费，并且对象一旦被重启，这个计时就丢了。

### 测试带时间的逻辑

回合是 30 秒，测试不能真的等。示例的做法是把时钟拨快，再让定时器立即触发：

```ts
async function advance(room: string, ms: number) {
  vi.useFakeTimers({ toFake: ["Date"] });
  vi.setSystemTime(Date.now() + ms);
  await runDurableObjectAlarm(env.ROOM.getByName(room));
}
```

`runDurableObjectAlarm` 是测试工具提供的，作用是立即执行一个对象上已设置的定时器。只伪造 `Date`，不伪造 `setTimeout` 这些，否则测试里的等待也会停住。因为处理函数里每件事都自己检查时间，这个测试方式和线上的行为是一致的：线上是时间真的到了，测试里是时钟被拨到了。

真实的 30 秒我也在本地开发服务器上等过一次：两个连接开局后不操作，约 30 秒后收到了轮空的状态和新的截止时间。

## 5.7 超时、轮空和弃权

回合超时之后怎么办，是一个产品决定，常见的有三种：

| 做法 | 表现 | 适合 |
|---|---|---|
| 轮空 | 这一回合什么都不做，换下一个人 | 跳过一回合没有严重后果的游戏 |
| 代打 | 服务端替他做一个默认的或者随机的操作 | 必须有人出牌游戏才能继续的情况 |
| 判负 | 直接输掉 | 节奏快、对等待容忍度低的对战 |

示例用的是轮空加上限：第一次超时轮空，连续两次超时按弃权处理。玩家自己操作一次，计数清零。

```ts
case "timeout": {
  if (state.phase !== "playing") return { ok: false, error: "not_playing" };
  const current = state.players[state.turn];
  if (!current || current.id !== action.playerId) return { ok: false, error: "not_your_turn" };
  const missed = current.missed + 1;
  // 连续超时达到上限，按弃权处理。
  if (missed >= MAX_MISSED_TURNS) return { ok: true, state: removePlayer(state, current.id) };
  // 否则这一回合轮空。
  const next = updatePlayer(state, current.id, { missed });
  return { ok: true, state: { ...next, turn: (state.turn + 1) % next.players.length } };
}
```

注意超时不区分玩家是掉线了还是在线但没操作。两种情况对其他玩家的影响是一样的，没有理由区别对待，而且区别对待会给人钻空子的机会：如果掉线不计超时，拔网线就成了暂停键。

**这条规则保证了每一局都会结束。** 最坏的情况是所有人都掉线并且再也不回来：定时器会一轮一轮地判超时，不断有人被判弃权，直到只剩一个人，对局结束、结算、清理。整个过程不需要任何人在线，也不需要任何后台任务来扫描"卡住的房间"。示例有一个测试覆盖这个场景：两个人开局后都断开，拨三次时钟，对局自己结束，胜者拿到了金币，房间被清空。

**一局对局必须在有限的时间内结束，无论玩家做什么或者不做什么。** 设计规则时把这一条当成硬性要求来检查，否则线上一定会积累永远不结束的房间。

### 一个从第 3 章带过来的错误

写上面那个测试时，它失败了：胜者的数据是对的，被判弃权的那个人的对局数却没有增加。

原因在第 3 章写的结算里。结算名单取的是对局结束时还在座位上的玩家，而中途离开或者弃权的人在那一刻已经被移出了座位，于是这一局对他来说没有发生过。在一个有胜率统计的游戏里，这意味着快输的时候退出就不计入败场。

修正是在状态里加一个 `forfeited` 列表，记下对局中途离开的人，结算时把他们一起算上：

```ts
// 中途离开和弃权的人也在名单里，他们同样打了这一局。
results: [...after.players.map((p) => p.id), ...after.forfeited].map((playerId) => ({
  playerId,
  won: playerId === after.winner,
  coins: playerId === after.winner ? WIN_COINS : 0,
})),
```

这个错误在第 3 章的测试里是发现不了的，因为那时的测试只打完整的对局。它说明了一件事：**结算的名单应该是"参加了这一局的所有人"，而不是"结束时还在的人"。** 做有入场费的房间时这一点更重要，退出的人交的入场费也在奖池里。

## 5.8 广播：发什么

### 全量还是增量

每次状态变化，可以把完整的状态发给所有人，也可以只发变化的部分。

| | 发完整状态 | 只发变化量 |
|---|---|---|
| 实现 | 简单，一条消息类型 | 每种变化一条消息类型，两端都要实现"应用变化" |
| 重连、丢消息 | 天然正确，下一条状态就能恢复 | 需要额外的完整快照，以及检测丢失的手段 |
| 带宽 | 状态大时浪费 | 省 |
| 出错的方式 | 很少出错 | 两端的状态可能悄悄地不一致 |

**回合制游戏先用完整状态。** 这类游戏的状态通常只有几百字节到几千字节，一局里的广播次数是几十到几百次，带宽不是问题，而增量同步带来的复杂度是实打实的。等状态确实大到有问题了（比如一局里有几百个单位的战棋）再换，并且换的时候保留完整快照这条消息。

费用上也没有理由一开始就做增量：发出的消息不计费，计费的是收到的消息。广播的成本是 CPU 时间和带宽，不是请求数。

### 合并消息

如果一次操作会产生多条通知（比如"掷出了 6"、"前进了 6 格"、"踩到了机关"、"后退 2 格"），把它们放进一条消息里发出去，不要连发四条。官方文档对此有专门的说明：每条消息都有固定的处理开销，大量的小消息会拖垮一个对象，即使总数据量很小；它的建议是把多条逻辑消息合并成一帧。

在只广播完整状态的协议里，这个问题自动不存在：一次操作一条状态。需要给客户端播放动画用的中间过程时，把过程作为一个事件数组放在同一条消息里。

### 这套模型的边界

回到第 1 章说过的话：这套架构适合回合制和慢节奏的同步，不适合每秒几十次状态同步的游戏。原因现在可以说得更具体了：

- 每条收到的消息都要计费，也都会打断休眠。
- 对象是单线程的，高频消息加上高频广播会占满它。
- 上面的整套设计（每次操作读一次存储、写一次存储）是为低频操作准备的。

如果你的游戏是每秒一两次操作，这套做法没有问题。如果是每秒十次以上，要重新考虑：把状态放在内存里、定期而不是每次都写存储、按固定的节拍合并广播。那是另一种设计，接受了"对象重启会丢失最近几百毫秒"的代价，本书不展开。

## 5.9 房间的一生

一个房间从出现到消失，经过这些阶段：

```
第一个玩家连接      对象被隐式创建，状态是初始值，存储是空的
      ↓
   等待阶段         有人加入就保存状态；人走光了立刻清空
      ↓ 所有人准备
   对局中           每个回合一个截止时间
      ↓ 有人到终点，或者只剩一个人
   已结束           状态和待结算记录一起写入
      ↓
   结算             发给每个玩家对象，失败就重试，直到全部成功
      ↓ 60 秒
   清理             关闭所有连接，清空存储
```

### 为什么必须清理

对象没有"销毁"这个操作，也不会自动过期。一个房间用完之后如果什么都不做，它的状态会永远留在存储里，按存储量计费。一个房间的状态很小，但房间的数量是随时间一直增长的：每天一万局，一年就是三百多万个再也不会被访问的对象。

清理的做法是清空存储：

```ts
private async destroy(): Promise<void> {
  for (const ws of this.ctx.getWebSockets()) {
    ws.close(CloseCode.RoomClosed, "room closed");
  }
  await this.ctx.storage.deleteAlarm();
  await this.ctx.storage.deleteAll();
}
```

存储清空之后，这个对象不再占用任何存储空间，也就不再产生费用。之后如果有人用同一个名字访问，得到的是一个全新的空房间。

关于 `deleteAll` 有一个和兼容日期有关的细节：兼容日期在 2026-02-24 及之后的项目，它会连定时器一起删除；更早的不会，定时器会留着，到点把对象再叫醒一次。示例里显式地先删了定时器，这样无论兼容日期是哪一天都正确。

### 什么时候清理

有两个时机：

**等待阶段人走光了，立刻清理。** 这是最常见的情况：有人建了房间，等不到人，走了。这时没有任何需要保留的东西。

```ts
// 还没开局、人已经走光：房间没有存在的必要了。
if (after.phase === "waiting" && after.players.length === 0) {
  await this.destroy();
  return;
}
```

**对局结束并且结算完成之后，延迟清理。** 示例里是 60 秒，让玩家看完结果。这里的顺序是关键：

```ts
// 结算发完之后才安排清理，没发完的房间不会被清掉。
if (timers.settle === undefined && timers.close === undefined) {
  timers.close = Date.now() + LINGER_MS;
}
```

**清理必须排在结算成功之后。** 待结算记录在房间的存储里，清空存储会把它一起删掉。如果清理的时间是在对局结束的那一刻就定好的，而结算因为某个玩家对象暂时不可用正在重试，房间就会带着没发完的奖励被清掉。所以清理的时间只在结算全部成功的那个分支里安排。

### 清理之后的记录

房间清空后，这一局的所有信息就只剩玩家对象流水里的那几行了。如果需要保留对局记录（用于客服查询、回放、反作弊），要在清理之前把它送出去：对局结束时往队列里发一条消息，消费者写进 D1 或 R2（3.10 节）。这同样要排在清理之前，并且和结算一样，要用"先记下待办、成功后删除"的方式保证送达。示例项目还没有做这一步，第 6 章做对局记录时会补上。

### 房间号的分配

到目前为止，房间号是客户端自己填的，谁都可以用任意的名字开一个房间。上线前要改成由服务端分配：

- 好友房：服务端生成一个短码，建房的人拿去分享。
- 匹配房：匹配成功后服务端生成房间号，直接发给被匹配到的几个人。

服务端分配的房间号还应该带上"谁可以进"的信息，否则知道房间号的人都能进。这部分放在第 6 章和匹配一起做。

## 5.10 管理接口：把人移出房间

第 4 章留下了一个问题：封禁一个玩家不会断开他已有的连接。房间需要一个把人移出去的接口：

```ts
/** 管理接口：把一个玩家移出房间。对局中等同于弃权。 */
async kick(playerId: string): Promise<void> {
  for (const ws of this.ctx.getWebSockets(playerId)) {
    ws.close(CloseCode.Kicked, "kicked");
  }
  await this.apply({ type: "leave", playerId });
}
```

它是一个 RPC 方法，没有对应的 HTTP 地址，所以只能被你自己的 Worker 调用。移出之后的状态变化走的还是那条唯一的路径：规则处理 `leave`，对局中就是弃权，只剩一人就结束并结算。

要让"封禁"自动触发"踢出"，还缺一块：封禁发生在玩家对象上，而玩家对象不知道这个玩家此刻在哪个房间。这正是 5.5 节提到的"玩家对象记下当前所在的房间"，有了它，封禁时就可以顺着找到房间并调用 `kick`。示例项目目前只提供了 `kick` 本身，两者的连接留到第 9 章做运营后台时完成。

## 5.11 跨房间的广播

房间里的广播很简单，因为房间里的人都连在同一个对象上。但游戏里总有一些消息要发给不在同一个房间里的人：全服的跑马灯、公会聊天、世界频道、"你的好友上线了"。

第 1 章说过，平台没有现成的全服广播，一个对象最多托管 32,768 条连接，实际能承载的还要少得多。这里把做法说完整：先看能不能不推送，然后是两种推送的做法，自己用频道对象来做，或者交给 Ably 这样的实时消息服务。示例项目没有实现这一节的内容，下面的代码是示意。

### 先问是不是真的需要推送

很多"广播"并不需要实时送达：

| 内容 | 实时性 | 做法 |
|---|---|---|
| 活动开始、配置更新、公告 | 晚一分钟没关系 | 客户端定期拉取，或者在已有的响应里捎带一个版本号（第 9 章） |
| 邮件、奖励到账 | 下次打开时看到即可 | 写进玩家对象，登录时读取 |
| 跑马灯、世界聊天、公会聊天 | 需要几秒内送达 | 频道对象，或者 Ably 这样的消息服务，见下文 |

能用拉取解决的就不要推送。推送要维持连接，而每一条长连接都意味着某个对象要托管它。

### 频道对象

需要实时推送时，单独建一类对象来托管这些连接，和房间分开。玩家进入游戏后连一条"频道"连接，这条连接只用来收推送，客户端几乎不往上发消息，所以托管它的对象绝大部分时间在休眠。

一个频道的人数可能超过单个对象能承受的量，所以要分片：

```ts
// 玩家连到哪一片，由玩家 ID 决定。
function shardOf(playerId: string, shards: number): number {
  let hash = 0;
  for (const char of playerId) hash = (hash * 31 + char.charCodeAt(0)) >>> 0;
  return hash % shards;
}

const channel = env.CHANNEL.getByName(`world:${shardOf(playerId, WORLD_SHARDS)}`);
```

广播时，把消息发给这个频道的每一片，每一片再发给自己托管的连接：

```ts
// 入口或队列的消费者：扇出到所有分片。
await Promise.all(
  Array.from({ length: WORLD_SHARDS }, (_, i) => env.CHANNEL.getByName(`world:${i}`).publish(message)),
);

// 频道对象：发给自己托管的所有连接。
publish(message: string): void {
  for (const ws of this.ctx.getWebSockets()) ws.send(message);
}
```

几个要想清楚的地方：

- **每一片放多少人。** 上限是 32,768，但那是硬上限。实际数字取决于消息的频率和大小，要靠压测得出，压测的方法见第 12 章。起步时可以按每片几千人估算。
- **分片数怎么定。** 分片数写在配置里。改变分片数会让玩家被分到不同的片上，所以调整时让客户端重连即可，频道连接上没有不能丢的状态。
- **扇出的并发。** 一个 Worker 的一次调用里能同时发起的对外请求数是有限的（见附录 A），分片很多时要分批，或者通过队列来扇出。
- **发送方不是玩家。** 世界聊天这类由玩家发起的消息，不要让客户端直接发到频道对象上，而是走一个 HTTP 接口：在那里鉴权、限流、过滤内容，然后再扇出。频道对象只管下发。
- **不保证送达。** 玩家掉线期间的广播就是丢了。跑马灯丢了没关系；不能丢的东西（比如奖励）不应该走这条路。

公会聊天、好友通知这类"发给一小群人"的消息，用的是同一个办法，只是频道的名字换成公会 ID，通常不需要分片。

### 另一个选择：Ably

频道对象不是唯一的做法。全局广播也可以整个交给专门的实时消息服务，Ably 是其中常用的一个，下面以它为例。本节的数字核对于 2026 年 11 月。

用 Ably 时，连接的走向和频道对象完全不同：

- **客户端直接连 Ably。** 玩家的频道连接不经过你的 Worker，也不占用任何对象。
- **后端只做两件事：签发令牌，发布消息。** 两件事都是普通的 HTTP 请求，Worker 里不需要引入 Ably 的 SDK。

分片、扇出、连接托管这三件事都由 Ably 负责，上一小节里要想清楚的几个地方大部分不用再想。

**签发令牌。** Ably 的 API 密钥只放在服务端，写进第 4 章讲的密钥配置里。客户端拿到的是一个短期令牌，官方推荐的格式是 JWT，用 API 密钥的后半段做 HMAC 签名，所以直接复用第 4 章的签名工具即可：

```ts
// API 密钥的格式是 "<密钥名>:<密钥内容>"。
async function ablyToken(env: Env, playerId: string, guildId: string | null): Promise<string> {
  const [keyName, keySecret] = env.ABLY_API_KEY.split(":");
  const now = Math.floor(Date.now() / 1000);

  // 只给订阅权限，而且只给这个玩家该收的频道。
  const capability: Record<string, string[]> = { world: ["subscribe"] };
  if (guildId) capability[`guild:${guildId}`] = ["subscribe"];

  const header = { typ: "JWT", alg: "HS256", kid: keyName };
  const claims = {
    iat: now,
    exp: now + 3600,
    "x-ably-clientId": playerId,
    "x-ably-capability": JSON.stringify(capability),
  };
  const encode = (value: object) => toBase64Url(new TextEncoder().encode(JSON.stringify(value)));
  const input = `${encode(header)}.${encode(claims)}`;
  return `${input}.${toBase64Url(await hmacSign(keySecret, input))}`;
}
```

这个函数放在一个需要登录的接口后面（比如 `POST /realtime/token`），客户端的 SDK 会在令牌快过期时自动再来取。有三点要守住：

- **权限写在令牌里，由服务端决定。** 客户端只能订阅令牌里列出的频道。玩家换了公会，下一次取令牌时拿到的就是新公会的频道。
- **不给客户端发布权限。** 这和上一小节"发送方不是玩家"是同一条原则：世界聊天仍然先走你的 HTTP 接口，鉴权、限流、过滤内容之后，由后端发布。
- **`clientId` 用玩家 ID。** 它由服务端写进令牌，客户端改不了。同一个玩家在所有设备上要用同一个 `clientId`，原因见下面的计费方式。

令牌最长可以签 24 小时。如果给密钥开启了令牌吊销，上限是 1 小时。封禁一个玩家时，不吊销的话他已有的令牌在过期前仍然能收到广播，对跑马灯来说通常可以接受。

**发布消息。** 入口或队列的消费者调用 Ably 的 REST 接口：

```ts
async function publish(env: Env, channel: string, name: string, data: unknown, id: string): Promise<void> {
  const url = `https://main.realtime.ably.net/channels/${encodeURIComponent(channel)}/messages?clientType=server`;
  const response = await fetch(url, {
    method: "POST",
    headers: {
      Authorization: `Basic ${btoa(env.ABLY_API_KEY)}`,
      "Content-Type": "application/json",
    },
    body: JSON.stringify({ id, name, data }),
  });
  if (!response.ok) throw new Error(`ably publish failed: ${response.status}`);
}
```

- `id` 是消息的唯一编号。带上它之后，同一个编号重复发布只会送达一次，所以放在队列的消费者里重试是安全的。这和 3.7 节的操作编号是同一个思路。
- `clientType=server` 声明这是服务端发出的请求。直接调用 REST 接口时不加这个参数，请求会被当成一个用户来计数。
- 不要在房间处理回合的路径上等这个请求返回。需要从房间里发全局消息时（比如"某某赢得了大奖"），把它放进队列，由消费者去发。

**限额。** 付费套餐（Pro 和 Business）下和游戏相关的几项：

| 项目 | 限额 |
|---|---|
| 同时在线的连接数 | 100,000 |
| 同一个 `clientId` 的并发连接数 | 10 |
| 每个频道每秒发布的消息数 | 100 |
| 每条连接每秒收到的消息数 | 100 |
| 每条连接可以加入的频道数 | 200 |
| 单条消息的大小 | 256 KiB（免费版 64 KiB） |
| 每个频道的在线状态成员数 | 200（开启服务端批处理后 10,000） |

一个世界频道每秒最多 100 条消息，对聊天来说够用；但一条连接每秒最多收 100 条，这是它订阅的所有频道加起来的数字，世界聊天很热闹时要在后端先做合并或抽样。

**计费方式。** Ably 目前按月活跃用户数计费，用 `clientId` 来区分用户：

| 套餐 | 包含的月活 | 价格（年付，每月） |
|---|---|---|
| 免费 | 500 | 0 |
| Pro | 1,000 | 29 美元 |
| Pro | 10,000 | 249 美元 |
| Pro | 50,000 | 1,149 美元 |

超出的部分每个月活 0.05 美元，超过 5 万要单独谈。另有一份公平使用政策，针对消息量或连接时长明显异常的账号，没有公开具体数字。

这个计费方式对游戏有两个直接的含义：

- **成本跟着月活走，不跟着消息量走。** 一个每月只登录一次的玩家和一个每天在线八小时的玩家，费用相同。对每个玩家收入很低、靠量取胜的游戏，要先把这笔钱算进单个玩家的成本里。
- **连上才算。** 只有连接过 Ably 的玩家才计入月活。如果广播只在某些界面才需要（比如进了大厅才显示跑马灯），到那时再连接，可以少算一部分人。

**怎么选。** 两种做法的对比：

| | 频道对象 | Ably |
|---|---|---|
| 连接由谁托管 | 你的 Durable Object | Ably |
| 要自己写的东西 | 分片、扇出、连接管理 | 签发令牌，调用发布接口 |
| 客户端 | 原生 WebSocket，不需要 SDK | 需要引入 Ably 的 SDK |
| 费用 | 按请求数和对象时长，计入 Cloudflare 账单 | 按月活 |
| 附带的功能 | 没有，都要自己做 | 断线后续传、消息历史、在线状态 |
| 供应商 | 一个 | 两个，多一份密钥、账单和故障面 |

本书的建议：

- 广播只是跑马灯和少量通知，玩家量大而单个玩家的收入低：用频道对象，费用最可控。
- 有世界聊天、公会聊天，需要消息历史和在线状态，或者团队不想维护连接这一层：用 Ably。
- 不论选哪个，把"发布一条广播"包成后端的一个函数，调用方不关心底下是什么。以后要换，只改这一个函数和客户端的连接代码。

最后说清楚边界。这里讨论的只是跨房间的广播。房间内的对局仍然由房间对象处理：对局需要一个权威的地方来校验操作、推进状态，而消息服务只负责把消息送到，不负责判断消息对不对。也有项目把房间内的消息同样交给消息服务，让客户端直接发布，这要求每一步的结果都能由各端按相同的规则推算出来，服务端另外做校验，是一套不同的设计，本书不展开。

## 5.12 发版时正在进行的对局

第 3 章讲过发版对对象的影响，这里补上房间特有的两点。

**房间的状态也是持久化的数据。** 发版时，正在进行的对局的状态是用旧代码写进去的，新代码要能读。这一章给状态加了 `version`、`connected`、`missed`、`forfeited` 几个字段，如果线上有正在进行的对局，新代码读到的旧状态里没有它们。处理的原则和表结构迁移一样（3.5 节）：新增的字段要有默认值，读取时补上；不要删除或者改变已有字段的含义。房间的寿命很短，另一个务实的办法是让旧的对局用旧代码跑完，用灰度发布控制切换的节奏（2.10 节）。示例项目没有线上的存量数据，没有写这一层兼容。

**协议的改动也要兼容。** 这一章把 `roll` 消息改成了必须带版本号，这对旧的客户端是一个不兼容的改动。上线之后，这类改动要通过 4.8 节的子协议版本来区分：新客户端声明 `game.v2`，服务端在一段时间内同时支持两个版本，等旧客户端基本消失后再移除。

## 5.13 示例项目的变化

这一章结束时，示例项目多了这些东西：

- `shared/src/rules.ts`：状态新增版本号、玩家的在线标记和超时计数、中途离开的名单；新增 `disconnect` 和 `timeout` 两个操作；`join` 兼作重连。
- `shared/src/protocol.ts`：`roll` 消息带版本号，新增 `leave` 消息；状态消息带回合的截止时间；新增关闭码的定义和消息长度的限制。
- `server/src/room.ts`：基本重写。按玩家打标签，新连接顶替旧连接；掉线不再等于离开；一个定时器管理回合超时、结算重试和房间清理三件事；每条连接的消息限频；对局结束并结算完成后清空存储；新增 `kick` 方法。
- 结算名单包含中途离开的玩家，修正了第 3 章留下的错误。
- 测试：规则的测试从 10 个增加到 21 个；服务端新增 `test/room.test.ts`，11 个测试，覆盖重连、顶替、过时的操作、回合超时、定时器提前触发、无人在线的对局自行结束、房间清理、踢人和消息限频。服务端一共 40 个测试。
- 联调页面：掷骰子时带上版本号，显示回合剩余时间和断开时的关闭码。

`Room` 上还有一个 `debugStorageKeys` 方法，用来在测试里确认存储确实被清空了。它只返回键名，但仍然不应该暴露成 HTTP 接口。

## 本章小结

- 房间只做五件事：管理连接、把外部的事翻译成操作、保存、广播、管理时间。所有的状态变化走同一条路径。
- 把所有会发生的事都列成操作，每个操作在每个阶段都要有确定的反应，包括拒绝。时间不进规则，超时由房间判断后作为操作交给规则。
- 状态带版本号。服务端用它拒绝过时的操作，客户端用它丢弃旧状态。
- 服务端权威：身份来自连接，结果由服务端算，消息用白名单解析并重新组装，限制大小和频率。有隐藏信息的游戏要按玩家发不同的视图。
- 用标签按玩家找连接。同一个玩家的新连接顶替旧连接，只有最后一条连接断开才算掉线。关闭码要让客户端知道该不该重连。
- 掉线不等于离开。对局中保留位置，重连就是再加入一次，重连后发完整的状态。
- 一个对象只有一个定时器。把各件事的到期时间记在存储里，定时器设在最早的那个上；触发时每件事自己检查是否到期。
- 截止时间只在回合换人时重设，发给客户端的是时刻而不是剩余秒数。判定超时的只有服务端。
- 超时不区分掉线和不操作。规则要保证每一局都能在有限时间内结束，不依赖任何人在线。
- 结算名单是参加了这一局的所有人，不是结束时还在的人。
- 回合制游戏先广播完整状态。发出的消息不计费，收到的计费；多条通知合并成一条消息。
- 房间用完必须清空存储，否则会永久占用并计费。清理要排在结算成功之后。
- 跨房间的消息先看能不能用拉取；需要推送时有两种做法：用独立的频道对象，按玩家 ID 分片，由入口或队列扇出；或者交给 Ably，后端只签发令牌和发布消息，费用按月活计。
- 房间的状态和协议都是要兼容的东西，发版时要考虑正在进行的对局和还没更新的客户端。
