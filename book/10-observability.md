# 第 10 章　埋点与可观测

> 状态：初稿　｜　文档核实与实际运行日期：2026-11-25

前面九章里，"第 10 章会给它加告警""第 10 章会把它做成指标"这样的话说了不下十次。这一章把它们兑现。

线上的系统在没有人看着的时候运行。它出了问题，你要么自己先发现，要么等玩家来告诉你。这一章做的事情只有一个目标：**让系统自己说出它的状态。** 出了错要说，变慢了要说，该发生的事没发生也要说。

这一章的代码在 [examples/server/src/obs/](../examples/server/src/obs/)。

## 10.1 四个问题，四种数据

关于线上系统，要回答的问题大致有四类，各自需要不同形状的数据：

| 问题 | 数据 | 例子 | 放在哪 | 留多久 |
|---|---|---|---|---|
| 这一次发生了什么 | 日志 | 这个订单为什么没发货 | Workers Logs | 7 天 |
| 总体上是多少 | 指标 | 匹配平均等多久，机器人占几成 | Analytics Engine | 3 个月 |
| 玩家在做什么 | 埋点 | 看了商店的人里多少买了东西 | Firebase（不在 Cloudflare 里） | 由分析平台决定 |
| 时间花在哪了 | 追踪 | 这个请求慢在哪一次调用上 | Workers 自带的追踪 | 随日志 |

四种数据经常被混在一起用，结果是哪种都用不好。最常见的两种混用：

- **用日志算指标。** 想知道匹配的平均等待时间，就去日志里搜出所有匹配成功的记录再算平均。量小的时候可以，量大了查询又慢又贵，而且日志只留 7 天。
- **用指标查个案。** 指标是聚合过的，它能告诉你今天有 12 笔订单发货失败，但说不出是哪 12 笔。

分清楚之后，同一件事往往要记两次：结算失败时，写一条日志（哪一局、什么错误），同时打一个指标（失败次数加一）。它们回答的是不同的问题。

## 10.2 日志

### 每条日志是一个对象

之前的代码里是这样打日志的：

```ts
console.error("结算失败，稍后重试", pending.matchId, error);
```

人读起来没有问题，但没法查。想找某一局的所有日志，只能做全文搜索；想知道今天这个错误出现了几次，要靠匹配那段中文。

平台的日志系统对对象形式的日志有专门的支持：把一个对象交给 `console`，它的每个字段都会被提取出来并建立索引。所以示例把所有日志改成了这个形状：

```ts
logger.error("settle_failed", { matchId: pending.matchId, error });
```

```ts
function write(level: "info" | "warn" | "error", event: string, fields: LogFields): void {
  const entry: LogFields = { event, ...fields };
  // 异常对象直接序列化是空的，取出有用的部分。
  if (entry.error instanceof Error) {
    entry.error = { name: entry.error.name, message: entry.error.message, stack: entry.error.stack };
  } else if (entry.error !== undefined && typeof entry.error !== "object") {
    entry.error = { message: String(entry.error) };
  }
  console[level](entry);
}
```

`event` 是这条日志的名字，其余字段是上下文。现在可以按 `event = settle_failed` 统计次数，按 `matchId` 找出一局的全部日志，按 `playerId` 找出一个玩家的全部日志。

那段处理异常的代码是必要的：`Error` 对象的 `message` 和 `stack` 不是可枚举的属性，直接序列化出来是一个空对象。很多人第一次查线上错误时，看到的就是一排 `"error": {}`。

### 三条约定

**事件名是固定的，变量放进字段。** `order_sync_failed` 是事件名，订单号是字段。不要写成 `` `order ${orderId} sync failed` ``，那样每条日志的名字都不一样，没法统计，也没法设告警。

**级别要有含义。**

| 级别 | 含义 | 例子 |
|---|---|---|
| `error` | 需要有人处理 | 收了钱发不了货，余额和流水对不上，消息进了死信队列 |
| `warn` | 出了问题，但系统会自己重试或者已经兜住 | 通知没送出去，核实某个订单失败，封禁后没踢到人 |
| `info` | 正常发生的、值得留痕的事 | 定时任务跑完了 |

判断标准是"半夜出现这条日志，需不需要叫醒人"。需要的才是 `error`。把预期之内的失败（玩家余额不足、签名不对的回调）打成 `error`，告警就会一直响，然后被所有人忽略。

**不记录秘密。** 密钥、令牌、游客凭证、支付平台的密钥，以及带有它们的地址和请求头，都不能出现在日志里。日志的访问权限通常比生产数据库宽松得多，而且会被导出到各种地方。第 8 章调用 Telegram 的地址里带着机器人令牌，所以那里出错时只记录了状态码，没有记录地址。

### 日志的配置和限额

日志采集在第 2 章就打开了：

```jsonc
// 日志全量保留；追踪打开后，请求经过的每一次对象调用、数据库查询都会被自动记录。
"observability": { "enabled": true, "traces": { "enabled": true } },
```

几个要知道的数字：

- **保留 7 天**（免费版 3 天）。要留更久，得导出去（10.8 节）。
- **单条日志最大 256 KB**，超出的部分被截断。
- **付费版每月包含 2,000 万条**，超出每百万条 0.60 美元。注意官方文档写明，这个价格从 2026 年 12 月 1 日起改为新的统一计价方式，上线前要重新核对。
- **每个账号每天最多 50 亿条**，超过后当天剩余的时间只保留 1%。

量很大时可以按比例采样，在配置里设 `head_sampling_rate`（0 到 1 之间）。采样是按请求进行的：一个请求被选中，它的所有日志都保留；没被选中，全部丢弃。要注意它对告警的影响：采样率是 10% 时，一条只出现一次的错误日志有九成的可能看不到。所以对于低频但重要的错误，不要采样；先靠减少无用的日志来控制量。

Durable Object 里打的日志和 Worker 的在一起，在控制台里可以按对象的类来筛选。

### 存储、查询、告警都用平台的

上面那个 `log` 函数只有十几行，它做的事情只是规定日志的形状。日志写出去之后的每一步都不需要自己搭：

- **采集和存储**：配置里打开 `observability` 之后，`console` 输出的每一条都被平台收走并保存，不需要日志代理，也不需要自己的日志服务。
- **请求记录**：平台为每一次调用自动生成一条调用日志，里面有请求的地址、状态码、耗时、CPU 时间、来源国家。所以示例没有自己打"访问日志"。
- **查询**：控制台里的查询界面可以按字段筛选、全文搜索、分组、排序，并把结果画成图。筛选用的就是日志对象里的字段名，比如 `event`、`playerId`；平台自动加的字段以 `$workers` 开头，比如 `$workers.cpuTimeMs`。
- **告警**：在日志上定义监控规则，10.7 节展开。

这套架构的一个好处是不用运维，日志这一块同样如此。自己要做的只有一件事：**把日志打成平台能用好的形状。**

## 10.3 请求编号

玩家说"我刚才点购买报错了"。线上每秒几百个请求，哪一个是他的？

入口给每个请求一个编号，放进应答头，并且在出错时写进日志：

```ts
async fetch(request: Request, env: Env): Promise<Response> {
  const requestId = request.headers.get("cf-ray") ?? crypto.randomUUID();
  let response: Response;
  try {
    response = await route(request, env);
  } catch (error) {
    log.error("unhandled_error", {
      requestId,
      method: request.method,
      path: new URL(request.url).pathname,
      error,
    });
    // 错误的细节只进日志，不返回给客户端。
    response = Response.json({ error: "internal", requestId }, { status: 500 });
  }
  // WebSocket 的握手应答不能改动。
  if (response.status === 101) return response;
  const headers = new Headers(response.headers);
  headers.set("X-Request-Id", requestId);
  return new Response(response.body, { status: response.status, statusText: response.statusText, headers });
},
```

编号优先用 `cf-ray`，这是平台给每个经过它的请求分配的标识，平台自己的日志里也用它。本地开发时没有这个请求头，就自己生成一个。

客户端在显示错误时把这个编号一起显示出来（或者放进"复制错误信息"里）。玩家把它发给客服，客服拿它一搜，就是那一次请求的日志。

这段代码还做了第二件事：**兜住所有没被处理的异常。** 在这之前，路由里任何一处抛出异常，客户端收到的是平台默认的错误页，日志里是一条没有上下文的异常记录。现在所有这类情况都变成一条带路径、带编号的 `unhandled_error` 日志，和一个格式统一的应答。

应答里只有 `internal` 和编号，没有错误的内容。异常的消息里可能有表名、内部地址、别的玩家的 ID，不应该发给客户端。

第 8 章的回调处理依赖"抛出异常，返回 500，让支付平台重发"。加了这层兜底之后行为不变：异常仍然变成 500，只是多了一条日志。

## 10.4 指标

### 数据点的形状

指标写进 Analytics Engine。它是一个专门存这类数据的时序存储，写入的每个数据点有三部分：

- **标签**（`blobs`）：字符串，用来分组和筛选。最多 20 个。
- **数值**（`doubles`）：数字，用来求和、求平均。最多 20 个。
- **采样键**（`indexes`）：一个字符串。数据量大到需要采样时，按这个键分别采样。

它的接口有一个容易出错的特点：标签和数值都是**按位置**对应的。写入时是数组里的第几个，查询时就是 `blob1`、`blob2`、`double1`。写的时候把两个标签的顺序调换了，不会有任何报错，只是从那一刻起的数据都是错位的。

所以示例把所有指标的定义集中在一处：

```ts
export const METRICS = {
  /** 一次匹配的结果。labels: 地区、结果（pair/bot）。values: 等待毫秒数。 */
  match_made: { labels: ["region", "outcome"], values: ["wait_ms"] },
  /** 匹配对象每次计算时队列里的人数。labels: 地区。values: 人数。 */
  queue_size: { labels: ["region"], values: ["waiting"] },
  /** 一局结束。labels: 类型（private/ranked/mirror）。values: 步数、参加的真人数。 */
  match_end: { labels: ["kind"], values: ["turns", "humans"] },
  /** 一次结算尝试。labels: 结果（ok/retry）。values: 1。 */
  settle: { labels: ["outcome"], values: ["count"] },
  /** 玩家对象送出一批通知。labels: 结果（ok/failed）。values: 条数、最旧一条等了多久（毫秒）。 */
  outbox_flush: { labels: ["outcome"], values: ["rows", "lag_ms"] },
  /** 对象被唤醒时构造函数花的时间。labels: 对象的类。values: 毫秒数。 */
  object_wake: { labels: ["class"], values: ["construct_ms"] },
  /** 一次定时任务。labels: 表达式、结果（ok/failed）。values: 耗时毫秒数。 */
  job_run: { labels: ["cron", "outcome"], values: ["ms"] },
  /** 一笔订单的状态变化。labels: 渠道、状态。values: 金额（最小单位）。 */
  payment: { labels: ["provider", "status"], values: ["amount"] },
} as const;
```

这张表既是代码，也是文档：查询时 `blob2` 是什么，看这里就知道。写入时个数不对会直接抛出异常，测试里就能发现：

```ts
export function toDataPoint(name: MetricName, labels: string[], values: number[]): DataPoint {
  const shape = METRICS[name];
  if (labels.length !== shape.labels.length || values.length !== shape.values.length) {
    throw new Error(`指标 ${name} 的字段个数不对`);
  }
  // 指标名同时作为采样键：数据量大到需要采样时，每种指标各自采样，量小的不会被量大的挤掉。
  return { indexes: [name], blobs: [name, ...labels], doubles: values };
}
```

所有指标写进同一个数据集，第一个标签固定是指标的名字。已有的指标只能在末尾追加字段，不能调换顺序，也不能删除中间的字段。这和表结构迁移是同一种约束。

**写指标不能影响业务：**

```ts
/** 写一个数据点。指标写不进去不应该影响正常的业务，所以这里吞掉所有异常。 */
export function metric(env: Env, name: MetricName, labels: string[], values: number[]): void {
  try {
    env.METRICS.writeDataPoint(toDataPoint(name, labels, values));
  } catch {
    // 忽略。
  }
}
```

`writeDataPoint` 不需要等待，它立刻返回，数据在后台写出。所以在房间和玩家对象里写指标是安全的，不违反"读改写之间不要等待外部调用"的约定。

### 前面几章欠下的指标

**匹配**（第 6 章）。匹配对象每次给一组人开好房，记一个点：

```ts
metric(this.env, "match_made", [region, group.length === 1 ? "bot" : "pair"], [Date.now() - ticket.since]);
```

有了它，就能回答匹配系统最重要的三个问题：玩家平均等多久，多大比例的人最后配到的是机器人，各个地区的差别有多大。第 6 章里"起步 100 分、每 3 秒放宽 100、10 秒补机器人"那几个数是拍出来的，这些指标是调整它们的依据。

**发件箱**（第 7 章）。玩家对象每次送出通知时，记下送了几条，以及最旧的一条等了多久：

```ts
// 最旧的一条通知已经等了多久。正常情况下接近 0，持续变大说明通知送不出去。
const oldest = (JSON.parse(String(rows[0]!.body)) as { at?: number }).at;
const lag = typeof oldest === "number" ? Math.max(0, Date.now() - oldest) : 0;
```

正常情况下这个延迟是几毫秒。队列出问题时，它会持续变大。这是一个"先行指标"：排行榜不更新、好友申请收不到这些玩家能感知的现象出现之前，这个数已经在涨了。

**对象的唤醒**（第 3 章）。3.3 节说过，冷启动里属于你自己的那部分开销是构造函数：

```ts
// 构造函数在每次唤醒时都执行，它的耗时就是这类对象冷启动里属于我们自己的那一部分。
const started = Date.now();
migrate(ctx.storage);
metric(env, "object_wake", ["Player"], [Date.now() - started]);
```

这个数平时很小。它有用的时刻是发版之后：新版本加了一次表结构迁移，或者有人在构造函数里加了一次查询，这个指标会立刻显示出来。

**支付**（第 8 章）和**定时任务**（第 9 章）各有一个，前者按渠道和状态统计订单，后者记录每次执行的耗时和结果。

### 查询

Analytics Engine 用 SQL 查询，通过 Cloudflare 的 API 访问。最近一小时各地区的匹配情况：

```sql
SELECT
  blob2 AS region,
  blob3 AS outcome,
  SUM(_sample_interval) AS matches,
  SUM(_sample_interval * double1) / SUM(_sample_interval) AS avg_wait_ms
FROM game_metrics
WHERE blob1 = 'match_made' AND timestamp >= NOW() - INTERVAL '1' HOUR
GROUP BY region, outcome
```

`_sample_interval` 是查询时一定要带上的东西。数据量大时，Analytics Engine 会自动采样：只存一部分数据点，每个存下来的点代表若干个原始的点，这个"若干"就是 `_sample_interval`。所以计数要写成 `SUM(_sample_interval)` 而不是 `COUNT()`，求和要乘上它，求平均要用加权的写法。数据量小、没有发生采样时它等于 1，两种写法结果相同；但只有一开始就写对，数据量上来之后图表才不会悄悄变得不准。

限额和价格：

- 每次调用 `writeDataPoint` 算一个数据点，一次 Worker 调用里最多写 250 个。
- 所有标签加起来不超过 16 KB，采样键不超过 96 字节。
- 数据保留 3 个月。
- 付费版每月包含 1,000 万个数据点，超出每百万 0.25 美元；查询每月包含 100 万次，超出每百万 1 美元。

用它的时候有一条界线：**不要把玩家 ID 当标签。** 指标回答的是总体的问题。一旦按玩家打点，数据点的数量就和玩家数成正比，而且你迟早会想用它查"某个玩家的情况"，那是日志和埋点的工作。

### 平台自带的指标

不用写任何代码，平台已经在记录一批指标：每个 Worker 的请求数、错误率、CPU 时间、响应耗时；每类对象的请求数、活跃时长、存储用量；队列的积压长度；D1 的查询耗时和读写行数。它们在控制台里能看到，也可以通过 GraphQL 接口取出来。

这些是**平台视角**的指标：它们知道一个请求花了多久，但不知道那是一次匹配还是一次购买。自己打的指标补的是**业务视角**。两种都要看：平台指标告诉你系统是否健康，业务指标告诉你游戏是否正常。一个所有请求都返回 200、耗时都很短，但所有玩家都配到机器人的系统，在平台指标里是完全健康的。

## 10.5 埋点

### 不放在 Cloudflare 里

埋点记录的是玩家的行为：打开了哪个界面，点了哪个按钮，在哪一步离开了。它和日志、指标是不同的东西：

- **保留到每一个玩家、每一次行为。** 分析时要按玩家把事件串成序列（先看了商店，然后买了东西），所以不能聚合。
- **量大。** 一个活跃玩家一天几百条。
- **看数据的不是工程师。** 用它的是策划、运营和投放，他们要的是漏斗、留存、分群这些现成的报表，而不是一个要写 SQL 才能查的存储。

这三点合起来，结论是埋点不值得自己建。在 Cloudflare 上自己做当然做得出来：客户端上报到一个接口，经队列批量写进 R2，再找一个查询引擎去读。这本书的初稿就是这么写的，然后删掉了。原因是那只做完了最容易的一半，存下来之后的漏斗、留存、分群、看板，每一样都要另外搭，而这些正是分析平台已经做好的东西。

示例项目用的是 Firebase 的分析功能（Google Analytics for Firebase）。选它的理由很实际：

- **免费，事件量不设上限。** 对一个还没有收入的新游戏，这比任何技术上的优点都重要。
- **报表是现成的。** 活跃、留存、漏斗、分群开箱即用。
- **投放要用。** 出海游戏买量的主要渠道之一是 Google 的广告，它的效果归因和这套数据是打通的。
- **原始数据可以导出。** 报表不够用时，可以把原始事件导出到 BigQuery 自己查。

代价是玩家的行为数据在一个第三方平台上，它在中国大陆访问不了（面向海外的游戏不受影响），在一些地区上报之前需要先取得玩家的同意（第 11 章）。

### 客户端直接上报

埋点由客户端的 Firebase SDK 直接发给 Firebase，**不经过我们的后端**。后端里没有任何接收埋点的接口，这部分流量、存储和费用都和 Cloudflare 无关。

客户端要做三件事。SDK 的具体用法以 Firebase 的文档为准，这里只说和后端有关的部分。

**把玩家 ID 设为用户标识。** 登录成功后，把服务端返回的玩家 ID 交给 SDK。之后这个玩家在任何设备上产生的事件都会归到同一个人，也才能和服务端的数据（D1 里的订单、对局记录）对上。

**把实验分组设为用户属性。** 从 `/config` 拿到自己在各个实验里的分组之后，设成用户属性，报表里就可以按分组对比。第 9 章留下的"曝光"也在这里解决：玩家真正看到实验内容的那一刻，客户端上报一条曝光事件。

**把自己的分析标识告诉服务端。** SDK 会给每个安装生成一个标识。客户端取到它之后调用一次后端的接口：

```ts
/** 客户端把 Firebase 给它的分析标识告诉服务端，服务端补报事件时用。 */
export async function handleAnalytics(request: Request, env: Env, pathname: string): Promise<Response | null> {
  if (pathname !== "/analytics/client") return null;
  // ……登录校验……
  const clientId = body?.clientId;
  if (typeof clientId !== "string" || !CLIENT_ID.test(clientId)) return fail(400, "bad_request");
  await env.PLAYER.getByName(claims.sub).setAnalyticsId(clientId);
  return json({ ok: true });
}
```

它被存在玩家对象里。用途在下一小节。

### 客户端的数据能信多少

客户端上报的数据有一个根本的局限：**它是客户端说的。** 客户端可以不报（装了拦截插件，网络断了），可以乱报，可以重复报。

所以要分清两类数据：

| 数据 | 以什么为准 | 为什么 |
|---|---|---|
| 界面浏览、点击、停留、漏斗 | Firebase | 只有客户端知道，丢一些、不准一些不影响结论 |
| 收入、订单、对局数、货币的产出和消耗 | 自己的数据库 | 会被拿去做决策和对账，不能建立在客户端的上报上 |

第二类数据在前面几章里都已经有了可靠的来源：订单在 D1 的支付记录表里（第 8 章），对局在对局记录表里（第 6 章），每个玩家的货币变动在他的流水里。**Firebase 上的数字用来看趋势、看行为，不用来算钱。** 两边的收入数字对不上时，以自己的为准。

实验的分组也是同样的道理。客户端报上来的"我在哪一组"只是方便在报表里直接看。真要严谨地分析一个实验，分组可以在离线时重新算：第 9 章的 `variantOf` 是一个纯函数，拿着玩家 ID 和实验名，在任何地方算出来的结果都一样。

### 服务端补报付款

有一类事件值得由服务端补报到 Firebase：付款。运营想在同一个漏斗里看到"看了商店 → 点了购买 → 付款成功"，而最后一步如果由客户端来报，恰恰是最不可靠的：付完钱之后玩家可能没有回到游戏，回调可能晚到，也有人会伪造。

Google Analytics 有一个给服务端用的上报接口，叫衡量协议（Measurement Protocol）。官方对它的定位说得很清楚：它用来**补充**客户端的自动采集，不是用来替代。这正是这里的用法。

付款的通知本来就要经过发件箱和队列（第 8 章），在消费者里顺手补报一次：

```ts
case "payment":
  await savePayment(env.DB, event);
  metric(env, "payment", [event.provider, event.status], [event.amount]);
  // 付款和退款是服务端确认过的事实，由服务端补报给分析平台，不依赖客户端。
  await reportPayment(env, event);
  return;
```

```ts
export async function reportPayment(env: Env, event: PaymentEvent): Promise<void> {
  if (event.status === "pending") return;
  // 没有配置数据流，或者这个玩家的客户端还没告诉我们它的分析标识：不报。
  if (!env.GA_MEASUREMENT_ID || !event.analyticsId) return;

  const stripe = event.provider === "stripe";
  const body: Record<string, unknown> = {
    // client_id 让这条事件和这个玩家在客户端产生的事件归到同一个人、同一台设备上。
    client_id: event.analyticsId,
    user_id: event.playerId,
    events: [
      {
        name: event.status === "paid" ? "purchase" : "refund",
        params: {
          // 订单号。同一笔付款被重复上报时，分析时可以按它去掉重复的。
          transaction_id: event.orderId,
          item_id: event.productId,
          payment_provider: event.provider,
          // 真实货币按规范填金额和币种。Stars 不是标准币种，单独放一个参数。
          ...(stripe
            ? { currency: event.currency.toUpperCase(), value: event.amount / 100 }
            : { stars: event.amount }),
          source: "server",
        },
      },
    ],
  };
  const at = event.status === "paid" ? event.paidAt : event.at;
  if (Date.now() - at < MAX_BACKDATE_MS) body.timestamp_micros = at * 1000;
  // ……发送……
}
```

几处细节：

- **要带上客户端的标识。** 这就是上一小节那个接口的用途。没有它，服务端报的事件和客户端报的事件会被当成两个不相干的用户，漏斗就接不上了。网页端的数据流用 `measurement_id` 加 `client_id`；原生应用的数据流用 `firebase_app_id` 加 `app_instance_id`，两者不能混用。示例按网页端写，因为这本书的客户端是网页和 Telegram 小程序。
- **可以补报过去的时间，最多 72 小时。** 付款的通知经过队列会晚几秒，掉单补回来的可能晚几小时，所以带上实际付款的时间。超过 72 小时的不带时间戳。
- **有上限。** 一次请求最多 25 个事件，事件名和参数名不超过 40 个字符，参数值不超过 100 个字符，请求体不超过 130 KB。
- **Stars 不当金额报。** 分析平台的收入报表按标准币种汇总，Stars 不在其中。示例把它放在一个自定义参数里；想在收入报表里看到，就要自己按一个汇率折算成真实货币再报。
- **密钥在地址里。** 接口的密钥是查询参数，所以这个地址和第 8 章 Telegram 的地址一样，不能出现在日志里。它放进密钥配置，衡量 ID 是普通的配置变量。

**报不上去就算了：**

```ts
try {
  const response = await fetch(url, { /* …… */ });
  // 这个接口只要收到请求就返回 2xx，内容不合法也不会报错。非 2xx 说明请求本身有问题，重试没有用。
  if (!response.ok) log.warn("analytics_report_failed", { orderId: event.orderId, status: response.status });
} catch (error) {
  log.warn("analytics_report_failed", { orderId: event.orderId, error });
}
```

这里不重试，也不让异常抛出去。补报失败不应该让这条支付通知被重新投递，更不应该影响发货。丢掉的只是分析平台上的一个数据点，而收入的真实数字在 D1 里。

要特别注意注释里说的那个行为：这个接口**内容错了也返回成功**。参数名拼错了、币种格式不对、标识不存在，它都照单全收然后悄悄丢弃。所以不能用"返回了 200"来判断接入是否正确。官方提供了一个专门的校验地址，把同样的请求发过去会返回具体的错误；接入时先用它验一遍，再去报表里确认事件真的出现了。

## 10.6 死信队列

第 6 章给对局记录的队列配了死信队列，当时说"里面的东西要有人看"。但只配置不消费的话，消息只是换了一个地方躺着，过了保留期照样被丢弃，而且没有任何人知道。

现在给死信队列也加上消费者：

```ts
/** 死信队列的消费者：记日志，存进表里，然后确认。到了这里的消息不会再自动重试。 */
export async function storeDeadLetters(batch: MessageBatch<unknown>, env: Env): Promise<void> {
  const insert = env.DB.prepare("INSERT INTO dead_letter (at, queue, message_id, body) VALUES (?, ?, ?, ?)");
  const now = Date.now();
  await env.DB.batch(
    batch.messages.map((message) => {
      const body = JSON.stringify(message.body) ?? "null";
      // 日志里只放开头一段，完整的内容在表里。
      log.error("dead_letter", { queue: batch.queue, messageId: message.id, preview: body.slice(0, 300) });
      return insert.bind(now, batch.queue, message.id, body);
    }),
  );
}
```

进了死信队列的消息做三件事：打一条 `error` 级别的日志（触发告警），完整地存进 D1 的一张表（保留证据），然后确认。

一条消息进死信队列，意味着它重试了好几次都处理不了。原因几乎总是两种之一：消息本身有问题（格式不对，引用了不存在的东西），或者处理它的代码有缺陷。两种都需要人来看。处理的流程是：看表里的内容，找出原因，修复代码，然后把表里的消息重新发回原来的队列。因为所有消费者都是可以重复处理的，重新投递是安全的。

入口的 `queue` 处理函数现在要分发三类队列。死信队列的名字以 `-dlq` 结尾，要最先判断，因为 `match-log-dlq` 同样以 `match-log` 开头：

```ts
async queue(batch: MessageBatch<unknown>, env: Env): Promise<void> {
  if (batch.queue.endsWith("-dlq")) {
    await storeDeadLetters(batch, env);
  } else if (batch.queue.startsWith("match-log")) {
    // ……
  } else {
    await handlePlayerEvents(batch as MessageBatch<PlayerEvent>, env);
  }
},
```

## 10.7 告警

有了日志和指标，还需要有东西在出问题时主动来找你。这一块同样不用自己搭：Cloudflare 的通知功能里有**监控规则**，它定期执行一条查询，结果满足条件时发出通知。示例项目里没有任何一行"发告警"的代码，告警全部是控制台里的配置。

### 监控规则能做什么

一条规则由三部分组成：查什么，怎么判断，通知谁。

**查什么。** 规则的查询跑在平台的 SQL 接口上，能查的数据集里，和我们有关的有三类：

| 数据集 | 内容 | 用来盯什么 |
|---|---|---|
| Workers 的日志（`logs.workersLogs`） | 10.2 节打的每一条日志 | 某个事件出现了，或者没出现 |
| Analytics Engine（`events.analyticsEngine.<数据集名>`） | 10.4 节打的每一个指标 | 业务指标偏离了正常范围 |
| 平台自己的数据集 | HTTP 请求、各产品的用量和状态 | 错误率、延迟、存储用量 |

可以用界面上的查询构造器，也可以直接写 SQL。自己写 SQL 时，查询要返回一个名为 `value` 的数值。

**怎么判断。** 有三种方式：

| 方式 | 判断的是什么 | 适合 |
|---|---|---|
| 阈值 | 结果和一个固定的数比较，支持大于、小于、等于等六种比较 | 绝大多数情况 |
| 异常检测 | 当前窗口和一段历史基线相比，偏离是否超出正常波动 | 说不出"多少算不正常"的指标 |
| SLO | 一短一长两个窗口里的成功比例是否都低于目标 | 关心成功率，又不想被短暂的抖动打扰 |

**通知谁。** 邮件（最多 20 个收件人）、Webhook（所有套餐可用，可以接到飞书、Slack 这类工具的机器人上）、PagerDuty（需要更高的套餐）。

规则最快每分钟执行一次。触发之后，问题持续期间默认每小时重复通知一次，可以调。

### 出现了不该出现的

第一类问题是"某件不该发生的事发生了"。做法是在日志上建阈值规则：某个事件名在一段时间内出现的次数，大于某个数。

这一章把所有需要告警的情况都整理成了固定的事件名，每一个对应一条规则：

| 事件 | 含义 | 建议的规则 |
|---|---|---|
| `payment_unfulfillable` | 收了钱但发不了货（第 8 章） | 15 分钟内次数大于 0 |
| `audit_mismatch` | 余额和流水对不上（第 8 章） | 15 分钟内次数大于 0 |
| `dead_letter` | 有消息进了死信队列 | 15 分钟内次数大于 0 |
| `job_failed` | 定时任务失败 | 15 分钟内次数大于 0 |
| `unhandled_error` | 没有被处理的异常 | 5 分钟内超过若干次 |
| `settle_failed` | 结算失败（会自动重试） | 15 分钟内超过若干次 |
| `leaderboard_write_failed` | 排行榜写入失败（会自动重试） | 15 分钟内超过若干次 |

前四个是"一次都不该有"的。后面几个偶尔出现是正常的（网络抖动、对象重启），持续出现才是问题，所以阈值设得高一些。

`audit_mismatch` 是怎么来的：玩家对象每天第一次登录时顺便对一次账（第 9 章清理流水的同一个位置）：

```ts
// 顺便对一次账。对不上说明有代码绕过流水改了余额，这是必须有人看的错误。
const audit = this.audit();
if (!audit.ok) log.error("audit_mismatch", { playerId: this.id, ...audit });
```

这把第 8 章的"三条规矩"变成了一个持续运行的检查。哪天有人写了一段直接改余额的代码，第二天这个告警就会响。

### 该出现的没有出现

第二类问题更隐蔽：系统没有报任何错，只是某件该做的事不再做了。定时任务是最典型的例子。它的配置被误删了，或者它在很靠前的地方就抛出了异常，结果是分数分布不再更新、未付款的订单没人核实、过期数据不再清理。没有任何一条错误日志，因为出错的代码根本没有运行。

对付这类问题要反过来：**不是等错误出现，而是确认成功一直在出现。** 定时任务每次成功跑完，打一条日志：

```ts
// 每次成功都留一条日志和一个数据点。平台的监控规则盯着这条日志：
// 一段时间内它出现的次数不够，说明任务不再发生了。所以事件名不能随便改。
log.info("job_done", { cron, ms, result });
metric(env, "job_run", [cron, "ok"], [ms]);
```

然后建一条用**小于**来比较的阈值规则：

| 规则 | 窗口 | 条件 |
|---|---|---|
| 5 分钟一次的任务还在跑 | 15 分钟 | `job_done`（且 `cron` 是那个表达式）的次数小于 1 |
| 每天一次的任务还在跑 | 25 小时 | `job_done`（且 `cron` 是那个表达式）的次数小于 1 |

窗口取任务间隔的两到三倍，偶尔晚一点不会误报。

这类检查有一个特点：它必须由被检查的系统**之外**的东西来执行。如果让自己的定时任务去检查自己的定时任务，那么定时任务整体不工作时，检查也不工作。监控规则是平台在它那一侧按时执行的，和你的 Worker 是否正常没有关系，正好满足这一点。

配置这类规则后要实际验证一次。官方文档有一句说明：查询没有返回任何行时不产生信号，这一轮不会触发。计数的查询在没有匹配的日志时返回的是一行 0 还是没有行，决定了这条规则在"一条日志都没有"的时候会不会响。验证的办法很简单：在预发环境把定时触发器停掉，等过了窗口，看通知有没有来。

同样的办法适用于任何"应该持续发生"的事：对局应该一直有人在打，付款应该每小时都有几笔。它们的次数突然掉到零，往往比任何错误日志都更早地说明出了大问题。

### 业务指标的告警

监控规则可以直接查 Analytics Engine，所以 10.4 节打的指标也能用来告警：

| 指标 | 规则 | 说明什么 |
|---|---|---|
| `outbox_flush` 的延迟 | 平均延迟大于几秒 | 通知送不出去，排行榜和好友关系在变旧 |
| `match_made` 里机器人的占比 | 用异常检测 | 匹配出了问题，或者某个地区的玩家突然少了 |
| `settle` 里重试的占比 | 用 SLO，目标 99% | 结算在大面积失败 |
| `job_run` 的耗时 | 大于正常值的几倍 | 清理任务快要做不完了 |

机器人占比这样的指标很难定一个固定的阈值：凌晨三点本来就高，晚高峰本来就低。这正是异常检测的用途，它比较的是"现在"和"之前一段时间"，而不是一个写死的数。

### 平台现成的通知

除了自己定义的规则，平台还有一批预先做好的通知类型，在同一个地方打开即可。和这本书的系统关系最大的是**用量通知**：某个产品的用量超过设定的值时提醒你。第 1 章算过成本，这里是它的保险：代码里一个死循环，或者一次被刷，都可能让某项用量在几小时内翻很多倍。给请求数、对象时长、队列操作、D1 读取行数各设一个比正常月用量高出一截的阈值。

### 少而准

告警的价值取决于它响的时候有没有人认真对待。几条经验：

- **每一条告警都要对应一个动作。** 收到它之后该做什么？答不上来的话，它不应该是告警，最多是一张图表。
- **宁可漏报，也不要一直误报。** 一天响十次的告警，第三天就没人看了，等它真的有事时也没人看。
- **日志里带够上下文。** 告警只说"某个事件出现了几次"，具体是哪一笔要回到日志里查。上面那些日志里带的 `orderId`、`matchId`、`playerId` 就是为这个准备的。
- **事件名是对外的约定。** 规则是按事件名配置的，代码里把 `job_done` 改个名字，对应的规则就再也不会触发，而且不会有任何提示。示例用测试把这些事件名固定了下来（10.10 节）。
- **采样会吃掉告警。** 如果开了日志采样，被采样掉的日志触发不了规则。低频而重要的事件所在的 Worker 不要采样。
- **新功能上线时把它的告警一起加上。** 写代码时最清楚这个功能"什么情况算坏了"，过后补很难补全。

## 10.8 追踪和导出

**追踪**回答的是"时间花在哪了"。一个请求进来，入口调用了玩家对象，玩家对象查了存储，入口又查了一次 D1，写了一次队列。哪一步慢？

Workers 的追踪是自动的。在配置里打开之后，不需要改代码，平台会记录一个请求经过的每一次对外调用：`fetch`、对象之间的 RPC、D1 的查询、KV 的读写、队列的发送，各自花了多久，并把它们连成一棵树。这对这套架构特别有用，因为一个请求往往要跨好几个对象，而单看任何一个对象的日志都看不出全貌。需要更细时，可以在自己的代码里手动加一段跨度，它会自动嵌进这棵树里。

**导出**解决的是保留期和工具的问题。平台自带的日志只留 7 天。要留得更久，或者想用团队已经在用的工具（Grafana、Honeycomb、Sentry 这一类），有三条路：

| 方式 | 是什么 | 适合 |
|---|---|---|
| OpenTelemetry 导出 | 平台按标准协议把日志和追踪发给外部的服务 | 已经有一套可观测工具。配置即可，不用写代码 |
| Logpush | 平台把日志批量推到 R2 或其他存储 | 要长期归档，以后再查 |
| Tail Worker | 另一个 Worker，在每次调用结束后收到它的日志和结果 | 要对日志做自定义的处理，比如过滤、脱敏之后再转发 |

官方文档的建议是：如果只是要把日志和错误发给现有的工具，优先用 OpenTelemetry 导出，不需要用 Tail Worker。

示例项目只打开了追踪，没有配置任何导出。

## 10.9 排查问题的路径

工具有了，实际遇到问题时怎么用。下面是几种常见情况的路径，用到的都是这本书里已经做好的东西。

**玩家报了一个错误，并且有请求编号。** 在日志里搜这个编号，直接得到那一次请求的 `unhandled_error` 日志，里面有路径、错误信息和调用栈。

**玩家说"我的金币不对"。** 打开管理后台的玩家页面（第 9 章），先看对账的结果。对得上，就把流水逐笔列出来给他解释，每一笔的编号都说明了来源（`match:` 是对局，`buy:` 是购买，`mail:` 是邮件）。对不上，这是一个代码缺陷，日志里应该已经有 `audit_mismatch`。

**玩家说"我充值没到账"。** 管理后台看这个玩家的订单状态。还是未付款的话，用后台的核实功能去支付平台查（第 9 章）；同时按订单号搜日志，看有没有 `payment_unfulfillable`。

**玩家说"这一局判得不对"。** 从 D1 的对局记录里取出这一局的操作日志（第 6 章），在本地用规则函数从头重放一遍。规则是确定性的，重放的结果就是服务端当时算出的结果。这是第 2 章坚持"规则是纯函数"在排查问题时的回报。

**"现在线上有点不对劲，但不知道是什么。"** 先看平台的指标：错误率和耗时有没有变化，从什么时候开始的，和哪一次发版的时间吻合。再看实时日志：

```bash
npx wrangler tail --status error --format json
```

`wrangler tail` 把线上正在产生的日志实时输出到终端。常用的筛选有按状态（`--status error`）、按日志里的文本（`--search`）、按请求方法（`--method`）。它有两个限制：一个 Worker 同时最多 10 个查看者；流量很大时会进入采样模式，丢掉一部分日志。所以它适合"看看现在在发生什么"，不适合用来确认"某件事有没有发生过"，后者要去查已经保存的日志。

**发版之后出了问题。** 先回滚（2.10 节），再查原因。回滚是一条命令、几秒钟的事，不要在线上有故障的时候调试。

这些路径有一个共同点：**每一步都依赖之前留下的东西。** 请求编号、流水的编号、对局的操作日志、固定的事件名，都是在写功能的时候顺手留下的。出了问题再想加，那一次的问题已经查不了了。

## 10.10 测试

这一章的代码大多是"顺便做的事"，测试的重点是确认它们确实做了，并且做的内容是对的。

日志用截住 `console` 的办法来检查：

```ts
function capture(level: "info" | "warn" | "error") {
  const entries: Record<string, unknown>[] = [];
  vi.spyOn(console, level).mockImplementation((entry: unknown) => {
    if (typeof entry === "object" && entry !== null) entries.push(entry as Record<string, unknown>);
  });
  return entries;
}
```

然后就可以断言"这个操作之后，出现了一条某某事件的日志，带着这些字段"。把日志当作被测试的输出，有一个额外的好处：告警依赖的事件名和字段被测试固定了下来，以后有人改了名字，测试会失败，而不是告警悄悄失效。

"该出现的没有出现"那条规则数的是 `job_done` 的条数，所以测试里除了确认成功时有这条日志，还确认了不该有的时候没有：

```ts
await runScheduled("1 2 3 4 5", Date.now(), env);
// 监控规则数的是 job_done 的条数，所以这里不能多出一条。
expect(infos.filter((e) => e.event === "job_done")).toHaveLength(1);
expect(errors.find((e) => e.event === "job_unknown")).toBeTruthy();
```

没有处理的异常的测试，顺带检查了细节没有泄露给客户端：

```ts
vi.stubGlobal("fetch", async () => {
  throw new Error("network down: secret-internal-detail");
});
// ……
expect(body.error).toBe("internal");
expect(JSON.stringify(body)).not.toContain("secret-internal-detail");
```

对账告警的测试需要制造一个"余额和流水对不上"的玩家。正常的代码路径造不出这种状态（这正是那些规矩的目的），所以用测试库提供的工具直接进到对象里改存储：

```ts
// 模拟一段绕过流水直接改余额的代码，并把"上次检查的时间"拨回去。
await runInDurableObject(stub, (_instance, state) => {
  state.storage.sql.exec("UPDATE profile SET coins = coins + 999, pruned_at = 0 WHERE id = 1");
});
```

补报付款的测试截住发往分析平台的请求，检查地址里的参数和请求体的内容；再让请求失败一次，确认支付记录照常写进了 D1，并且警告日志里没有密钥。

## 本章小结

- 日志、指标、埋点、追踪回答四类不同的问题，不要混用。同一件事往往要同时记日志和指标。
- 日志是对象：固定的事件名加上可筛选的字段。级别按"要不要叫醒人"来定。不记录秘密。
- 入口给每个请求一个编号，放进应答头和错误日志；兜住所有没被处理的异常，细节只进日志。
- 指标的字段是按位置对应的，定义集中在一处，只能在末尾追加。写指标不能影响业务。查询时永远带上采样间隔。
- 不要把玩家 ID 当指标的标签。
- 平台的指标说明系统是否健康，自己打的指标说明游戏是否正常，两种都要看。
- 埋点不自己建，用 Firebase：客户端直接上报，不经过后端。自己建只做完了存储这一半，报表才是难的那一半。
- 客户端的数据只用来看行为和趋势。收入、订单、对局这些会用来做决策的数字，以自己数据库里的为准。
- 付款由服务端补报到同一个数据流，带上客户端的标识才能接上漏斗。补报失败不重试，不影响业务。
- 分析平台的上报接口内容错了也返回成功，接入时要用它的校验地址验证。
- 死信队列要有消费者：记日志、存表、等人来看。修好之后可以重新投递。
- 日志的采集、存储、查询和告警都用平台自带的功能，自己只负责把日志打成合适的形状。
- 告警用平台的监控规则，不写在代码里。出现了不该出现的，对事件的次数设"大于"；该出现的没有出现，对成功日志的次数设"小于"。
- 监控规则也能查自己打的指标。说不出固定阈值的指标用异常检测，关心成功率的用 SLO。
- 打开用量通知，给成本上一道保险。
- 告警要少而准，每一条对应一个动作。事件名是对外的约定，用测试固定下来。
- 追踪是自动的，打开即可。日志要留得更久就导出去。
- 排查问题用的东西，都是写功能时顺手留下的。
