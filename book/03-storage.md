# 第 3 章　存储选型

Cloudflare 上能存数据的地方有好几种，选错了不会马上出问题，但会在数据量上来之后变成很难回头的债。这一章先把游戏里的数据分类，再说每一类该放在哪里，接着把 Durable Object 的模型和生命周期讲完整，然后解决两个绕不开的问题（另有一节专门讲怎么用 Hyperdrive 接上外部数据库）：一个对象内怎么保证一致，跨对象又怎么保证一致。

示例项目在这一章增加了玩家对象：每个玩家一份存档，对局结束后由房间给双方结算。代码在 [examples/server/src/player.ts](../examples/server/src/player.ts) 和 [room.ts](../examples/server/src/room.ts)。

## 3.1 先分数据，再选存储

选型的顺序不是"我有哪些存储可用"，而是"我有哪几类数据"。一个游戏后端里的数据大致分五类，它们对一致性、查询方式和容量的要求完全不同。

| 数据 | 例子 | 特点 | 放在哪里 |
|---|---|---|---|
| 玩家自己的 | 货币、背包、等级、战绩 | 只有这个玩家读写，必须强一致，不能丢 | 玩家对象的存储 |
| 一局之内的 | 房间状态、回合、手牌 | 生命周期短，读写频繁，只有房间里的人关心 | 房间对象的存储 |
| 需要跨玩家查询的 | 排行榜、订单、邀请关系、对局记录 | 要按各种条件检索，写入相对少 | D1 |
| 全局只读的 | 数值表、活动配置、开关 | 读极多写极少，晚几十秒生效可以接受 | KV |
| 只追加的大体量数据 | 长期归档的对局记录和日志 | 量大，几乎不改，很少在线查 | 经队列写入 R2 |

这张表背后的原则只有一条：**谁是这份数据唯一的写入者，就放在谁的对象里。** 玩家的金币只该由玩家对象来改，房间的回合只该由房间对象来推进。这样每份数据都有一个单线程的主人，并发问题从根上就不存在。只有那些天生要跨玩家检索的数据，才交给 D1。

第 1 章说过，这样分还顺带解决了容量问题：玩家数据按玩家分散在各自的对象里，D1 里只剩下增长缓慢的索引类数据。

## 3.2 几种存储的脾气

| | 对象自带的存储 | D1 | KV | R2 |
|---|---|---|---|---|
| 是什么 | 每个对象私有的 SQLite | 托管的 SQLite 数据库 | 全球分发的键值存储 | 对象存储 |
| 一致性 | 强一致，单线程 | 强一致，单线程，一次处理一条查询 | 最终一致，改动传播到其他节点可能要 60 秒或更久 | 强一致 |
| 查询能力 | 对象内 SQL | 全库 SQL | 只能按键读 | 只能按键读 |
| 容量上限 | 单个对象 10 GB，账号总量不限 | 单库 10 GB，不能提高 | 单个值 25 MiB | 单个对象 5 TiB |
| 写入限制 | 受单对象吞吐限制 | 受单线程限制 | 同一个键每秒 1 次 | 同一个键每秒 1 次 |
| 存储单价（每 GB 每月） | 0.20 美元 | 0.75 美元 | 0.50 美元 | 0.015 美元 |
| 适合 | 玩家数据、房间状态 | 跨玩家查询 | 配置、静态表 | 回放、归档、导出 |

容量和价格是付费版的数字，免费额度见[附录 A](../appendix/a-cloudflare-limits.md)。

还有三样东西不是存储，但经常和存储一起出现：

- **Queues**：消息队列。把"不必马上完成的写入"挪到后台，见 3.10 节。
- **Hyperdrive**：让 Workers 高效地连接外部的 Postgres 或 MySQL。它是 D1 装不下之后的出口，也是接入已有数据库的方式，见 3.11 节。
- **Analytics Engine**：面向指标和用量数据的时序存储，第 10 章再讲。

## 3.3 先认识 Durable Object

上面的表里，最重要的两类数据都放在"对象的存储"里。在讲怎么存之前，需要先把 Durable Object（下文简称 DO）本身讲清楚。第 1 章用三句话介绍过它，第 2 章直接用它写了房间，这一节补上完整的模型。后面所有关于存储和一致性的规矩，都是从这个模型推出来的。

### 它是什么

官方的定义是：DO 是一种特殊的 Worker，它把计算和存储结合在了一起。和普通 Worker 对比着看最清楚：

| | 普通 Worker | Durable Object |
|---|---|---|
| 状态 | 无状态，请求之间不共享任何东西 | 有状态，自带一份私有存储 |
| 实例 | 同一份代码在全球很多节点上同时运行 | 每个对象全球只有一个实例 |
| 位置 | 在离请求最近的节点执行 | 固定在一个位置，创建在离首次请求较近的地方 |
| 并发 | 多个请求并行处理 | 单线程，一次只执行一段代码 |
| 寻址 | 通过域名和路径 | 通过名字或 ID |

可以把一个 DO 类理解成一个"模板"，每个名字对应这个模板的一个实例。`Room` 类有成千上万个实例，每个房间号一个；`Player` 类的实例数等于玩家数。一个命名空间下能创建多少个对象没有硬性上限。

这正是它适合做游戏后端的原因。游戏里的大多数东西本来就是"一个个带状态的实体"：一个房间、一个玩家、一个公会、一张排行榜。DO 让你为每个实体写一段单线程的代码，不用考虑锁，也不用考虑这个实体此刻在哪台机器上。

### 怎么找到一个对象

配置文件里的绑定（比如 `ROOM`）代表一个命名空间。通过它用名字取对象：

```ts
const room = env.ROOM.getByName("room-123");
```

返回的不是对象本身，而是一个引用，对它的调用会被路由到对象所在的位置。全世界任何节点上用同一个名字取到的都是同一个对象。

除了按名字，还有另一种取法：

| 方式 | 写法 | 适用场景 |
|---|---|---|
| 按名字 | `getByName(name)`，或 `idFromName(name)` 再 `get(id)` | 名字本身有业务含义：房间号、玩家 ID。最常用 |
| 随机 ID | `newUniqueId()` 生成，`id.toString()` 存起来，之后用 `idFromString()` 还原 | 没有天然的名字，ID 由系统分配并保存在别处，比如匹配成功后新开的房间 |

`get` 和 `getByName` 都可以带一个位置提示参数，建议对象创建在哪个地区，只对首次创建生效。第 6 章按地区匹配时会用到。

关于寻址，有三件事必须知道：

**对象是访问时隐式创建的。** 没有"创建对象"这个接口，第一次访问一个名字，对象就存在了。这意味着任何能访问到入口的人，只要换一个名字，就能让你多出一个对象。所以名字必须在入口处校验格式，涉及玩家数据的访问必须先鉴权。第 2 章入口里的正则就是为此而设，第 4 章会补上鉴权。

**对象内部可以知道自己的名字。** 通过名字访问的对象，在内部可以用 `this.ctx.id.name` 读到自己的名字，不需要调用方另外传进来。用随机 ID 创建的对象没有名字。

**名字就是分片键。** 你怎么给对象命名，就决定了数据和负载怎么切分。按玩家 ID 命名，每个玩家的请求落在各自的对象上；如果图省事用了一个固定的名字（比如 `"global"`），全服的请求都会挤进同一个单线程对象。第 1 章说的"不留全局单点"，落到代码上就是命名时的这个选择。

### 一个类里能写什么

平台会在不同的事件发生时调用类上对应的方法：

| 方法 | 什么时候被调用 | 示例项目里的用途 |
|---|---|---|
| `constructor(ctx, env)` | 对象每次被唤醒时 | 玩家对象在这里做表结构迁移 |
| `fetch(request)` | 收到 HTTP 请求时 | 房间在这里接受 WebSocket 连接 |
| 公开的方法 | 被其他代码通过 RPC 调用时 | 玩家对象的 `getProfile`、`applyMatchResult` |
| `webSocketMessage(ws, message)` | 托管的连接收到消息时 | 房间处理准备和掷骰子 |
| `webSocketClose` / `webSocketError` | 连接关闭或出错时 | 房间处理玩家离开 |
| `alarm()` | 定时器到点时 | 房间重试没发完的结算 |

`fetch` 和 RPC 怎么选：需要处理原始的 HTTP 请求（比如升级成 WebSocket）时用 `fetch`，其余情况用 RPC。RPC 的调用有完整的类型，参数和返回值可以是任何能序列化的数据，对象里抛出的异常会传回调用方。

构造函数里拿到的 `ctx` 是对象访问平台能力的入口，常用的成员有这些：

| 成员 | 作用 |
|---|---|
| `ctx.id` | 对象自己的 ID，按名字访问时带有 `name` |
| `ctx.storage` | 私有存储，下一节详细讲 |
| `ctx.acceptWebSocket(ws, tags)` | 把连接交给平台托管，使对象可以休眠。可以给连接打标签，每个连接最多 10 个 |
| `ctx.getWebSockets(tag)` | 取出当前托管的连接，可按标签过滤 |
| `ctx.setWebSocketAutoResponse(pair)` | 设置自动应答，用于心跳，不会唤醒对象 |
| `ctx.blockConcurrencyWhile(fn)` | 在回调完成前不处理其他事件，只用于初始化 |
| `ctx.abort()` | 立即重置对象 |

一个对象最多可以托管 32,768 个 WebSocket 连接。这是硬上限，实际能承载多少还受单线程吞吐的限制。

### 生命周期

这是整个模型里最重要、也最容易被忽略的部分。一个对象并不是创建之后就一直在内存里，它在下面几个状态之间流转：

| 状态 | 含义 | 是否计时长费用 |
|---|---|---|
| 未激活 | 不在内存里。所有对象的初始状态 | 否 |
| 活跃 | 正在处理事件 | 是 |
| 空闲，可休眠 | 在内存里，没有事件，也没有任何东西阻止它休眠 | 否 |
| 空闲，不可休眠 | 在内存里，没有事件，但有东西让它无法休眠 | 是 |
| 已休眠 | 被移出内存，托管的 WebSocket 连接仍然保持 | 否 |

状态之间的转换有明确的时间：

- 处于"空闲，可休眠"状态满 **10 秒**，对象进入休眠。
- 处于"空闲，不可休眠"状态满 **70 到 140 秒**，对象被移出内存，回到未激活状态。此时如果有非托管的连接，会被断开。

下面任何一条成立，对象就无法休眠：

- 有还没触发的 `setTimeout` 或 `setInterval`。
- 有还没完成的输入输出，比如正在等待的网络请求，或者没结束的 `ctx.waitUntil()`。
- 使用了标准的 WebSocket 接口（`ws.accept()`），而不是 `ctx.acceptWebSocket()`。
- 有请求还在处理中。

此外，对外的网络请求、对其他对象的 RPC 调用、对外建立的连接，每一个都会让对象最长保持 15 分钟不被移出内存。

现在可以把第 1 章的那笔账说得更精确了。时长只在两种时候计算：对象在执行代码，或者对象空闲但不满足休眠的条件。一个空闲并且可以休眠的对象，即使还在内存里、还没到 10 秒，也不计时长。所以消息来得密不要紧，要紧的是两条消息之间有没有东西挡着它休眠。**10 秒决定的不是费用，而是多久会有一次冷启动**：间隔超过 10 秒，下一条消息到来时构造函数要重新执行一遍。

心跳是最容易破坏这一点的地方。很多客户端每隔几秒发一次心跳，如果由房间的代码来回应，对象就永远醒着。正确的做法是让平台代为应答：

```ts
constructor(ctx: DurableObjectState, env: Env) {
  super(ctx, env);
  // 心跳由平台直接应答，不会唤醒对象。
  ctx.setWebSocketAutoResponse(new WebSocketRequestResponsePair("ping", "pong"));
}
```

客户端发来的文本恰好是 `ping` 时，平台直接回 `pong`，对象的代码不会被执行，休眠也不会被打断。示例项目的房间已经加上了这一行。

### 被唤醒和被关闭时发生什么

**唤醒时，构造函数重新执行。** 无论是从未激活状态第一次被访问，还是从休眠中被一条消息唤醒，都会先跑一遍构造函数，然后才处理事件。所以构造函数要轻，只做必须的初始化。

**休眠或移出内存时，内存里的东西全部丢弃。** 类的成员变量、缓存、计数器，都没了。只有存储里的数据和托管连接上的附加数据能留下来。

**没有关闭前的回调。** 平台不提供"对象即将被关闭"的通知，不存在可以用来保存数据的析构函数。任何"退出时统一保存"的设计在这里都行不通。

**对象会因为你控制不了的原因被重启。** 发布新代码、平台升级运行时、平台调整对象的位置，都会让对象重启。正在运行的对象重启时，它身上的 WebSocket 连接会断开，正在处理的请求最多有 30 秒时间完成。

**同一个类的多个对象可能共用一个运行环境。** 所以不要用模块级的全局变量存放某个对象的状态，它可能被别的对象读到。

### 冷启动要注意什么

"冷启动"指的是对象不在内存里时，一个事件到来，平台要先把它拉起来才能处理。Workers 的运行环境本身启动很快，没有传统云函数那种启动虚拟机的开销，所以这里的冷启动成本主要不在平台，而在你自己的代码和对象所在的位置。

在回合制游戏里这不是偶发事件。对象空闲 10 秒就休眠，一个玩家思考时间稍长的房间，可能每个回合都要被唤醒一次。冷启动路径上的每一毫秒，都会乘以这个频率。

先分清三种情况，它们的成本不一样：

| 情况 | 发生了什么 | 额外开销 |
|---|---|---|
| 第一次访问一个名字 | 平台要确认全球没有同名对象在别处运行，再创建它 | 这次全球检查最多需要几百毫秒，之后位置信息会被缓存 |
| 唤醒未激活的对象 | 对象身上没有任何连接，由一次新的请求拉起，执行构造函数 | 构造函数的耗时；如果是 WebSocket，还有建立连接的耗时 |
| 唤醒休眠的对象 | 执行构造函数，连接还在 | 构造函数的耗时 |

下面是要注意的八件事。

**一、模块顶层的代码要轻。** 处理函数之外的顶层代码必须在 1 秒内解析并执行完，否则发布时就会被拒绝。即使没有超限，这部分时间也会计入每一次冷启动。不要在顶层解析大型配置、构建查找表或初始化重量级的库，把它们挪到第一次用到的地方。

**二、构造函数要轻。** 它在每次唤醒时都执行。官方对使用休眠的对象的建议很直接：尽量减少构造函数里的工作。示例项目里，房间的构造函数只设置了心跳应答，玩家的构造函数只做一次版本号查询，迁移只在版本落后时才真正执行。

需要在处理请求之前完成异步初始化时，用 `blockConcurrencyWhile` 包住：

```ts
constructor(ctx: DurableObjectState, env: Env) {
  super(ctx, env);
  ctx.blockConcurrencyWhile(async () => {
    this.config = (await ctx.storage.get<Config>("config")) ?? DEFAULT_CONFIG;
  });
}
```

它保证回调完成之前不处理任何事件。使用时守住两条：回调里只做本地存储的读写，不要发网络请求，否则这个对象的所有请求都会被外部服务的延迟卡住；回调抛出异常或超时会导致对象被重置。同步的 SQL 调用不需要它，直接写在构造函数里即可。

**三、按需加载，不要一次读全。** 不是每个事件都需要全部数据。玩家对象被唤醒可能只是为了查一下金币，没必要把流水表也读进内存。把读取放到真正用到的方法里。

**四、连接的身份放在附加数据里。** 休眠唤醒后内存是空的，但 `serializeAttachment` 存下的数据还在连接上。把"这个连接是谁"放在这里，唤醒后处理消息就不需要先查一次存储。上限是 16,384 字节，更大的数据放存储，附加数据里只留一个键。

**五、留意第一次访问的那几百毫秒。** 按名字第一次访问一个对象时的全球检查，会让"创建房间"和"新玩家首次登录"比平时慢一截。有两个办法：

- 用 `newUniqueId()` 创建的对象可以跳过这次检查。由服务端分配房间号的场景（比如匹配成功后开房）适合用它，把生成的 ID 发给客户端即可。
- 提前访问一次。匹配成功时由服务端先调用一下房间对象，等玩家的连接到达时它已经就绪。

**六、谁第一个访问，决定对象在哪里。** 对象创建在离首次请求较近的位置，之后不会迁移，远处的调用者每次请求都要被转发过去。容易踩的坑是：如果玩家对象是被一个后台任务第一次访问的（比如队列的消费者批量发奖时碰到了一个新玩家），它就会被创建在那个任务运行的地方，而不是玩家身边，这个玩家以后的每次请求都要绕路。

所以要让玩家自己的请求成为第一次访问；做不到时，在首次访问时传入位置提示。位置提示只对第一次生效，并且是尽力而为。另外，南美、非洲和中东这几个提示区域，对象会被创建在邻近的受支持地点，而不一定在区域之内，面向这些地区的游戏要实测延迟。

**七、发版等于一次批量冷启动。** 发布新代码后，对象会陆续切换到新版本。这个过程有几个细节：

- 正在运行的对象被强制更新时，它身上的 WebSocket 连接会断开。
- 处于休眠状态的对象，它的托管连接保持不变，下次被唤醒时直接运行新代码。这是使用托管连接的又一个好处。
- 切换期间会出现新旧版本并存：新版本的入口代码可能调用到一个还在运行旧版本的对象。所以 RPC 方法的签名要保持兼容，只加新方法、只加可选参数，不要改已有方法的含义。
- 大量连接同时断开，客户端会同时重连，形成一波集中的冷启动。客户端的重连要用指数退避并加上随机抖动，发版要避开在线高峰。

**八、调用方要准备好对象不可用。** 对象重启、过载、所在节点故障时，调用它的代码会收到异常。异常上有几个属性用来判断怎么处理：

| 属性 | 含义 | 怎么办 |
|---|---|---|
| `retryable` 为真 | 暂时性错误 | 操作是幂等的才重试，并使用指数退避 |
| `overloaded` 为真 | 对象过载 | 不要重试，重试只会让过载更严重 |
| `remote` 为真 | 异常来自对象里的代码 | 按业务错误处理 |

出错之后，原来的对象引用可能已经处于损坏状态，重试前要重新获取一次。还要注意平台自己也会重试：获取引用时默认最多重试 4 次，加上你自己的重试，同一个操作实际可能被执行很多次。这是 3.7 节要求所有跨对象操作都带操作编号的另一个原因。

最后说一件不要做的事：**不要为了避免冷启动而让对象保持常驻。** 用 `setInterval` 或者自己应答的心跳把对象一直留在内存里，等于用全额的时长费用去换几毫秒。只有极少数全服共用的热点对象值得这样做，而且它们通常本来就一直有流量。

想知道冷启动在你的游戏里实际花了多少时间，可以量一下构造函数执行了多久，作为一个指标上报。第 10 章会把它做成固定的指标。

### 从模型推出的规矩

把上面的事实翻译成写代码时要遵守的规矩，就是下面这几条。后面几节会逐条展开，这里先列在一起：

1. **内存只是缓存，存储才是数据。** 任何需要保留的东西，在改动发生的那一刻就写入存储，不要攒着。
2. **构造函数和模块顶层的代码都要轻。** 它们在每次冷启动时都会执行，并且挡在第一个事件前面。
3. **不要用 `setInterval`，定时任务用定时器接口。** 前者让对象无法休眠，后者不会。
4. **连接用 `ctx.acceptWebSocket` 托管，心跳用自动应答。**
5. **客户端必须会重连。** 发版和平台维护都会断开连接，这是常态，不是故障。
6. **对象的名字要校验，访问要鉴权。**
7. **凡是全服只有一个的东西，命名时就要想好怎么分片。**
8. **让玩家自己的请求成为对玩家对象的第一次访问，** 否则对象会建在离玩家很远的地方。
9. **RPC 方法的签名保持兼容，调用方要处理对象暂时不可用。** 发版期间新旧版本会并存。

## 3.4 对象自带的存储：两套接口，各有用处

每个使用 SQLite 存储的对象都有一份私有的数据库。访问它有两套接口，示例项目各用了一次。

### 键值接口：整块存取

房间的状态是一整个对象，每次都整体读出、整体写回，用键值接口最省事：

```ts
private async load(): Promise<RoomState> {
  return (await this.ctx.storage.get<RoomState>(STATE_KEY)) ?? initialState();
}

private async save(state: RoomState): Promise<void> {
  await this.ctx.storage.put(STATE_KEY, state);
}
```

值可以是任意能被结构化克隆的数据，不需要自己序列化。`put` 也可以一次传入一个对象，同时写多个键，一次调用最多 128 个。

### SQL 接口：按行读写

玩家数据是结构化的，而且各个字段会被分别修改，适合用表来存：

```ts
private readProfile(): Profile {
  const row = this.ctx.storage.sql.exec("SELECT coins, wins, games FROM profile WHERE id = 1").one();
  return { coins: Number(row.coins), wins: Number(row.wins), games: Number(row.games) };
}
```

`sql.exec` 是同步调用，直接返回一个游标，不需要 `await`。因为数据库和代码在同一台机器的同一个线程里，一次查询的开销接近一次函数调用。常用的方法有：

- `toArray()`：取出全部行。
- `one()`：取出唯一的一行，结果不是恰好一行时抛出异常。
- 游标本身可以用 `for...of` 遍历。
- `rowsRead` 和 `rowsWritten`：这次查询读写了多少行，正好对应计费单位。

参数一律用 `?` 占位再传入，不要拼接字符串。

有一个容易忽略的细节：SQLite 的整数是 64 位的，而 JavaScript 的数字只能精确表示到 2 的 53 次方左右。金币这类数值正常情况下到不了这个量级，但如果你的游戏有指数增长的数值（放置类游戏很常见），要提前想好用字符串还是别的方式存。

### 怎么选

整块读、整块写、结构经常变的数据用键值接口，比如房间状态。需要部分更新、需要条件查询、行数会增长的数据用 SQL，比如玩家的资产和流水。一个对象里两者可以混用，它们存在同一个数据库里。

## 3.5 表结构迁移

传统数据库只有一个，发版前跑一次迁移脚本就行。这里的情况不同：每个玩家一个数据库，可能有几百万个，其中绝大多数此刻在休眠，没法也没必要一次迁移完。

做法是让每个对象在被唤醒时自己检查、自己升级：

```ts
const MIGRATIONS: string[] = [
  `CREATE TABLE profile (
     id INTEGER PRIMARY KEY CHECK (id = 1),
     coins INTEGER NOT NULL DEFAULT 0,
     wins INTEGER NOT NULL DEFAULT 0,
     games INTEGER NOT NULL DEFAULT 0
   );
   INSERT INTO profile (id) VALUES (1);`,
  `CREATE TABLE ledger (
     op_id TEXT PRIMARY KEY,
     kind TEXT NOT NULL,
     coins INTEGER NOT NULL,
     created_at INTEGER NOT NULL
   );`,
];

function migrate(storage: DurableObjectStorage): void {
  const sql = storage.sql;
  sql.exec("CREATE TABLE IF NOT EXISTS schema_version (version INTEGER NOT NULL)");
  const current = sql.exec("SELECT version FROM schema_version").toArray()[0];
  const applied = current ? Number(current.version) : 0;
  if (applied >= MIGRATIONS.length) return;

  storage.transactionSync(() => {
    for (const statement of MIGRATIONS.slice(applied)) {
      sql.exec(statement);
    }
    sql.exec("DELETE FROM schema_version");
    sql.exec("INSERT INTO schema_version (version) VALUES (?)", MIGRATIONS.length);
  });
}
```

`migrate` 在对象的构造函数里调用。构造函数在对象每次被唤醒时执行一次，而 SQL 是同步的，所以迁移一定在处理任何请求之前完成。版本号存在自己建的表里，因为对象的 SQLite 不支持 `PRAGMA user_version`。

使用这种方式要守三条规矩：

1. **迁移列表只能在末尾追加。** 已经发布的条目绝不能改。线上有的对象执行过它，有的还没有，改了就会出现两种不同的结构。
2. **每条迁移要快。** 它挡在这个玩家的第一个请求前面。给一个玩家的几百行数据加列没问题，需要重算大量数据的迁移应该拆成后台任务。
3. **新结构要让旧代码也能用。** 这是第 2 章留下的问题：回滚只换代码，不动数据。如果新版本改了表结构然后被回滚，旧代码面对的是新结构。

第三条具体怎么做：

| 想做的改动 | 安全的做法 |
|---|---|
| 加一个字段 | 直接加，带默认值。旧代码不认识它，也不受影响 |
| 删一个字段 | 分两次发布：先发布不再读写它的代码，确认稳定后再发布删除 |
| 改字段的含义或单位 | 不要原地改。加一个新字段，新代码两个都写，稳定后再停用旧字段 |
| 改字段的类型 | 同上，当作"加新字段、停旧字段"处理 |

键值接口存的整块数据同理。给 `RoomState` 加字段时，读取处要能处理旧数据里没有这个字段的情况；更稳妥的办法是在数据里带一个版本号，读取时按版本转换。

## 3.6 对象内的一致性

对象是单线程的，但"单线程"不等于"不会交叉执行"。一个处理函数执行到 `await` 时让出控制权，另一个请求有可能插进来。平台为此提供了两道保护，弄清楚它们保护什么、不保护什么，是写对房间和玩家逻辑的前提。

**输入闸门。** 当代码在等待存储操作时，新的事件不会被送进来。所以下面这段"读、改、写"是安全的，两次存储操作之间不会有别的消息插入：

```ts
const before = await this.load();
const result = applyAction(before, action);
await this.commit(before, result.state);
```

**输出闸门。** 对外发出的消息会被扣住，直到已经发起的存储写入确认落盘。所以不会出现"客户端已经收到新状态，但数据其实没存上"的情况。

**不受保护的情况：等待外部调用。** 一旦 `await` 的是一个网络请求，或者对另一个对象的调用，输入闸门就打开了，别的消息可以插进来执行。由此得出本书在对象里写代码的第一条规矩：

> **读、改、写之间不要等待任何外部调用。** 需要调用外部时，先把自己的状态改完存好，再去调用；调用返回后如果还要改状态，重新读一遍，不要用调用之前读到的旧值。

### 多个写入的原子性

连续的多个写入，只要中间没有 `await`，就会被自动合并成一次原子提交。要显式表达"这几步必须一起成功"，SQL 这边用 `transactionSync`：

```ts
this.ctx.storage.transactionSync(() => {
  const seen = sql.exec("SELECT 1 FROM ledger WHERE op_id = ?", opId).toArray();
  if (seen.length > 0) return;
  sql.exec("INSERT INTO ledger (op_id, kind, coins, created_at) VALUES (?, 'match', ?, ?)", opId, result.coins, Date.now());
  sql.exec("UPDATE profile SET coins = coins + ?, wins = wins + ?, games = games + 1 WHERE id = 1", result.coins, result.won ? 1 : 0);
});
```

回调里抛出异常时，里面所有的写入一起回滚。回调必须是同步函数。不能自己在 `exec` 里写 `BEGIN TRANSACTION`，平台不允许。

键值接口这边，把要一起写的键放进同一次 `put`：

```ts
await this.ctx.storage.put({ [STATE_KEY]: after, [PENDING_KEY]: pending });
```

## 3.7 跨对象的一致性

对局结束时，房间要给每个玩家记一笔：胜者加金币，所有人的场次加一。房间是一个对象，每个玩家各是一个对象，而平台没有跨对象的事务。如果房间刚给第一个玩家记完就出了故障，第二个玩家就漏了；如果简单地重试，第一个玩家又会被记两次。

这是游戏后端里最经典的问题，支付发货、邮件领奖、邀请奖励都是同一个结构。解法由三部分组成。

**第一，先在自己这里记下"要做什么"。** 房间在保存"对局已结束"的同一次写入里，存下一条待结算记录：

```ts
private async commit(before: RoomState, after: RoomState): Promise<void> {
  if (before.phase === "playing" && after.phase === "finished") {
    const pending: PendingSettlement = {
      matchId: crypto.randomUUID(),
      results: after.players.map((p) => ({
        playerId: p.id,
        won: p.id === after.winner,
        coins: p.id === after.winner ? WIN_COINS : 0,
      })),
    };
    await this.ctx.storage.put({ [STATE_KEY]: after, [PENDING_KEY]: pending });
    return;
  }
  await this.save(after);
}
```

状态和待结算记录在一次 `put` 里，要么都写入，要么都没写入。不会出现"对局结束了但没人记得要结算"。

**第二，接收方按操作编号去重。** 玩家对象把每一笔变动记进流水表，操作编号是主键。同一个编号再来一次，直接跳过。上一节那段 `transactionSync` 做的就是这件事：查重、记流水、改余额，三步在一个事务里。

**第三，发送方反复尝试，直到全部成功。**

```ts
private async settle(): Promise<void> {
  const pending = await this.ctx.storage.get<PendingSettlement>(PENDING_KEY);
  if (!pending) return;
  try {
    for (const r of pending.results) {
      await this.env.PLAYER.getByName(r.playerId).applyMatchResult(pending.matchId, {
        won: r.won,
        coins: r.coins,
      });
    }
    await this.ctx.storage.delete(PENDING_KEY);
  } catch (error) {
    console.error("结算失败，稍后重试", pending.matchId, error);
    await this.ctx.storage.setAlarm(Date.now() + RETRY_DELAY_MS);
  }
}

async alarm(): Promise<void> {
  await this.settle();
}
```

全部成功才删除待结算记录。中途任何一步失败，记录还在，定时器过几秒再触发一次，从头再发一遍。已经记过的玩家会因为去重而跳过，没记上的补上。

这里对玩家对象的调用用的是 RPC：玩家类上的公开方法可以通过对象的引用直接调用，参数和返回值有完整的类型。

三部分合起来，得到的保证是：**名单上每个玩家的结算最终会发生，而且只发生一次。**（这份名单本身有一个遗漏：它只取了对局结束时还在座位上的人，中途离开的人不在里面。第 5 章 5.7 节会发现并修正。） 它不是即时的，玩家可能晚几秒才看到金币到账，但不会丢，也不会重复。本书后面凡是涉及"一个对象要让另一个对象改数据"的地方，用的都是这个结构，第 8 章的支付发货只是把房间换成了订单。

关于定时器，有几个事实需要知道：

- 每个对象同一时刻只能有一个定时器，再次设置会覆盖之前的。一个对象里有多种定时需求时，要自己维护一张待办表，定时器只指向最近的那一项。
- 定时器保证至少触发一次。处理函数抛出异常时平台会自动重试，从 2 秒开始指数退避，最多 6 次。所以示例里选择自己捕获异常并重新设置定时器，这样可以一直重试下去。
- 触发时间不是精确的，可能有延迟。

流水表会一直增长。去重只需要覆盖"可能发生重试"的时间窗口，所以可以定期删掉比如 30 天以前的记录。示例项目暂时没有做清理，第 8 章给出清理的方法，第 9 章安排它什么时候执行。

## 3.8 要不要在内存里缓存

第 2 章的房间每次都从存储读状态，没有缓存。这是有意的，现在可以把理由说完整。

对象的存储是本地的，一次读取的开销很小。而缓存带来两个风险：一是对象休眠或被移出内存后内存清空，任何只存在于内存里的修改都会丢；二是内存和存储一旦不一致，问题很难复现。所以默认的建议是：**不缓存，直到你测出来存储读取确实是瓶颈。**

真要缓存，遵守下面的写法：

- 把内存当作存储的副本，绝不当作数据的来源。
- 修改时先写存储，再更新内存。两步之间不要有 `await` 外部调用。
- 加载放在构造函数里，或者在第一次使用时惰性加载。需要异步加载时用 `blockConcurrencyWhile` 包住，保证加载完成之前不处理请求。它只用于初始化，不要在日常的请求处理里使用。
- 不要用全局变量存状态，多个对象可能共用同一个运行环境。

另外一条和成本有关：**存储写入按行计费**，付费版每月包含 5,000 万行，超出部分每百万行 1 美元。示例里的房间每处理一条消息就保存一次状态。按第 1 章的场景估算，每月 9,000 万条消息就是至少 9,000 万行写入，超出的 4,000 万行是 40 美元。第 12 章对着最终的代码数过，实际每一步写的不止一行。这又一次印证了那条原则：消息节奏决定成本。减少写入的办法不是攒着不存（那样会丢数据），而是减少需要服务端处理的消息。

## 3.9 D1：需要跨玩家查询的数据

对象存储回答不了"所有对象里满足某个条件的有哪些"。比如查某个玩家邀请了谁、列出最近的订单、按分数排出前一百名，这类需求放在 D1 里。

D1 也是 SQLite，通过绑定访问：

```ts
const row = await env.DB.prepare("SELECT inviter FROM invite WHERE invitee = ?")
  .bind(playerId)
  .first<{ inviter: string }>();

await env.DB.batch([
  env.DB.prepare("INSERT INTO orders (id, player_id, amount) VALUES (?, ?, ?)").bind(id, playerId, amount),
  env.DB.prepare("UPDATE order_stats SET total = total + ? WHERE day = ?").bind(amount, day),
]);
```

`first()` 取第一行，没有则返回 `null`；`all()` 取全部；`run()` 用于写入。`batch` 里的语句作为一个事务执行，其中一条失败则整体回滚。D1 没有交互式事务，不能在"开始"和"提交"之间穿插应用代码的判断，需要原子性的操作要设计成一次 `batch` 能表达的形式。

使用 D1 时要记住它的三个特性：

**一个库同一时刻只处理一条查询。** 官方文档明确说每个 D1 数据库是单线程的。它的吞吐取决于每条查询有多快，所以索引要建好，查询要短，不要在线上库里跑分析型的大查询。

**读多写少时可以开读副本。** 通过会话接口 `withSession()` 使用。它保证同一个会话内读到的数据不会倒退，适合"刚写完马上要读到"的场景。

**它是索引，不是玩家数据的源头。** 玩家有多少金币，以玩家对象为准。D1 里即使存了一份用于排序或统计，也只是副本，允许有延迟，由队列异步同步过去。不要让一次操作同时依赖"对象里的值"和"D1 里的值"都是最新的。

示例项目在本章还没有用到 D1，第 6 章保存对局记录时引入。

## 3.10 KV、R2 和 Queues

### KV：配置和静态表

KV 的特点是读得快、全球分发，代价是最终一致：一次写入传播到其他节点可能需要 60 秒甚至更久，同一个键每秒只能写一次。免费版每天只有 1,000 次写入。

所以它只适合读极多、写极少、晚一点生效也无所谓的数据：数值表、活动开关、公告内容。**不要把任何余额、计数器、库存放进 KV**，两个节点同时读到旧值再各自写回，结果就错了。

第 9 章做远程配置时会用到它。

### R2：大对象和归档

R2 是对象存储，每 GB 每月 0.015 美元，流量不收费。适合放体积大、写入后基本不变的东西：对局回放、日志归档、数据导出、客户端资源。

读写按操作次数计费，写入类操作每百万次 4.50 美元，读取类每百万次 0.36 美元。所以它不适合存大量很小的对象：把一万条记录写成一万个文件，远不如攒成一个文件再写。

### Queues：把写入挪到后台

队列本身不是存储，但它决定了很多数据怎么落地。典型的用法是：请求处理时只往队列里丢一条消息就返回，由消费者在后台批量写入 D1 或 R2。玩家感受到的延迟更低，后端的写入也被削平了。

三个要点：

- **至少投递一次。** 同一条消息可能被消费多次，所以消费者必须是幂等的，做法和 3.7 节一样，带上操作编号。
- 单条消息上限 128 KB，一批最多 100 条。
- 付费版每月包含 100 万次操作，超出每百万次 0.40 美元。一条消息从写入到读取再到删除通常算 3 次操作。

第 6 章的对局记录和第 7 章的玩家通知都会用到它。

## 3.11 Hyperdrive：接上外部数据库

前面几种存储都在 Cloudflare 内部。但有些情况下你需要一个传统的关系型数据库：

- D1 的 10 GB 单库上限不够用，拆库的代价又太高。
- 公司已经有 Postgres 或 MySQL，账号、订单、中台数据都在里面，新游戏要接进去。
- 需要 D1 给不了的能力：交互式事务、大表上的复杂查询、成熟的分析和报表工具。

Hyperdrive 就是为这种情况准备的。它不是数据库，而是架在 Workers 和你的数据库之间的一层连接服务。支持 PostgreSQL（9.0 到 18.x）和 MySQL（5.7 到 8.x，包括 MariaDB），自建和主流的托管服务都可以，不支持 SQL Server 和 MongoDB。它包含在免费版和付费版里，不单独收费；免费版每天限 10 万次查询。

### 为什么不能直接连

Workers 的代码可能在全球任何一个节点上执行，每个请求都是独立的，没有常驻进程来维持连接池。如果在 Worker 里直接连数据库，会遇到两个问题：

- **每个请求都要重新建立连接。** 建立一条数据库连接需要多次往返（建立 TCP、协商 TLS、认证），玩家在亚洲、数据库在美国时，光握手就要花掉几百毫秒。
- **连接数失控。** 流量一高，成千上万个请求各开一条连接，数据库的连接数上限很快被打满。

Hyperdrive 做了三件事来解决：

1. **在 Worker 附近完成连接的建立。** 握手发生在边缘节点和 Hyperdrive 之间，不用跨洲往返。
2. **在数据库附近维护连接池。** 到数据库的真实连接是复用的，数量受控。
3. **缓存读查询的结果。** 默认开启。

### 接入

先创建一个配置，把数据库的连接串交给 Hyperdrive 保管：

```bash
npx wrangler hyperdrive create game-db --connection-string="postgres://user:password@db.example.com:5432/game"
```

然后在配置文件里绑定它：

```jsonc
"hyperdrive": [
  { "binding": "HYPERDRIVE", "id": "<上一步返回的配置 ID>" }
]
```

代码里用普通的数据库驱动，只是连接串换成绑定提供的：

```ts
import { Client } from "pg";

const client = new Client({ connectionString: env.HYPERDRIVE.connectionString });
await client.connect();
const { rows } = await client.query("SELECT id, status FROM orders WHERE player_id = $1", [playerId]);
```

每个请求新建一个客户端即可，真正的连接池由 Hyperdrive 维护。几个容易卡住的细节：

- 驱动依赖 Node.js 兼容层。兼容日期在 2026-08-04 之后的项目默认已开启，更早的需要在配置里加上 `nodejs_compat` 标志。
- 驱动有最低版本要求：`pg` 8.16.3、`postgres` 3.4.5、`mysql2` 3.13.0。
- 使用 `mysql2` 时必须传 `disableEval: true`。
- 使用 Postgres.js 时不要设置 `prepare: false`，官方说明这会导致查询间歇性挂起或失败。

### 连接数据库的三种网络方式

数据库在哪里、是否暴露在公网，决定了 Hyperdrive 怎么连过去。

| 方式 | 数据库的状态 | 怎么配置 | 适用 |
|---|---|---|---|
| 公网直连 | 有公网地址 | 创建配置时直接给连接串。可以在数据库的防火墙上只放行 Cloudflare 的 IP 段 | 托管数据库服务，起步最快 |
| Tunnel 加 Access | 在私有网络里，不暴露公网 | 在内网运行 `cloudflared` 建立隧道，用 Access 的服务令牌做认证，创建配置时传入隧道的主机名和令牌 | 自建数据库，或安全要求不允许公网暴露 |
| Workers VPC | 在私有网络里 | 官方目前推荐的私网连接方式，不需要配置 Access 应用和服务令牌 | 新项目的私网连接 |

三种方式都要求数据库启用 TLS。Postgres 支持的校验级别是 `require`（默认）、`verify-ca` 和 `verify-full`，后两种需要上传数据库的 CA 证书；也支持客户端证书做双向认证。不加密的连接不被支持。

存放玩家订单和账号的库，建议至少用 `verify-full`，并且不要走"公网全开"。

### 本地开发时怎么连

本地开发有两种模式，行为差别很大，要分清楚。

| 模式 | Worker 在哪里运行 | 连的是哪个数据库 | 连接池和缓存 |
|---|---|---|---|
| `wrangler dev`（默认，本地模式） | 你的电脑上 | 你指定的本地连接串，直连 | 都不生效 |
| `wrangler dev --remote`（远程模式） | Cloudflare 上 | 已部署的 Hyperdrive 配置指向的库 | 都生效 |

**本地模式**下，Hyperdrive 被完全绕过，Worker 直接连到你给的数据库。连接串有两种给法：

```jsonc
"hyperdrive": [
  {
    "binding": "HYPERDRIVE",
    "id": "<配置 ID>",
    "localConnectionString": "postgres://user:password@localhost:5432/game"
  }
]
```

或者用环境变量，变量名的最后一段是绑定名：

```bash
export CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_HYPERDRIVE="postgres://user:password@localhost:5432/game"
```

两者都设置时环境变量优先。连接串里有密码，更稳妥的做法是用环境变量，不要把它写进会提交的配置文件。

本地模式有一个需要记住的盲区：**因为缓存和连接池都不生效，由它们引起的问题在本地永远复现不出来。** 读到旧数据、会话状态丢失、连接池耗尽，这些都只会出现在线上或远程模式里。

**远程模式**下一切和线上一致，适合验证上面那些问题。但它用的是已部署的配置，如果那个配置指向正式库，你在本地的每一次写入都会落到真实数据上。所以要给预发环境建一个单独的 Hyperdrive 配置，指向预发库，远程调试只用它。

### 让 Worker 靠近数据库运行

Hyperdrive 省掉了建立连接的往返，但每一条查询本身仍然要从 Worker 所在的节点走到数据库。官方给的参考数字是：Worker 离数据库远时每条查询 20 到 30 毫秒，放在附近时 1 到 3 毫秒。

如果一个请求里只查一次，这点延迟无所谓。但如果要顺序查五六次（先查账号，再查订单，再写流水），就是五六次跨洲往返。这时应该反过来想：让玩家的请求多走一段路到数据库附近，在那里把几条查询一次做完。

这由 Worker 的 placement 配置控制，有下面几种模式：

| 模式 | 配置 | Worker 在哪里运行 |
|---|---|---|
| 默认 | 不配置 | 离玩家最近的节点 |
| 智能 | `"placement": { "mode": "smart" }` | 平台分析这个 Worker 访问的后端之后自动选择 |
| 指定云区域 | `"placement": { "region": "aws:us-east-1" }` | 靠近指定的云厂商区域，也支持 `gcp:` 和 `azure:` 前缀 |
| 指定主机 | `"placement": { "host": "db.example.com:5432" }` | 靠近指定的地址，通过 TCP 探测确定，目前是实验性功能 |

几种模式互斥，只能选一个。使用时要知道这些：

- 智能模式在部署后最长需要 15 分钟来分析，期间仍按默认方式运行。数据库位置明确时，直接指定区域更可控。
- **判断标准是一个请求里有几条顺序查询。** 官方的说法很明确：多条顺序查询就用 placement；只有一条查询时，它不会改善端到端的延迟。
- 它只影响 `fetch` 处理函数，不影响 RPC 方法。静态资源仍然从离玩家最近的节点返回。
- 它管不到 Durable Object。对象的位置按 3.3 节讲的规则决定，和这个配置无关。

最后一点对游戏后端的结构有直接影响。placement 是整个 Worker 的属性，而游戏的大部分请求（进房间、连 WebSocket）应该留在玩家附近。所以不要给游戏的主入口开 placement。更合适的做法是把访问外部数据库的那部分接口拆成一个单独的 Worker，只给它配置 placement，主入口在需要时通过服务绑定去调用它。这是本书建议的结构，不是官方文档的原话。

### 连接池的限制

Hyperdrive 的连接池工作在事务模式：一条连接只在一个事务期间归你使用，事务结束就还给池子。这意味着凡是依赖"会话"的功能都不可靠：

| 功能 | 是否可用 |
|---|---|
| 普通查询、事务 | 可用 |
| 驱动层面的预处理语句（`pg`、Postgres.js） | 可用 |
| 事务内的 `SET`，事务级咨询锁 | 可用，连接归还时重置 |
| 会话级咨询锁 | 不可用。锁可能留在被归还的连接上 |
| `LISTEN` / `NOTIFY` | 不可用 |
| SQL 层面的 `PREPARE` / `EXECUTE` | 不可用 |
| MySQL 的 `USE`、一次执行多条语句 | 不可用 |

到数据库的连接数有上限：免费版约 20 条，付费版约 100 条，可以调整，最少 5 条。这是所有请求共用的。

对游戏来说，这带来一条硬性要求：**事务必须短。** 一个事务占着一条连接，事务没结束，别的请求就用不了它。活动开启的瞬间如果有大量长事务，池子耗尽后的请求会报"无法从池中获取连接"。具体做法是：事务里只放数据库操作，不要在事务中间调用外部接口或等待其他对象；单条语句的执行上限是 60 秒，但实际应该控制在毫秒级。

### 查询缓存的坑

读查询的结果默认会被缓存 60 秒，过期后还有 15 秒的窗口会先返回旧结果、同时在后台刷新。最需要记住的一点是：**写入不会让缓存失效。** 你刚更新了一行，紧接着用同样的语句去读，拿到的可能还是更新前的结果。

这对游戏是危险的。下面这些读取绝不能走缓存：

- 余额、库存、订单状态。
- 权限和封禁状态。
- 任何"写完马上读"的流程。

官方推荐的做法是为同一个数据库建两个配置，一个开缓存，一个关缓存：

```bash
npx wrangler hyperdrive create game-db-fresh --connection-string="postgres://..." --caching-disabled
```

```jsonc
"hyperdrive": [
  { "binding": "HYPERDRIVE", "id": "<开缓存的配置 ID>" },
  { "binding": "HYPERDRIVE_FRESH", "id": "<关缓存的配置 ID>" }
]
```

代码里按用途选择。更安全的默认值是反过来：**默认用不缓存的那个，只有明确可以接受延迟的查询才用带缓存的。** 商品列表、排行榜快照、活动配置这类数据适合缓存。

还有两个细节：包含 `NOW()`、`RANDOM()` 这类非确定性函数的查询不会被缓存；判断方式是文本匹配，所以注释里出现这些函数名，也会让一条本可缓存的查询变成不缓存。

### 它在这套架构里的位置

引入外部数据库之后，各类数据的归属不变，变的只是 D1 的那一格：

- 玩家自己的数据仍然在玩家对象里，对象仍然是它的唯一写入者。
- 外部数据库承担的是原来 D1 的角色：需要跨玩家查询的数据，以及 D1 做不了的分析型查询。
- 两边的同步仍然走队列，带操作编号，允许延迟。

还有两条使用上的建议：

- **由 Worker 或队列的消费者访问外部数据库，不要让房间对象在处理回合时去查。** 一次跨洲查询几十毫秒，等待期间别的消息可以插进来（见 3.6 节），对象也无法休眠。
- **认清代价。** 这套技术栈最大的好处是没有需要运维的东西，而外部数据库的备份、升级、扩容、监控和账单都要有人负责。它是 D1 确实不够用时的出口，不是起步时的默认选择。

本书的示例项目不使用 Hyperdrive，后面的章节都以 D1 为准。

## 3.12 数据变大以后

第 1 章列过天花板，这里给出具体的处理顺序。

### 单个对象

单个对象上限 10 GB。玩家对象正常情况下远远到不了，会无限增长的只有流水和历史记录这类表，定期清理或归档即可。可以用 `ctx.storage.sql.databaseSize` 读到当前数据库的字节数，作为指标上报，提前发现异常增长的玩家。

房间对象在对局结束后就没用了。数据留着会一直计费，应该在结算完成后调用 `ctx.storage.deleteAll()` 清空，它会删掉对象的整个数据库；在本书使用的兼容日期下，还会一并删掉定时器。示例项目目前没有清理，第 5 章处理房间的生命周期时补上。

### D1 接近 10 GB

按下面的顺序处理，前面的手段代价更低：

1. **先确认里面的数据该不该在这里。** 最常见的原因是把日志、埋点、玩家明细放进了 D1。日志和埋点各有专门的去处（第 10 章），玩家明细应该在玩家对象里。
2. **归档冷数据。** 一年前的订单、已结束的赛季，导出到 R2，线上库只留近期数据。
3. **拆库。** 官方给 D1 的定位就是横向扩展成多个小库。按地区、按玩家 ID 的哈希，或者按时间拆。每个库都要在配置文件里声明绑定，所以适合拆成固定的几个到几十个库，由代码根据键选择用哪一个。跨库的查询要在应用层合并，这是拆库的主要代价，拆之前要确认查询都能按拆分键路由。
4. **外接数据库。** 如果业务确实需要一个大的关系型数据库，通过 Hyperdrive 连接外部的 Postgres 或 MySQL，做法见 3.11 节。接口层和对象层不用动，只是 D1 那部分查询换了目标。这一步意味着重新引入一个需要运维的组件，是最后的选择。

## 3.13 备份与恢复

**对象存储**支持按时间点恢复，可以回到过去 30 天内的任意时刻。接口是 `getCurrentBookmark()`、`getBookmarkForTime()` 和 `onNextSessionRestoreBookmark()`。要注意它的粒度是单个对象：能把某一个玩家的存档恢复到昨天，但没有"把全服回档"的一键操作。这对处理个别玩家的数据事故很有用，比如某次错误的发奖。

**D1** 有类似的时间旅行功能，付费版可以恢复到过去 30 天内的任意一分钟，免费版是 7 天。恢复是原地覆盖，进行中的查询会被取消。

两者都只保护"数据被写坏"，不保护"数据被逻辑上合法地改错"。所以涉及资产的变动一定要记流水：有了流水，才能算出谁被多发了、多发了多少，再写一笔反向的记录去修正，而不是回档。

- `server/src/room.ts`：对局结束时写入待结算记录，逐个调用玩家对象，失败后由定时器重试；心跳改由平台自动应答。

## 本章小结

- Durable Object 是带私有存储的单线程实体，按名字寻址，访问时隐式创建。它会休眠、会被移出内存、会被重启，没有关闭前的回调，所以内存只是缓存。
- 冷启动的成本主要来自你自己的代码和对象的位置：顶层代码和构造函数要轻，数据按需加载，首次访问决定对象建在哪里，发版会带来一波集中的重启和重连。
- 空闲 10 秒且没有东西阻止时对象进入休眠，休眠不计时长费用。心跳用自动应答，定时任务用定时器，不要用 `setInterval`。
- 先给数据分类，再选存储。谁是唯一的写入者，数据就放在谁的对象里；只有需要跨玩家检索的才进 D1。
- 对象存储有键值和 SQL 两套接口。整块存取用前者，部分更新和会增长的数据用后者。
- 表结构迁移由每个对象在唤醒时自己完成。迁移列表只追加，新结构要让旧代码也能用。
- 等待存储时不会被别的消息插入，等待外部调用时会。读、改、写之间不要等待外部调用。
- 跨对象没有事务。用"先记下要做什么、接收方按编号去重、发送方重试到成功"来保证最终一致且只生效一次。
- 默认不在内存里缓存。存储写入按行计费，减少写入的办法是减少消息。
- KV 只放配置，绝不放余额和计数器；R2 放大对象；队列的消费者必须幂等。
- Hyperdrive 用来连接外部的 Postgres 或 MySQL。事务要短；写入不会让查询缓存失效，余额和订单这类读取必须走关闭缓存的配置；一个请求里有多条顺序查询时，用 placement 让那个 Worker 靠近数据库运行；本地模式下连接池和缓存都不生效。
- 资产变动一定要记流水，它是出事故之后唯一能用来修正数据的依据。
