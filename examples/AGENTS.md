# 写给 AI 编程助手的约定

开始任何改动前先读完这个文件。

## 目录分工

- `shared/`：协议类型和游戏规则。规则必须是纯函数，不能出现任何平台接口、时间和随机数；随机数由调用方传入。
- `server/`：Worker 入口和 Durable Object。只负责连接、鉴权、调用规则、保存和广播状态，不写游戏规则。鉴权相关的代码都在 `server/src/auth/`。
- `client/`：联调用的最小页面，不要往里加功能。

## 必须遵守

- 改了规则就要改 `shared/src/rules.test.ts`；改了接口或房间行为就要改 `server/test/`。
- 交付前运行 `npm run typecheck` 和 `npm test`，两者都通过才算完成。
- 改了 `server/wrangler.jsonc` 之后运行 `npm run types -w server`。
- 新增绑定时，`env.staging` 里要同步声明，绑定不会被环境继承。
- 对象的内存状态会在休眠后清空，任何需要保留的数据都要写进存储。
- 读、改、写之间不要等待外部调用（网络请求、对其他对象的调用）。先把自己的状态存好再调用外部。
- 一个对象要让另一个对象改数据时，必须带操作编号：发送方先把待办记进自己的存储，接收方按编号去重，发送方重试到成功。参照 `room.ts` 的 `settle` 和 `player.ts` 的 `applyMatchResult`。
- 任何改动玩家资产的操作都要写流水表，并且和余额的修改在同一个事务里。
- `player.ts` 的 `MIGRATIONS` 只能在末尾追加，已有条目不能改。新的表结构必须让上一个版本的代码也能正常运行。
- 余额、计数器、库存不能放进 KV。
- 房间里所有的状态变化都通过 `Room.apply` 走规则，不要在别处直接改状态或直接写 `state` 这个键。
- 新的玩法行为先在 `shared/src/rules.ts` 里加操作，并说明它在等待、对局中、已结束三个阶段各自的结果；时间不进规则，超时由房间判断后作为操作传入。
- 规则必须保证每一局都能在有限时间内结束，不依赖任何玩家在线。
- 解析客户端消息时只取认识的字段并重新组装对象，不要把客户端传来的对象原样往后传。
- 会改变对局的客户端消息要带状态版本号，服务端核对后才执行。
- 房间里需要"到点执行"的事，把到期时间记进 `Timers` 并调用 `arm`，不要直接调用 `setAlarm`。`alarm` 里每件事都要自己检查是否到期。
- 清理房间只能安排在结算全部成功之后。
- 结算名单是参加了这一局的所有人（座位上的加上 `forfeited`），不是结束时还在的人。
- 服务端主动断开连接时使用 `shared/src/protocol.ts` 里定义的关闭码，新增关闭码时说明客户端该不该重连。
- 玩家 ID 只能从校验通过的访问令牌里取（`authenticate` 或 `authenticateWebSocket` 的返回值）。不要从地址、请求体或客户端的请求头里读玩家 ID。
- 新增的 HTTP 接口默认需要登录。不需要登录的接口必须限流，并在改动说明里单独列出。
- 入口把玩家 ID 传给对象时，用 `headers.set` 覆盖请求头，不要用 `append`。
- 校验外部平台的数据时，先验签名再使用其中的任何字段，并检查签发时间。比较签名用 `crypto.subtle.verify` 或 `crypto.subtle.timingSafeEqual`，不要用 `===`。
- 新增密钥时，加进 `wrangler.jsonc` 的 `secrets.required`（顶层和 `env.staging` 都要加）、`.dev.vars.example` 和 `vitest.config.ts`。
- `server/src/index.ts` 只能导出处理器和对象类。常量和工具函数放到别的模块，否则开发服务器无法启动。
- 交付前除了测试，还要确认 `npm run dev` 能正常启动。
- 涉及限额、价格、接口签名时查 Cloudflare 官方文档，不要凭记忆。

## 不要做

- 不要运行 `wrangler deploy`、`wrangler rollback` 或任何会改动线上环境的命令。
- 不要在对象里使用 `setInterval` 或 `setTimeout` 做定时任务，用定时器接口（`ctx.storage.setAlarm`）。前者会让对象无法休眠。
- 不要在代码里应答心跳，心跳由 `setWebSocketAutoResponse` 处理。
- 不要用模块级的全局变量保存对象的状态。
- 不要在模块顶层或构造函数里做重活（解析大配置、读全量数据、发网络请求），它们在每次冷启动时都会执行。
- 不要修改已有 RPC 方法的签名或含义，只能新增方法或可选参数。发版期间新旧版本会并存。
- 不要给对象用固定的名字（比如 `"global"`），除非已经说明它的请求量上限和分片方案。
- 不要在房间对象里等待外部接口或模型返回。
- 不要为了省事在内存里缓存状态，除非有测量数据说明存储读取是瓶颈。
- 不要改动支付、发奖、货币相关的代码而不单独说明。
- 不要把密钥、令牌、游客凭证写进日志、错误信息或对象的名字里。
- 不要把余额、等级、权限这类会变化的数据放进访问令牌。
- 不要改动令牌的格式、有效期或校验逻辑而不单独说明。

## 每次改动后要回答

1. 改了哪些文件，为什么。
2. 客户端发给服务端的消息频率有没有变化。
3. 房间对象还能不能正常休眠。有没有新增会阻止休眠的东西（`setTimeout`、等待中的外部调用）。
4. 存储的写入次数有没有变化。
