# 写给 AI 编程助手的约定

开始任何改动前先读完这个文件。

## 目录分工

- `shared/`：协议类型、游戏规则和匹配规则。规则必须是纯函数，不能出现任何平台接口、时间和随机数；随机数和当前时间由调用方传入。
- `server/`：Worker 入口和 Durable Object。只负责连接、鉴权、调用规则、保存和广播状态，不写游戏规则。鉴权相关的代码都在 `server/src/auth/`。
- `client/`：联调用的最小页面，不要往里加功能。

## 必须遵守

- 改了规则就要改 `shared/src/rules.test.ts`；改了接口或房间行为就要改 `server/test/`。
- 交付前运行 `npm run typecheck` 和 `npm test`，两者都通过才算完成。
- 改了 `server/wrangler.jsonc` 之后运行 `npm run types -w server`。
- 新增绑定时，`env.staging` 里要同步声明，绑定不会被环境继承。
- 对象的内存状态会在休眠后清空，任何需要保留的数据都要写进存储。
- 读、改、写之间不要等待外部调用（网络请求、对其他对象的调用）。先把自己的状态存好再调用外部。
- 一个对象要让另一个对象改数据时，必须带操作编号：发送方先把待办记进自己的存储，接收方按编号去重，发送方重试到成功。参照 `room.ts` 的 `settle` 和 `player.ts` 的 `applyMatchResult`。
- 任何改动玩家资产的操作都要写流水表，并且和余额的修改在同一个事务里。
- `player.ts` 的 `MIGRATIONS` 只能在末尾追加，已有条目不能改。新的表结构必须让上一个版本的代码也能正常运行。
- 余额、计数器、库存不能放进 KV。
- 房间里所有的状态变化都通过 `Room.apply` 走规则，不要在别处直接改状态或直接写 `state` 这个键。
- 新的玩法行为先在 `shared/src/rules.ts` 里加操作，并说明它在等待、对局中、已结束三个阶段各自的结果；时间不进规则，超时由房间判断后作为操作传入。
- 规则必须保证每一局都能在有限时间内结束，不依赖任何玩家在线。
- 解析客户端消息时只取认识的字段并重新组装对象，不要把客户端传来的对象原样往后传。
- 会改变对局的客户端消息要带状态版本号，服务端核对后才执行。
- 房间里需要"到点执行"的事，把到期时间记进 `Timers` 并调用 `arm`，不要直接调用 `setAlarm`。`alarm` 里每件事都要自己检查是否到期。
- 清理房间只能安排在结算全部成功之后。
- 结算名单是参加了这一局的所有人（座位上的加上 `forfeited`），不是结束时还在的人。
- 服务端主动断开连接时使用 `shared/src/protocol.ts` 里定义的关闭码，新增关闭码时说明客户端该不该重连。
- 玩家 ID 只能从校验通过的访问令牌里取（`authenticate` 或 `authenticateWebSocket` 的返回值）。不要从地址、请求体或客户端的请求头里读玩家 ID。
- 新增的 HTTP 接口默认需要登录。不需要登录的接口必须限流，并在改动说明里单独列出。
- 入口把玩家 ID 传给对象时，用 `headers.set` 覆盖请求头，不要用 `append`。
- 校验外部平台的数据时，先验签名再使用其中的任何字段，并检查签发时间。比较签名用 `crypto.subtle.verify` 或 `crypto.subtle.timingSafeEqual`，不要用 `===`。
- 新增密钥时，加进 `wrangler.jsonc` 的 `secrets.required`（顶层和 `env.staging` 都要加）、`.dev.vars.example` 和 `vitest.config.ts`。
- `server/src/index.ts` 只能导出处理器和对象类。常量和工具函数放到别的模块，否则开发服务器无法启动。
- 交付前除了测试，还要确认 `npm run dev` 能正常启动。
- 房间只能由服务端调用 `Room.open` 开出来，房间号用 `newUniqueId()` 生成。不要新增按名字访问房间的路径，也不要把 `open` 暴露成 HTTP 接口。
- 每一种开房方式都要有开局期限（`Timers.start`），保证没人来的房间会被清理。
- 分数、地区和玩家 ID 一样，由入口从玩家对象和 `request.cf` 读取后写进请求头，不接受客户端传入。
- 匹配对象里没有队列表，排队的人就是还连着的连接。不要另外存一份队列。
- 在对象里调用别的对象之前，先同步地把"正在处理"的状态标记好（参照 `Matchmaker.run` 里的 `mark`），等待期间别的事件会插进来。
- 机器人和录像是房间里由服务端出手的座位，通过规则操作入座和出手，不要为它们绕过规则直接改状态。结算时跳过 `isServerSeat` 的座位。
- 机器人的决策用规则算法，写成 `shared/` 里的纯函数，不要调用模型。
- 改了 `Action` 的种类或含义时，同步检查 `room.ts` 里写日志的地方和 `match/record.ts` 里生成录像的地方。
- 往队列里发的消息，消费者必须能重复处理：写 D1 用主键加 `INSERT OR IGNORE`。新增队列时同时配置死信队列。
- D1 的表结构变更写成 `server/migrations/` 里的新文件，已有的文件不能改。
- 玩家对象要让外面知道的任何变化（写 D1 的副本、通知另一个玩家）都走发件箱：在修改数据的同一个事务里调用 `emit`，事务之后调用 `flush`。不要在玩家对象里直接写 D1 或直接调用另一个玩家对象。
- 新增通知种类时，在 `social/events.ts` 的 `PlayerEvent` 里加类型、在 `handleOne` 里加处理，并说明它为什么可以被重复处理、乱序到达时会怎样。
- 通知里带当前值，不带增量。接收方按 `seq` 覆盖，或者按编号去重。
- 由消费者调用的玩家对象方法（`friendIncoming`、`friendConfirm`、`friendRemoved`、`grantInviteReward` 这一类）必须能重复执行。
- 接口里出现别的玩家的 ID 时，先按格式校验，再确认玩家存在（`getPublic().exists`），然后才做别的。
- 任何一个玩家能让另一个玩家的对象写入数据的地方，都要有数量上限。
- 排行榜的查询要有读取行数的上限。不要写会随玩家总数增长的查询（不带 `LIMIT` 的 `COUNT`、`OFFSET` 翻页）。
- 发奖一律写流水并按操作编号去重，包括金额为 0 的情况。
- 金币、宝石、道具的任何增减都通过 `Player.transact`（或事务里的 `applyDelta`）完成。不要新增直接修改 `profile.coins`、`profile.gems` 或 `item` 表的语句。
- "扣什么、给什么"写成一次变更（一个 `Delta`），不要拆成两次调用。
- 涉及钱的测试最后调用 `audit()`，确认余额和流水对得上。
- 价格、奖励数量只从服务端的商品表和常量里取，不接受客户端或第三方回调里带来的数值。
- 金额用整数的最小单位，不用小数。
- 玩家发起的购买必须带客户端生成的编号；服务端发起的变更用业务上的唯一标识做编号（订单号、对局编号、广告平台的观看编号）。
- 新增支付渠道时走已有的 `createOrder`、`fulfillOrder`、`refundOrder`，不要另写发货逻辑。
- 回调接口先校验来源再读内容：用请求体或查询串的原文验签名，检查时间，比较用 `safeEqual` 或 `crypto.subtle.verify`。
- 回调的应答规则：处理成功才返回 2xx；暂时处理不了（对象不可用、通知来早了）返回非 2xx 让对方重发；永远处理不了的（格式不对、不认识的类型）返回 2xx。新增回调时把每一种到达顺序都走一遍。
- 调用支付平台创建资源的接口时带幂等键。
- 流水只增不改。退款、冲正、追回都是新的一笔反向流水。
- 涉及限额、价格、接口签名时查 Cloudflare 官方文档，不要凭记忆。

## 不要做

- 不要运行 `wrangler deploy`、`wrangler rollback` 或任何会改动线上环境的命令。
- 不要在对象里使用 `setInterval` 或 `setTimeout` 做定时任务，用定时器接口（`ctx.storage.setAlarm`）。前者会让对象无法休眠。
- 不要在代码里应答心跳，心跳由 `setWebSocketAutoResponse` 处理。
- 不要用模块级的全局变量保存对象的状态。
- 不要在模块顶层或构造函数里做重活（解析大配置、读全量数据、发网络请求），它们在每次冷启动时都会执行。
- 不要修改已有 RPC 方法的签名或含义，只能新增方法或可选参数。发版期间新旧版本会并存。
- 不要给对象用固定的名字（比如 `"global"`），除非已经说明它的请求量上限和分片方案。
- 不要在房间对象里等待外部接口或模型返回。
- 不要在房间对象里直接读写 D1，对局记录走队列。
- 不要在读榜、读好友榜时逐个访问玩家对象，需要展示的字段放进 D1 的副本里。
- 不要在注册时发邀请奖励，也不要做多级邀请返利。
- 不要新增由客户端直接领取奖励的接口。奖励要有服务端自己能验证的依据。
- 不要把机器人令牌、支付密钥或带有它们的地址写进日志和错误信息。
- 不要在测试里向真实的支付平台发请求，对外的 `fetch` 一律用替身。
- 不要让匹配对象每秒空转，按 `planMatches` 返回的 `nextCheck` 设定时器。
- 不要为了省事在内存里缓存状态，除非有测量数据说明存储读取是瓶颈。
- 不要改动支付、发奖、货币相关的代码而不单独说明。
- 不要把密钥、令牌、游客凭证写进日志、错误信息或对象的名字里。
- 不要把余额、等级、权限这类会变化的数据放进访问令牌。
- 不要改动令牌的格式、有效期或校验逻辑而不单独说明。

## 每次改动后要回答

1. 改了哪些文件，为什么。
2. 客户端发给服务端的消息频率有没有变化。
3. 房间对象还能不能正常休眠。有没有新增会阻止休眠的东西（`setTimeout`、等待中的外部调用）。
4. 存储的写入次数有没有变化。
